## 1. Что предлагается

1. Каждая комната получает группу MLS (RFC 9420). Состав задают подписанные commit участников, а не список сервера плюс сертификаты [signed-membership.md](../security/signed-membership.md): сервер перестаёт быть источником истины о составе, остаётся доставка (Delivery Service).
2. Сообщения комнаты — `PrivateMessage`: данные отправителя зашифрованы в самом сообщении. Это даёт полноценный sealed sender на уровне протокола; серверный `author_tag` остаётся только для правки и удаления.
3. Шифронабор — гибрид X25519 + ML-KEM-768 (постквантовая конфиденциальность и PQ-восстановление после компрометации, PCS), подписи остаются Ed25519. Конкретный набор берётся из `draft-ietf-mls-pq-ciphersuites`, когда его поддержит OpenMLS (раздел 4).
4. Реализация — OpenMLS (Rust) → `wasm32-unknown-unknown`, загружается как статический модуль, закреплённый манифестом релиза. Альтернатива без WASM — `ts-mls` (раздел 3).
5. Историю после перезагрузки обеспечивает локальное зашифрованное хранилище расшифрованных сообщений (раздел 9): прямая секретность MLS стирает ключи сообщений.
6. Миграция — по одной комнате, через состояние `senderkeys → dual → mls` с подписанным переключением; комнаты, где есть участник без WASM, остаются на Sender Keys (раздел 11).
7. PQ-ratchet (5.7) для групп — это гибридный KEM-набор плюс регулярные обновления ключа листа и commit. SPQR рассчитан на двусторонние чаты; применять его только если появятся чаты 1:1 (раздел 12).

## 2. Цели и не-цели

### Цели

- **Ц1.** Восстановление после компрометации (PCS) для групп: утёкшее состояние участника перестаёт открывать будущие сообщения после его обновления или любого commit.
- **Ц2.** Постквантовая конфиденциальность ключей группы, в том числе против «перехватить сейчас, расшифровать потом» (HNDL) и PQ-PCS.
- **Ц3.** Состав группы меняют только участники своими подписями. Сервер не может добавить читателя; он может отказать в доставке или не убрать вышедшего.
- **Ц4.** Данные отправителя скрыты внутри сообщения; серверу не виден стабильный идентификатор отправителя (`senderKeyId` исчезает).
- **Ц5.** Стандартный протокол с формально разобранными свойствами и векторами тестов вместо самодельной цепочки.

### Не-цели

- **Н1.** Замена протокола сейчас: это дизайн; запуск — отдельное решение владельца после прототипа.
- **Н2.** Постквантовая подлинность: подписи остаются Ed25519. Квантовый противник сможет подделывать будущие сообщения и commit после появления CRQC, но не расшифровать записанное. Наборы с ML-DSA из драфта в охват не входят.
- **Н3.** Несколько устройств на аккаунт. Одно устройство, как сейчас.
- **Н4.** Скрыть от сервера состав комнаты, размеры, эпохи и порядок (раздел 8).
- **Н5.** Двусторонние чаты и SPQR (раздел 12).
- **Н6.** Группы больше 256 участников: оценка размера дерева с PQ-ключами (раздел 13) не позволяет.
- **Н7.** Федерация и совместимость с чужими клиентами MLS.

## 3. Сравнение с текущей схемой и реализация

### 3.1 Что есть и что даст MLS

| Свойство | Sender Keys + PQXDH (сейчас) | MLS с гибридным набором |
|---|---|---|
| Доставка ключа группы | попарно, PQXDH (гибрид X25519 + ML-KEM) | дерево TreeKEM, гибридный KEM на каждом узле пути |
| Прямая секретность | на цепочку: ключи сообщений кэшируются ради истории | по эпохе и поколению сообщения; использованный ключ удаляется |
| PCS | нет; только ротация при уходе участника и по счётчику (5.2) | да: после обновления листа или commit |
| PQ-PCS | нет | да, при гибридном наборе |
| Данные отправителя | `senderKeyId` виден серверу | зашифрованы (`encrypted_sender_data`) |
| Состав группы | список сервера + сертификаты (5.4) | дерево и commit участников |
| Стоимость | `O(n)` попарных key-share на ротацию | `O(log n)` на commit, но Welcome содержит дерево |
| История после перезагрузки | читается из кэша ключей | только из локального хранилища расшифрованного (раздел 9) |
| Размер групп | до 1000 по лимиту приглашений | до 256 (раздел 13) |

### 3.2 Реализация

- **OpenMLS** (Rust, поддерживают Phoenix R&D и Cryspen) → `wasm32-unknown-unknown` через `wasm-bindgen`. Сборка проекта CI под `wasm32-unknown-unknown` есть, но это сборка без исполнения тестов; запуск тестов в браузере и размер модуля надо проверить в прототипе.
- **Криптопровайдер**: RustCrypto (`openmls_rust_crypto`) для классических наборов; libcrux (`openmls_libcrux_crypto`) — формально верифицированные X25519 и ML-KEM, нужен для X-Wing/ML-KEM. Подпись и HPKE внутри WASM: ключи в памяти модуля.
- **Размер**: OpenMLS с провайдером — порядка единиц мегабайт до сжатия (оценка, измерить). Модуль грузится лениво, только когда комната уходит на MLS.
- **CSP** сегодня: `script-src 'self' 'nonce-…'` (`lib/security-utils.js`; nonce уйдёт по R10). WASM требует `'wasm-unsafe-eval'` в `script-src`. Директива разрешает `WebAssembly.compile/instantiate`, но не `eval` и не `new Function`. Это единственное ослабление CSP; `unsafe-eval` остаётся запрещён. Модуль грузится как `/vendor/mls/mls_bg.wasm` и входит в манифест релиза и SRI-проверки (R10).
- **Воспроизводимая сборка WASM**: закреплённый toolchain (`rust-toolchain.toml`), `cargo build --locked`, сборка в Docker, `wasm-bindgen` и `wasm-opt` закреплённых версий, `SOURCE_DATE_EPOCH`; в CI сравнение хэша двух независимых сборок; хэш модуля в `release/manifest.json`. Без воспроизводимости модуль нельзя проверить независимо (R10).
- **Tor Browser**: на уровнях «Повышенный» (Safer) и «Высокий» (Safest) WebAssembly выключен (NoScript). Участник без WASM не сможет работать в MLS-комнате. Следствия: (а) комната переходит на MLS, только если **все** текущие участники объявили поддержку; (б) пользователи Tor на повышенных уровнях остаются на Sender Keys; (в) комната, куда вступает такой участник, откатывается (раздел 11).
- **Без WASM**: `ts-mls` — реализация RFC 9420 на TypeScript, заявлена поддержка X-Wing и ML-KEM; работает и при выключенном WASM. Требует оценки зависимостей (`@hpke/core`, при необходимости `@noble/*`), вендоринга в `public/vendor/`, объёма аудита и скорости. Решение между OpenMLS/WASM и `ts-mls` принимается по итогам прототипа (раздел 14, фаза 0). Правило проекта «новые зависимости не ставим без обоснования» (agent-rules) действует и здесь.

## 4. Шифронабор и идентичность

### 4.1 Шифронабор

- Базовый классический набор: `0x0001` (X25519, AES-128-GCM, SHA-256, Ed25519). Годится для прототипа и как запасной вариант.
- PQ-набор: гибрид ML-KEM-768 + X25519 из `draft-ietf-mls-pq-ciphersuites` (версия -06 на 2026-10-09 описывает гибридные и чисто ML-KEM наборы; перечень и кодовые точки перепроверить). OpenMLS поставляет экспериментальный набор X-Wing + ChaCha20-Poly1305 (`0x004D`), кодовая точка не закреплена IANA, совместимость с чужими реализациями не гарантируется. Для замкнутой системы (клиент и сервер Nyxo) это допустимо, но группа привязана к набору: смена — через `ReInit` (новая группа).
- Выбор: стартовать на наборе, который поддержит провайдер и закроет драфт; кодовые точки частного использования (диапазон `0xF000–0xFFFF`) допустимы до присвоения IANA.
- Оценка издержек (по данным Cryspen для X-Wing, замерено на малой группе): KeyPackage около 2,7 КБ против 0,3 КБ; Welcome около 5,5 КБ против 0,7 КБ; самообновление около 4 КБ против 0,5 КБ. Проекту это приемлемо для групп до сотен участников.

### 4.2 Идентичность и учётные данные

- Учётные данные листа — `BasicCredential`, идентичность — `u32be(userId)`.
- Ключ подписи листа MLS **отдельный** от identity-ключа Ed25519 аккаунта: подписи OpenMLS синхронны, а неизвлекаемый `CryptoKey` Web Crypto подписывает асинхронно. Следствие: ключ подписи листа лежит в памяти WASM и в хранилище устройства в извлекаемом виде (слабее неизвлекаемого identity-ключа; предел против XSS, раздел 13).
- **Привязка к identity.** Расширение KeyPackage/LeafNode (тип из диапазона частного использования): `{ identitySignPub[32], sig[64] }`, `sig = Ed25519(identity, "nyxo-mls-bind-v1\0" ‖ u16be(ciphersuite) ‖ u32be(userId) ‖ leafSignaturePub[32])`.
- **Служба аутентификации (AS).** Участник принимает лист, только если привязка проверена закреплённым identity-ключом этого `userId` (то же закрепление, коды безопасности и проверка по журналу [key-transparency.md](../security/key-transparency.md), что и сегодня). Новый identity (смена ключа) = лист отвергается до решения пользователя.
- Метки домена добавляются в общий реестр: `nyxo-mls-bind-v1\0` (привязка листа), `nyxo-mls-join-v1\0` (подпись входа по ссылке), `nyxo-msg-v1\0` (AAD сообщения), `nyxo-room-v1` (идентификатор группы: `group_id = "nyxo-room-v1" ‖ u32be(roomId)`).

## 5. KeyPackage

- Каждый клиент выкладывает пачку одноразовых KeyPackage (по 30–50) и один `last resort` (по образцу PQ-prekey 5.1): когда одноразовые закончились, выдаётся `last resort`.
- `lifetime` ≤ 7 суток для одноразовых (как ротация SPK), для `last resort` — до 30 суток; `last resort` имеет расширение `last_resort`.
- Хранилище `lib/key-store.js`, таблица `mls_key_packages(id BIGSERIAL, user_id, kind SMALLINT, data BYTEA, PRIMARY KEY (id))`, индекс по `user_id`; время создания хранится с точностью до суток (T3.2). Пачка пополняется, когда остаток ниже порога (как `LOW_WATER_OPK`).
- API: `POST /api/keys/key-packages` (батч, ≤ 200 за запрос, подпись привязки проверяется сервером для защиты в глубину), `GET /api/keys/key-package/:userId` (общая комната или заявитель, лимиты как у `bundle`), счётчик остатка.
- **Атака исчерпания**: участник может выкачать чужие одноразовые KeyPackage. Лимит на пару (как у bundle, 5/час) и `last resort` ограничивают ущерб; последствие — Add через `last resort` (слабее прямая секретность первого сообщения).
- Размер хранения: 50 × 2,7 КБ ≈ 135 КБ на пользователя.

## 6. Сервер доставки (Delivery Service)

### 6.1 Таблицы (схема в DDL по R0 к моменту запуска; иначе `lib/migrations`)

```sql
CREATE TABLE mls_groups (
  room_id    INTEGER PRIMARY KEY REFERENCES rooms(id) ON DELETE CASCADE,
  epoch      INTEGER NOT NULL,                     -- последняя принятая эпоха
  suite      INTEGER NOT NULL,
  group_info BYTEA,                                -- последний GroupInfo (подписан участником)
  gi_epoch   INTEGER
);
CREATE TABLE mls_handshake (
  room_id INTEGER NOT NULL REFERENCES rooms(id) ON DELETE CASCADE,
  epoch   INTEGER NOT NULL,                        -- эпоха, КОТОРУЮ создаёт commit
  data    BYTEA NOT NULL CHECK (octet_length(data) <= 262144),
  PRIMARY KEY (room_id, epoch)
);
CREATE TABLE mls_welcome (
  id           BIGSERIAL PRIMARY KEY,
  room_id      INTEGER NOT NULL REFERENCES rooms(id) ON DELETE CASCADE,
  recipient_id INTEGER NOT NULL,                   -- удаляется при выдаче и при удалении аккаунта
  data         BYTEA NOT NULL
);
```

Сообщения приложения остаются в `messages` (`encrypted = true`), `text` — `MLSMessage` в base64; форма проверяется `lib/e2ee-envelope.js` (новый вариант алгоритма `mls`).

### 6.2 Правила

- **Commit принимается только на текущей эпохе.** Запрос `POST /api/mls/:room/commit { epoch, commit, welcomes[], groupInfo }`: под `mls_groups FOR UPDATE` проверяется `epoch = mls_groups.epoch + 1`; иначе 409 `{ code:'mls-epoch-conflict' }`, клиент загружает журнал и повторяет. Первичный ключ `(room_id, epoch)` — вторая страховка. Блокировка стоит после `rooms` в порядке [message-ordering.md](../security/message-ordering.md) §8.
- **Рассылка**: событие сокета `mlsHandshake { roomId, epoch }` (без данных), клиенты забирают `GET /api/mls/:room/log?after=<epoch>`.
- **Welcome** доставляется получателю один раз (`GET /api/mls/:room/welcome`), строка удаляется при выдаче; лимит ожидающих на получателя; запись удаляется при выходе и удалении аккаунта.
- **GroupInfo** (для внешнего входа) загружается вместе с commit и подписан участником; сервер хранит последний.
- **Журнал handshake** хранится, пока комната жива; для офлайн-участников. Размер журнала ограничен: старые эпохи вне окна `max_past_epochs` можно свернуть до GroupInfo (раздел 9).
- Сервер **не расшифровывает** и не проверяет криптографически содержимое commit: только форму (`MLSMessage`, `wire_format`, размер), эпоху и принадлежность отправителя комнате. Подлинность commit проверяют участники.
- Сообщения приложения: `POST /api/messages` как сейчас; в `PrivateMessage` `authenticated_data = "nyxo-msg-v1\0" ‖ u32be(messageId)`: шифротекст привязан к `id` строки ([message-ordering.md](../security/message-ordering.md) §6), поэтому проверка `mid` сохраняется вдвойне (внутри содержимого и в AAD MLS).

## 7. Состав и права

Политики 5.4 превращаются в правила проверки commit у получателей (сервер их не навязывает):

| Событие | Реализация в MLS |
|---|---|
| Вход по одобрению | участник, одобривший заявку, делает commit с `Add` по KeyPackage заявителя (привязка проверена); человек решает, как сегодня (код безопасности). Сертификаты допуска не нужны: подпись commit — допуск |
| Вход по ссылке | расширение `GroupContext`: `nyxo_invite { invitePub, expiresMin }`, его ставит commit приглашающего. Вошедший делает **внешний commit** по GroupInfo и кладёт в `authenticated_data` подпись `Ed25519(ключ приглашения, "nyxo-mls-join-v1\0" ‖ group_id ‖ epoch ‖ leafSignaturePub)`. Участники принимают внешний commit, только если подпись проверена `invitePub` и срок не истёк. Секрет `s` выводит ключ приглашения тем же HKDF, что в [signed-membership.md](../security/signed-membership.md) §6.5. Вариант с PSK из секрета проще для модели, но требует знания секрета всеми участниками; здесь не принят |
| Код без секрета | заявка (как сегодня) |
| Выход, удаление аккаунта | MLS запрещает участнику убрать себя commit'ом. Удаление делает другой участник: `Remove` для листа, которого уже нет в списке сервера. Исполнитель определяется правилом: минимальный `userId` среди присутствующих; если за 5 секунд (плюс 5 секунд на ранг) commit не пришёл, следующий |
| Убрать чужого | получатели **отвергают** `Remove`, если цель всё ещё в списке сервера и не сам committer (защита от враждебного участника, исключающего других) |
| Неподтверждённый участник | понятие сохраняется: лист без проверенной привязки к identity отвергается AS |
| Хэш взгляда на ключи | заменён MLS: `tree_hash` и `confirmation_tag` каждой эпохи общие для группы; раздвоение сервера даёт неспособность расшифровать сообщения друг друга. Сверка `epoch_authenticator` (короткий отпечаток) — необязательная ручная проверка |
| Прозрачность ключей | сохраняется: журнал проверяет identity-ключи, к которым привязаны листья |

Сервер больше не источник истины о составе: расхождение списка сервера и дерева MLS — предупреждение пользователю, а не молчаливое подчинение.

## 8. Метаданные

- `PrivateMessage` шифрует данные отправителя (индекс листа, поколение) и содержимое. Серверу виден: `group_id` (= комната), `epoch`, тип содержимого (`application`/`commit`/`proposal`), размер шифротекста с паддингом, момент приёма и сессия отправителя запроса.
- Паддинг: `padding_size` в политике группы (блоками по 256 байт, как Padmé в текущем коде).
- Эпоха меняется при каждом commit; число эпох и их время раскрывают частоту изменений состава.
- `author_tag` ([sealed-sender.md](../security/sealed-sender.md)) остаётся: он нужен для правки, удаления и отметок прочтения на стороне сервера. Он не заменяет и не раскрывает данные отправителя в сообщении. Если правка и удаление по автору станут не нужны, тег можно убрать.
- Welcome раскрывает серверу пару «получатель — комната» на время хранения (как сегодня `e2ee_key_shares`).
- Живой сервер по-прежнему видит отправителя запроса: sealed sender на хранении и внутри сообщения, а не на сети.

## 9. История и хранилище на устройстве

Прямая секретность стирает ключи сообщений, поэтому после перезагрузки сообщение нельзя расшифровать повторно (в Sender Keys можно). Решение:

- Расшифрованное сообщение сохраняется в `msgstore:<room>:<mid>` = AES-256-GCM-шифротекст на неизвлекаемом ключе устройства (`CryptoKey` в IndexedDB), AAD `room ‖ mid`. Защита от чтения диска, но не от XSS на странице.
- Режим «Не хранить историю» (5.3): `msgstore` не пишется, после перезагрузки прежние сообщения нечитаемы — совпадает с задуманным.
- Таймер комнаты и исчезающие сообщения удаляют и локальные копии.
- Окно прошлых эпох `max_past_epochs` (предложение: 8): клиент хранит секреты последних эпох, чтобы расшифровать сообщения, пришедшие, пока он обрабатывал commit; офлайн дольше окна даёт пробел в истории («сообщение пришло, пока вы были не в сети»). Это регресс относительно Sender Keys; смягчается тем, что аккаунт живёт не дольше недели без активности.
- Загрузка истории с сервера (100 сообщений на страницу): для каждого сообщения нужна его эпоха; клиент применяет журнал commit по порядку и расшифровывает сообщения своей эпохи; вне окна — «недоступно».
- Состояние группы (`mls:state:<room>`) пишется транзакцией IndexedDB вместе с курсором журнала (последняя применённая эпоха).

## 10. Вкладки и целостность состояния

- Одна запись состояния на комнату, один писатель: Web Locks `nyxo-mls-<userId>-<roomId>` на всё чтение-изменение-запись состояния ([message-ordering.md](../security/message-ordering.md) §9.7 вводит Web Locks для Sender Keys, но его решение 3 в §16 от них отказалось; для MLS блокировка **обязательна**, так как разошедшиеся состояния необратимы).
- Приём commit: применить в памяти, записать состояние и курсор одной транзакцией, затем отправлять подтверждения. Отправка commit: сначала сервер, затем локальное применение после ответа 200.
- **Развилка** (локальная эпоха не сходится с журналом, потеряна запись, ошибка применения): восстановление внешним commit по актуальному GroupInfo с заменой собственного листа (`Remove` старого + `Add` нового с той же идентичностью). Политика получателей: внешний commit от идентичности, уже состоящей в группе, принимается как «ресинхронизация», если привязка к identity действительна. Пользователь видит служебную строку.
- Нет Web Locks: комната остаётся на Sender Keys (MLS без межвкладочной блокировки небезопасен).

## 11. Миграция с Sender Keys

Для каждой комнаты автомат состояний, хранящийся **на устройстве** и изменяемый только подписанным сообщением (сервер состояние не определяет — иначе понижение версии):

```
senderkeys ──(создана группа MLS, подписанный переключатель)──> dual ──(все подтвердили)──> mls
                          ^                                                                 │
                          └──────────── откат (участник без MLS вступил / ошибка) ─────────┘
```

1. **Возможность.** Клиент объявляет `mls` в key-store (флаг в метаданных пакета ключей: WASM работает, `Web Locks` есть, KeyPackage загружены). Комната мигрирует, когда флаг есть у **всех** текущих участников; на каждом новом участнике проверяется заново.
2. **Создание.** Любой участник (по правилу: минимальный `userId`) создаёт группу MLS, добавляет всех commit'ами и отправляет Welcome. Сразу после создания в канал Sender Keys уходит сообщение-переключатель `{ t:'mls-switch', groupId, epoch, treeHash, suite }`, подписанное так же, как обычные сообщения Sender Keys (подлинность участника-автора).
3. **`dual`**: клиент читает оба канала; новые сообщения отправляются через Sender Keys до тех пор, пока каждый участник не прислал подтверждение в MLS (`application`-сообщение `mls-ack`). Затем `mls`.
4. **`mls`**: новые сообщения — только MLS; клиент **не принимает** новые сообщения Sender Keys в этой комнате (защита от понижения: сервер не может «вернуть» старый канал). Старая история остаётся на Sender Keys и читается прежним кодом, пока не истечёт.
5. **Откат**: вступил участник без MLS, или ошибка группы. Подписанный `mls-switch-back` в MLS-канале; комната возвращается на Sender Keys, группа MLS удаляется. После отката повторная попытка не раньше чем через сутки.
6. **Новые комнаты** после запуска создаются сразу в `mls` (если создатель поддерживает), состояние `mls` — в `GroupContext`; вступивший по Welcome говорит только на MLS.
7. **Что остаётся в коде**: Sender Keys, 5.2/5.3 и подписанный состав остаются, пока существуют комнаты старого режима. Удаление этого кода возможно только после того, как все живые комнаты перейдут (комнаты временные: срок жизни в неделях).

## 12. PQ-ratchet (5.7)

- Для групп постквантовое восстановление после компрометации даёт **гибридный KEM в TreeKEM** плюс регулярные обновления: каждый активный участник обновляет лист (`Update` в commit) каждые N = 50 своих сообщений или T = 24 часа (что раньше), и при любом изменении состава. Между обновлениями секрет эпохи PQ-устойчив, как только закрыт первым гибридным KEM-шагом.
- **SPQR** (Sparse Post-Quantum Ratchet, Signal, 2025) — PQ-ratchet для двусторонней Double Ratchet: «Triple Ratchet» с ML-KEM-768. У Nyxo двустороннего ratchet нет: комната на двоих — группа MLS из двух листьев, где обновление листа уже даёт PQ-PCS на гранулярности commit. Применять SPQR стоит только при появлении чатов 1:1 с собственной цепочкой на каждое сообщение.
- Хвост риска: между обновлениями квантовый противник с записанным трафиком и компрометацией состояния читает до следующего обновления; интервал N/T — компромисс стоимости и защиты.

## 13. Пределы и риски

| № | Риск или предел | Оценка и меры |
|---|---|---|
| 1 | Размер группы. Дерево с PQ-листьями: лист около 1,5 КБ, внутренние узлы с ключами по 1,2 КБ; Welcome с деревом около 3 КБ на участника | 100 участников — порядка 300 КБ, 1000 — около 3 МБ на Welcome. Предел MLS-комнаты — 256; большие остаются на Sender Keys (текущий предел приглашений 1000) |
| 2 | Размер WASM и CSP | измерить в прототипе; `'wasm-unsafe-eval'` единственное ослабление; модуль в манифесте и SRI |
| 3 | Tor Browser «Повышенный»/«Высокий» без WASM | комната остаётся на Sender Keys; альтернатива — `ts-mls` |
| 4 | Развилки состояния, коллизии commit | серия 409 и повтор; назначенный исполнитель; ресинхронизация внешним commit (раздел 10) |
| 5 | Всплеск commit из-за исчезающих аккаунтов | временные аккаунты истекают постоянно: каждый уход — commit. Пакетирование: исполнитель объединяет `Remove` нескольких ушедших за ≤ 30 секунд в один commit |
| 6 | Исчерпание KeyPackage | лимиты, `last resort`, пополнение (раздел 5) |
| 7 | Ключ подписи листа извлекаем | слабее, чем у identity-ключа; защита от XSS — CSP и R10; альтернатива — подписание в отдельном воркере с неизвлекаемым ключом (асинхронный мост, усложнение OpenMLS API) |
| 8 | Статус аудита OpenMLS и PQ-наборов | перед запуском выяснить: независимый аудит, статус X-Wing/libcrux («экспериментальный» у поставщика), IANA-кодовые точки; решение о запуске зависит от ответа |
| 9 | Драфт набора не окончательный | частные кодовые точки, группа привязана к набору; смена — `ReInit` |
| 10 | Поддержка Rust toolchain и `wasm-bindgen` | закрепление версий, обновления по Dependabot-подобной процедуре, воспроизводимая сборка |
| 11 | Регресс истории | окно `max_past_epochs`, локальное хранилище; честное объяснение в «Как это работает» |
| 12 | Подпись остаётся Ed25519 | постквантовой подлинности нет (Н2) |

## 15. Тестирование

- Векторы RFC 9420 и репозитория `mls-implementations` (key schedule, tree math, secret tree, messages, welcome, treesync); в Node и в браузере (WASM) одинаковые.
- Фаззинг разбора `Welcome`, `Commit`, `GroupInfo`, `PrivateMessage` обёртки (`cargo fuzz`) и валидации расширений Nyxo.
- Протокольные тесты на fake-DS (по образцу `test/fake-server.js`): параллельные commit (409 и повтор), офлайн-догон журнала, удаление ушедших, пакетный `Remove`, внешний commit по ссылке (верный, просроченный, чужая подпись), ресинхронизация, Welcome с чужой привязкой identity, листья со сменой identity-ключа, откат миграции, запрет принятия Sender Keys в `mls`-комнате, MLS-сообщение под чужим `id` (AAD).
- Сквозные (Postgres): `epoch` и конфликт 409, удаление Welcome при выдаче и выходе, удаление комнаты каскадом, лимиты KeyPackage.
- Нагрузочные: время commit и размер Welcome для 32/128/256 участников; потребление памяти WASM.
- Воспроизводимость WASM: две независимые сборки дают один хэш.

## 16. Выкат

- Решение о запуске принимается после фазы 0 и ответа по аудиту (риск 8). Включается серверной настройкой `MLS_ENABLED=yes` (выключено по умолчанию; без неё маршруты `/api/mls/*` отвечают 404, клиент не объявляет `mls`).
- Метрики без идентификаторов: число комнат по режиму, доля 409 при commit, остаток KeyPackage, число откатов миграции.
- Откат релиза — остановка включения; комнаты в `mls` читают историю локально и остаются работоспособными, пока работает клиент с MLS; если клиент без MLS, комната откатывается на Sender Keys по разделу 11.
- Тексты «Как это работает» и политика конфиденциальности: что меняется (история хранится на устройстве, регресс при долгом отсутствии, размер групп); обновляет T5.1.
