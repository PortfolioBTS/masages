## 1. Что предлагается

1. Упаковывать **тот же статический клиент** (`public/`), байт-в-байт равный файлам релиза из манифеста R10, в приложение: код становится частью подписанного пакета, а не приходит с сервера при каждом запуске. Это то, чего не даёт service worker (6.2): закрепление по подписи разработчика, а не по первому посещению.
2. Настольные системы (Windows, macOS, Linux) — **Tauri v2**; Android и iOS — **Capacitor**. Альтернатива — Tauri v2 на всех пяти платформах (вопрос 1 раздела 18).
3. Для работы пакетного клиента с сервером нужна **подготовка сервера и клиента** (раздел 8): запросы идут с другого origin, куки `SameSite=Lax` туда не доходят. Предлагается сессия по заголовку, а не по куке.
4. Обновления — только через подписанный канал: Tauri updater (подпись minisign, ключ вшит в приложение) и магазины для мобильных. Обновление кода «по воздуху» (live update) запрещено.
5. Ключи шифрования остаются в хранилище WebView (IndexedDB, неизвлекаемые `CryptoKey`), как в вебе; на втором шаге — обёртка ключом из системного хранилища (Keystore, Keychain). Резервное копирование данных приложения отключается.
6. Уведомления — без текста и без идентификаторов: «новое сообщение», приложение само забирает данные.
7. Tor: на настольных системах — прокси SOCKS; на Android — через Orbot или встроенный прокси WebView; на iOS в первой версии не поддерживается (рекомендуется Tor Browser и веб-клиент).
8. Этап — дизайн и подготовка: в этом документе нет кода приложений; перечень подготовительных правок репозитория — раздел 19.

## 2. Цели и не-цели

### Цели

- **Ц1.** Исполняемый код клиента закреплён подписью разработчика и совпадает с проверяемым релизом (манифест R10).
- **Ц2.** Подмена кода сервером невозможна для установленного приложения: сервер может только отдать данные, но не скрипты.
- **Ц3.** Сохраняются свойства сервиса: временные аккаунты, отсутствие аналитики и сторонних сервисов, минимум метаданных.
- **Ц4.** Нативные возможности используются там, где они усиливают приватность: хранилище ключей, уведомления без содержимого, запрет скриншотов и резервного копирования.
- **Ц5.** Один исходный клиент для веба и приложений; различия — в тонкой обёртке и в явном перечне (раздел 5).

### Не-цели

- **Н1.** Защита от скомпрометированного устройства, вредоносных расширений ОС и физического доступа к разблокированному устройству.
- **Н2.** Новые функции протокола: приложение говорит с сервером тем же API (плюс режим сессии по заголовку).
- **Н3.** Сборка и публикация сейчас. Нужны аккаунты разработчика Apple и Google, сертификаты подписи, юридические тексты и решение владельца.
- **Н4.** Совместимость старых версий приложений с новым сервером за пределами одного релиза: совместимость API на релиз (раздел 17).
- **Н5.** Поддержка нескольких устройств на аккаунт.
- **Н6.** Автообновление мобильных приложений вне магазинов.

## 3. Модель угроз

| Кто | Что видит или умеет | Что даёт приложение | Что остаётся |
|---|---|---|---|
| Злонамеренный сервер | отдаёт код и данные; ведёт обновления сайта | в приложении код вшит и подписан: выдать новый код нельзя; изменение возможно только новой подписанной версией | первая установка из ненадёжного источника; сервер видит те же метаданные, что и в вебе |
| Подмена канала загрузки приложения | сайт или зеркало отдаёт чужую сборку | подпись ОС (Authenticode, notarization, подпись APK/магазина), сверка хэша релиза | доверие к первой загрузке и каналу публикации (GitHub Releases, магазины) |
| Кража устройства без разблокировки | файловая система приложения | шифрование диска ОС; ключи обёрнуты ключом из Keystore/Keychain (шаг 2) | на разблокированном устройстве ключи доступны приложению |
| Облачные резервные копии | данные приложения попадают в резервную копию ОС | `allowBackup=false`, исключение из резервных копий iOS | пользовательские резервные копии устройства целиком |

| Вредоносный сайт или локальный процесс | пытается обратиться к API или подделать origin приложения | `Origin` приложения проверяется точным списком; запросы без заголовка сессии отклоняются | на Windows и Android origin приложения — обычный `http(s)://….localhost`: подделка локальным процессом возможна, но без сессии он ничего не получает |
| XSS внутри приложения | исполняет код в WebView | та же CSP, что в вебе (`script-src 'self'`); нет Tauri-команд для неизвестных страниц | активная XSS пользуется ключами, как в вебе |
| Магазин | может удалить приложение, потребовать изменений | — | политика магазинов к анонимным мессенджерам (раздел 15, строка 12) |

## 5. Упаковка веб-клиента

### 5.1 Принцип: те же байты

`scripts/build-native.js` (будущий): копирует файлы из `public/` в `dist-native/`, **проверяя каждый файл по `release/manifest.json`** (хэш SHA-256 совпадает с манифестом релиза того же тега), и добавляет файлы приложения:

| Файл | Откуда | Зачем |
|---|---|---|
| `native.html` | новый, в репозитории | входная страница приложения: те же `<script>`/`<link>` с теми же SRI, что в `index.html`, плюс CSP как `<meta>` (для Capacitor) и подключение `native/boot.js` до остальных скриптов |
| `native/boot.js` | новый | задаёт `window.NYXO_NATIVE = { apiBase, platform }`, отключает регистрацию service worker, подключает мосты (диплинки, уведомления) |
| остальные файлы | `public/**` | байт-в-байт |

В `index.html` ничего не меняется: хэш веб-манифеста остаётся прежним. Отдельный `release/manifest-native.json` перечисляет `native.html`, `native/boot.js` и ссылку на хэш веб-манифеста.

### 5.2 Чего нет в `public/` сегодня

- **База API.** Скрипты приложения (`public/js/*.js`, до волны 6 — один `public/script.js`) обращаются к `/api/…` относительно текущего origin и создают сокет без адреса. Для приложения нужен единственный настраиваемый `apiBase` в функции `api()` (`public/js/07-api-listeners.js`), в остальных прямых вызовах `fetch` (например, `05-attachments.js`, `09-auth-screen.js`) и при создании сокета (`public/js/01-state.js`); разбиение `script.js` уже выполнено, задача — раздел 19.
- **Режим сессии по заголовку** (раздел 8).
- **Отключение service worker** в приложении: у `tauri://` и `capacitor://` его нет или он бесполезен, закрепление даёт подпись пакета.
- **Диплинки** `#join=<КОД>.<секрет>` (раздел 10).

### 5.3 Версии

Версия приложения равна версии релиза (R10) плюс номер сборки приложения (`2.1.0+app3`). Хэш веб-манифеста показывается на экране «О приложении» рядом с хэшем нативного манифеста — для сверки с релизом на GitHub.

### 6.1 Tauri updater

- Ключевая пара minisign: `tauri signer generate`; открытый ключ — в `plugins.updater.pubkey` (содержимое, не путь), закрытый — **вне репозитория** (секрет CI `TAURI_SIGNING_PRIVATE_KEY` и пароль). Проверка подписи обязательна и не отключается.
- `bundle.createUpdaterArtifacts: true` создаёт пакет обновления и файл `.sig`; манифест обновлений — статический `latest.json` (`version`, `platforms.<ОС-архитектура>.url` и `.signature`) в GitHub Releases.
- Ключ updater — отдельный от ключей подписи ОС и от ключа прозрачности. Потеря закрытого ключа = обновления перестают приниматься, пользователям нужна ручная переустановка с новым ключом; план восстановления описывается в `docs/ops` (вопрос 6).
- Перед установкой приложение показывает версию и отпечаток нативного манифеста; пользователь может сверить с релизом.
- Обновление не должно ослаблять закрепление: `endpoints` — только `https://` собственного релиза; никаких «каналов» от сервера Nyxo.

### 6.2 Capacitor

Только магазины. **Live update** (Capgo, Appflow и подобные) запрещён: он снова доставляет код сервером, что обесценивает закрепление, и противоречит политикам магазинов. В релиз-чеклисте — проверка, что плагины OTA не подключены.

### 6.3 Конвейер

`.github/workflows/native-release.yml` на тег `v*`: матрица раннеров (Windows, macOS, Linux; для iOS — macOS), шаги: `npm ci`, `node scripts/build-native.js` (проверка хэшей), сборка, подпись, публикация артефактов и `latest.json`, аттестация происхождения (`actions/attest-build-provenance`), сверка хэшей опубликованных артефактов отдельным заданием. Все `uses:` закреплены полным SHA (правило `docs/dev/ci.md`); секреты подписи — в окружении `release` с обязательным подтверждением.

## 7. Закрепление кода: приложение против 6.1–6.2

| Свойство | Веб + service worker (6.2) | Приложение A/B |
|---|---|---|
| Первое получение кода | доверие к серверу (TOFU) | подпись ОС или магазина; каналу публикации нужно доверять |
| Подмена кода сервером после первого получения | возможна: сервер выдаёт новый `sw.js`; пользователь видит предупреждение, если не игнорирует | невозможна: код внутри пакета |
| Адресная подмена конкретному пользователю | ловится только ручной сверкой отпечатка | невозможна для установленного приложения |
| Обновление | баннер, пользователь нажимает «Обновить» | updater или магазин; подпись обязательна |
| Очистка данных сайта | молча сбрасывает закрепление | данные приложения и его код независимы |
| Tor Browser | service worker обычно недоступен | не применимо (приложение вне Tor Browser) |
| Что остаётся общим | CSP, SRI, манифест, проверка `/verify.html` | то же внутри пакета |
| Новые поверхности | — | цепочка поставки приложения (Rust, Tauri, Capacitor, плагины), подпись, магазины |

Вывод: приложения усиливают защиту от подмены кода сервером, но переносят доверие в цепочку поставки и ключи подписи. Эти ключи нужно беречь не слабее, чем `KT_SIGNING_KEY`.

## 8. CSP, origin и сессия

### 8.1 Откуда приходит клиент

| Платформа | Origin страницы (по документации; проверить при сборке) |
|---|---|
| Tauri v2, macOS, Linux, iOS | `tauri://localhost` |
| Tauri v2, Windows, Android | `http://tauri.localhost` (с `app.windows[].useHttpsScheme` — `https://tauri.localhost`) |
| Capacitor, Android | `https://<server.hostname>` (по умолчанию `https://localhost`) |
| Capacitor, iOS | `capacitor://<server.hostname>` (по умолчанию `capacitor://localhost`) |

Все они — **другой origin**, чем сервер Nyxo. Для Capacitor задаётся уникальное значение `server.hostname`, чтобы не совпадать с любым локальным `https://localhost`.

### 8.2 Что ломается

1. **Куки.** Сессионная кука `SameSite=Lax` не отправляется и не устанавливается при кросс-сайтовых запросах из WebView; `csrf_token` читается скриптом через `document.cookie` только со своего origin.
2. **Проверка Origin** (`isTrustedOrigin`): принимает только свой хост, `ALLOWED_ORIGINS` и onion. Функция `parseOrigin` разбирает **только `http:` и `https:`**, поэтому `tauri://localhost` и `capacitor://…` сегодня недопустимы как записи `ALLOWED_ORIGINS`.
3. **CORS.** Сервер не отдаёт `Access-Control-Allow-*` (клиент и API — один origin): браузерные запросы из приложения блокируются.
4. **Сокет.** `io.use(sessionMiddleware)` читает куку из рукопожатия; без куки сессия не определяется.
5. **COEP/COOP/CORP и CSP заголовками сервера** на локальные ресурсы приложения не действуют (страницу отдаёт приложение).

### 8.3 Варианты

| Вариант | Суть | Оценка |
|---|---|---|
| 1. Куки + `SameSite=None; Secure` для нативных origin | ослабляет CSRF-защиту веба; сторонние куки блокируются WKWebView и современными WebView | не рекомендуется |
| 2. Нативный HTTP-клиент (`tauri-plugin-http`, CapacitorHttp) с собственным cookie-хранилищем | запросы идут мимо WebView; куки живут в нативном слое; WebSocket остаётся проблемой | неоднозначно: две сетевые реализации, WebSocket вне нативного клиента |
| 3. **Сессия по заголовку** | при регистрации и `GET /api/auth` приложение получает токен сессии в теле ответа и хранит в защищённом хранилище; шлёт заголовок `X-Nyxo-Session`, сокету — `auth.token`. CSRF для таких запросов не нужен (заголовок не прикрепляется чужим сайтом автоматически), `Origin` — точный список | **выбран** |
| 4. Тонкая оболочка (C) | всё как в вебе | только как промежуточный шаг |

### 8.4 Серверные изменения для варианта 3 (подготовка, раздел 19)

- `NATIVE_ORIGINS` (список точных origin, включая `tauri://…` и `capacitor://…`): `parseOrigin` расширяется, чтобы принимать неweb-схемы **только** для записей этого списка; сравнение строгое, целиком.
- CORS для маршрутов `/api/*` и сокета: только для `NATIVE_ORIGINS`, `Access-Control-Allow-Headers: Content-Type, X-Nyxo-Session`, без `Allow-Credentials`.
- Токен сессии = подписанное значение `connect.sid` (то, что сегодня лежит в куке): middleware до `sessionMiddleware` подставляет его в кук-заголовок запроса, если пришёл заголовок `X-Nyxo-Session` с допустимым `Origin`; для сокета — из `handshake.auth.token`. Токен выдаётся **только** по запросу с заголовком `X-Nyxo-Client: native` и допустимым origin и **в куку не ставится**.
- CSRF: запросы с валидным заголовком сессии и допустимым origin проверку `X-CSRF-Token` не требуют; веб-запросы с кукой — по-прежнему.
- Срок жизни токена = срок жизни сессии (R2); выход и «Удалить и выйти» удаляют сессию на сервере как сейчас.
- Токен — такой же секрет, как кука `connect.sid`: хранится в защищённом хранилище (раздел 9), в логи и URL не попадает.

### 8.5 CSP приложения

Страницу отдаёт приложение, поэтому политика задаётся в приложении: в Tauri — `app.security.csp`, в Capacitor — `<meta http-equiv="Content-Security-Policy">` в `native.html` (на Android можно усилить заголовками через перехват запросов). Содержимое — как у веба (`lib/security-utils.js`), без `'nonce-…'` (R10) и с явным адресом сервера:

```
default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data: blob:; font-src 'self';
media-src 'self' blob:; worker-src 'self'; object-src 'none'; base-uri 'self'; form-action 'none';
connect-src 'self' https://nyxo.example wss://nyxo.example ipc: http://ipc.localhost
```

- `ipc:` и `http://ipc.localhost` нужны Tauri v2 для связи с ядром (по документации Tauri; проверить).
- Для MLS-модуля ([mls-pq.md](mls-pq.md)) добавляется `'wasm-unsafe-eval'` в `script-src`.
- Адрес `.onion` добавляется в `connect-src` только если приложение настроено на onion и Tor (раздел 11).
- Tauri при сборке добавляет в CSP собственные хэши/nonce для встроенных скриптов; исключить это через `dangerousDisableAssetCspModification` нельзя без последствий — результат проверить в собранном приложении.
- `frame-ancestors` в приложении неприменима; встраивание чужих страниц в WebView запрещено (нет `iframe`).

### 8.6 Навигация и IPC

Любая навигация WebView за пределы `native.html` блокируется (`server.allowNavigation` пуст; в Tauri — пустые права для удалённых URL). Права IPC Tauri выдаются **только** окну `main` с локальной страницей: удалённых URL в `capabilities/*.json` нет. Известная проблема Tauri в определении «локальный» origin на Windows и Android (CVE-2026-42184, классификация удалённого адреса с поддоменом `tauri` как локального) требует свежей версии Tauri: версию закрепить и обновлять по уведомлениям безопасности.

## 9. Хранение ключей

### Шаг 1 (как в вебе)

IndexedDB WebView; неизвлекаемые `CryptoKey` для приватных ключей; seed ML-KEM байтами. Дополнительно:

- **Android**: `android:allowBackup="false"`, `android:fullBackupContent="false"`, правила `dataExtractionRules`; `FLAG_SECURE` на окне (запрет скриншотов и превью в списке задач); `usesCleartextTraffic="false"`.
- **iOS**: данные WKWebView исключаются из резервных копий; размытие окна в переключателе приложений.
- **Tauri**: каталог данных WebView — отдельный профиль приложения; окно создаётся без вкладок/адресной строки и без DevTools в релизной сборке.
- **«Удалить и выйти»** очищает IndexedDB, `localStorage`, кэш и данные WebView программно (Tauri — очистка данных просмотра окна; Capacitor — `clearData` через плагин или удаление хранилища), как `deleteLocalData` в вебе.

### Шаг 2 (системное хранилище)

Мастер-ключ обёртки AES-256 хранится в Android Keystore / iOS Keychain (на настольных — менеджер учётных данных ОС через плагин, поддерживаемость плагина проверить). Закрытые ключи в IndexedDB дополнительно шифруются этим ключом, разблокировка — по требованию (биометрия, PIN устройства). Ограничение: аппаратные хранилища не поддерживают Ed25519/X25519 на всех устройствах, поэтому обёртка защищает данные в покое, но не от кода внутри приложения. Токен сессии (раздел 8.4) тоже хранится в этом хранилище.

## 10. Диплинки и уведомления

### 10.1 Диплинки

`https://<сервер>/#join=<КОД>.<секрет>` открывается в приложении (Android App Links, iOS Universal Links, у Tauri — плагин deep-link). Фрагмент не уходит на сервер при открытии в браузере; при открытии приложением его читает система и передаёт приложению. Платформы по-разному сохраняют фрагмент в универсальных ссылках — **проверить** на устройстве. Запасной формат: `nyxo://join#КОД.секрет` (схема приложения). Секрет не логируется и не показывается в уведомлениях и истории ОС.

### 10.2 Уведомления без текста

- Нативные приложения получают push через FCM (Android) и APNs (iOS), настольные — через локальные уведомления при открытом сокете. Содержимое уведомления — фиксированный текст «Новое сообщение» без имени комнаты, отправителя и тела; идентификаторов в полезной нагрузке нет.
- Регистрация токена: `POST /api/push/register { platform, token }` (ограничение числа токенов на аккаунт), удаление при выходе, удалении аккаунта и истечении срока аккаунта. Токен хранится в `push_tokens` без времени (до суток), связь «токен — аккаунт» известна серверу и платформе push.
- Серверная отправка: при новом сообщении в комнате отправляется один пустой push на токены участников, у которых нет открытого сокета, без текста и без `roomId`; пакетирование в окно 30 секунд, чтобы по частоте уведомлений не было видно ритма беседы.
- Приложение при пробуждении открывает сокет и забирает данные; расшифровка происходит в приложении, уведомление остаётся общим. Показ имени и текста в уведомлении **не планируется**: для этого ключи пришлось бы держать вне WebView.
- Цена: Google и Apple видят, что устройство получает уведомления Nyxo и когда. Альтернативы: UnifiedPush (Android, свой распределитель), фоновая служба с постоянным сокетом (расход батареи). iOS без APNs надёжных вариантов нет.
- Временные аккаунты: тихий push не продлевает срок жизни аккаунта; продлевает только открытие приложения (запрос или сокет). Выбор срока «Пока открыта вкладка» на мобильных означает «пока приложение в переднем плане и до 30 минут после»; экран входа в приложении должен предлагать «1 день» по умолчанию (вопрос 7).

## 11. Tor

- **Настольные (Tauri)**: направить весь трафик WebView через SOCKS5 локального Tor. WebView2 принимает параметры командной строки (`app.windows[].additionalBrowserArgs`, `--proxy-server=socks5://127.0.0.1:9050`); у окна есть настройка прокси (`proxyUrl`, проверить по схеме), на macOS — прокси WKWebView. Утечка DNS и запросов вне прокси должна быть проверена тестом. Свой Tor-демон или Arti внутри приложения — отдельная фаза: поставка, подпись и обновление Tor ложатся на проект.
- **Android**: Orbot как прокси/VPN; для WebView — `ProxyController` из AndroidX WebKit (нужен плагин). Без плагина пользователь включает Orbot для приложения.
- **iOS**: Tor в стороннем приложении ограничен (ограничения Network Extension, App Store); в первой версии не поддерживается, приложение сообщает об этом. Рекомендация — Tor Browser на другой платформе или веб-клиент.
- **Адрес**: приложению нужен выбор сервера: clearnet (`https://`) или onion (`http://…onion` через Tor). Адрес onion берётся из `onionUrl` ответа `GET /api/auth` (R3) и закрепляется; в `connect-src` добавляется только при настройке.
- **Закрепление TLS**: сертификаты хостинга меняются, жёсткое закрепление риск поломки; полагаемся на системное доверие и HSTS-политику сервера. Вопрос 8.
- Правило: приложение с включённым Tor не должно делать запросов мимо прокси (обновления updater тоже идут через него либо выключаются; GitHub Releases при этом виден Tor-выходу).

## 15. Граничные случаи и атаки

| № | Ситуация | Исход |
|---|---|---|
| 1 | Сервер отдаёт новый клиент | приложение его не загружает: код внутри пакета; обновление только подписанное |
| 2 | Подложный `latest.json` | подпись minisign не пройдёт; обновление отклонено |
| 3 | Утекла закрытая часть ключа updater | подписанное вредоносное обновление; отзыв — новая ручная установка с новым ключом; ключ хранится только в CI-секрете окружения `release` |
| 4 | Токен сессии в хранилище украден | равносилен краже куки (R2): срок жизни сессии, выход и удаление аккаунта инвалидируют |
| 5 | Запрос к API с чужим `Origin` приложения | отклоняется: `NATIVE_ORIGINS` — точные строки; запрос без заголовка сессии не авторизован |
| 6 | Локальный процесс подделывает `http://tauri.localhost` | без токена сессии ничего не получает; токен недоступен процессу вне приложения |
| 7 | Диплинк с секретом ссылки попал в журнал ОС | предупреждение пользователю; секрет одноразового смысла не имеет (действует до поворота приглашения) |
| 8 | Уведомление раскрывает содержимое | не бывает: полезная нагрузка пуста; проверяется тестом на сервере |
| 9 | Резервная копия устройства с данными приложения | отключена; если включена пользователем — ключи в ней (шаг 2 снижает риск) |
| 10 | Приложение на мобильных закрыто на сутки при сроке «Пока открыта вкладка» | аккаунт удалён через 30 минут без сокета; предупреждение на экране входа (вопрос 7) |
| 11 | XSS в клиенте | ограничена CSP; у страницы нет прав IPC кроме разрешённых; ключами пользоваться может, как в вебе |
| 12 | Отказ магазина | риск публикации: политики магазинов к сообщениям пользователей (жалобы, блокировка) и анонимным аккаунтам; нужны юридические тексты и механизм жалоб; прямая установка (GitHub Releases, F-Droid) остаётся запасным путём |
| 13 | Версия Tauri с уязвимостью определения локального origin | обновление зависимости; версия Tauri закреплена и отслеживается Dependabot-подобным процессом |
| 14 | Старый клиент приложения и новый API | совместимость API на один релиз (раздел 17); сервер отвечает `client-outdated`, приложение предлагает обновить |
| 15 | Невозможность прокси Tor на iOS | приложение не соединяется через onion; пользователю объясняется; рекомендован Tor Browser |

## 16. Тесты и проверка

- **До кода**: проверка схем конфигураций Tauri и Capacitor (`tauri.conf.json`, `capacitor.config.json`) актуальной версией инструмента; сборка пустого приложения на каждой платформе.
- **Сервер** (после подготовки): режим сессии по заголовку — вход, выход, удаление аккаунта, CSRF-обход только при допустимом origin и заголовке; CORS только для `NATIVE_ORIGINS`; сокет с `auth.token`; запрос с чужим origin отклонён; `parseOrigin` принимает пользовательские схемы только в списке.
- **Клиент**: `apiBase` в `api()` и сокете; service worker не регистрируется в приложении; диплинки (разбор секрета без нормализации).
- **Пакет**: `scripts/build-native.js` отказывается собирать при несовпадении хэша любого файла `public/**` с манифестом; тест на повторяемость списка файлов.
- **Ручной чек-лист приложения**: вход, группа, E2EE-сообщение, файл, удаление аккаунта (данные WebView пусты), чужая навигация заблокирована, DevTools нет в релизе, скриншоты запрещены (Android), резервная копия отключена, уведомление без текста, обновление с версии на версию, откат на старую подпись отклонён, ссылка-приглашение открывается приложением.
- **Tor**: пакетный анализ — приложение не делает запросов вне SOCKS-прокси.

## 17. Выкат и совместимость

- Приложения публикуются после G6 (разбиение файлов) и после выхода релиза с манифестом (T3.3) и SW (T4.3). Раньше не имеет смысла: клиент ещё меняется.
- Версия приложения привязана к тегу релиза; сервер сохраняет совместимость API на один релиз для установленных приложений (старое приложение не обновляется мгновенно). Несовместимый запрос → 400 `client-outdated`; приложение показывает «Обновите приложение» со ссылкой на канал.
- Откат релиза — по R0 для сервера; для приложений: нельзя «откатить» подписанное обновление, можно выпустить исправляющее (обновление версии вперёд).
