# Смена MESSAGE_ENCRYPTION_KEY: перетегирование и перешифровка

Порядок действий оператора при смене `MESSAGE_ENCRYPTION_KEY` и скрипт `scripts/retag-messages.js`. Контракт — [sealed-sender.md](../security/sealed-sender.md), разделы 6, 7, 13 и 14.1.

Пока реальных пользователей нет, смену ключа проще заменить сбросом базы ([deploy-railway.md](deploy-railway.md)): все данные тестовые. Процедура ниже нужна, когда в базе есть сообщения, которые нельзя терять.

## Что зависит от ключа

Один `MESSAGE_ENCRYPTION_KEY` (32 байта после разбора base64) порождает три разных вывода, каждый со своей меткой домена:

| Что | Вывод | Что ломается без прежнего ключа |
|---|---|---|
| Тег автора `author_tag` строки комнаты | `K_tag = HKDF(ключ, "nyxo-author-tag-key-v1")`, затем HMAC от (комната, пользователь, неделя) | Правка, удаление, таймер и «прочитано» не находят свои сообщения; выход и удаление аккаунта не находят строки по тегам |
| Шифрование строки комнаты `enc:v3` | `K_enc3 = HKDF(ключ, "nyxo-msg-enc-v3")`, в AAD входит тег | Сервер не читает текст строки (клиенту уходит «Не удалось расшифровать») |
| Псевдоним квоты вложений `qkey` | `K_quota = HKDF(ключ, "nyxo-upload-quota-v1")`, HMAC от `user_id` | Окна квоты, начатые под прежним ключом, перестают находиться (пользователь получает свежее окно) |

Чат с ботом шифруется `enc:v2` сырым ключом и читается по `kid` из `MESSAGE_ENCRYPTION_KEY_PREVIOUS`, тегов у него нет. Скрипт его строки **не переписывает**: они исчезают вместе с аккаунтом или чатом, а пока лежат под прежним ключом, тот должен оставаться в `…_PREVIOUS` (проверка — шаг 6).

Потеря ключа — потеря серверной читаемости, права удалять сообщения по тегу и сведений о квоте. Резервную копию ключа делают до смены и хранят отдельно от дампов ([backups.md](backups.md)).

## Порядок

Лучше в тихое время: скрипт держит строки пачками по 500 в одной транзакции (только таблица `messages`), правка сообщения в этот момент безопасна (запись правки условна по тегу строки и при совпадении с перетегированием просит повторить), но нагрузка на базу есть.

1. **Подготовка.** Сохраните прежний ключ в менеджере паролей. Сгенерируйте новый:
   ```
   node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"
   ```
2. **Включите оба ключа и перезапустите сервис.** Новый — в `MESSAGE_ENCRYPTION_KEY`, прежний — первым в `MESSAGE_ENCRYPTION_KEY_PREVIOUS` (если там уже были более старые, оставьте и их через запятую). Новые строки и теги идут под новым ключом, старые читаются и удаляются как раньше: теги проверяются по всем ключам.
3. **Пробный прогон.** В окружении сервиса (на Railway — `railway run`, с теми же переменными, что у приложения):
   ```
   node scripts/retag-messages.js --dry-run
   ```
   Скрипт ничего не пишет и сообщает, сколько строк будет переписано и сколько починить нельзя. Тексты сообщений и id строк в отчёт не попадают (id — только с `--verbose`).
4. **Перетегирование.**
   ```
   node scripts/retag-messages.js
   ```
   Для каждой строки комнаты скрипт расшифровывает `enc:v3` старым ключом с её старым тегом, находит владельца тега перебором (участники комнаты и вышедшие из `user_left_rooms` × все недели с создания аккаунта × все ключи), считает новый тег по тому же `created_at`, шифрует под `K_enc3` нового ключа с AAD, содержащим **новый** тег, и записывает `author_tag` и `text` одним `UPDATE`. Строка, уже лежащая под новым ключом (и `kid`, и тег), пропускается: скрипт идемпотентен и возобновляем, после обрыва его просто запускают снова.
5. **Проверка.**
   ```
   node scripts/retag-messages.js --verify
   ```
   Должно быть «Проверка пройдена»: нет строк со старым `kid` и нет тегов, не входящих в теги владельцев комнаты под **новым** ключом. Код выхода 2 — проверка не пройдена.
6. **Проверьте чат с ботом.** Записей `enc:v2` под прежним ключом (`<kid>` — первые 8 hex SHA-256 от прежнего ключа, они же видны в начале записи) не должно остаться:
   ```sql
   SELECT count(*) FROM messages WHERE room_id IS NULL AND text LIKE 'enc:v2:<kid>:%';
   ```
   Пока счёт больше нуля, прежний ключ из списка не убирают (такие записи исчезают с аккаунтом по сроку его жизни, до недели без активности).
7. **Уберите прежний ключ** из `MESSAGE_ENCRYPTION_KEY_PREVIOUS` и перезапустите сервис. Только после шагов 5 и 6.

## Что скрипт не может починить

Эти строки он оставляет как есть и перечисляет в итоге (код выхода 2):

- **владелец тега не найден** — аккаунт удалён (строк у него быть не должно) либо утерян один из прежних ключей, либо запись повреждена;
- **не расшифровалось** — повреждённый шифротекст, перенос между комнатами или подмена тега в базе (тег входит в AAD);
- **не `enc:v3` или неизвестный `kid`** — запись без префикса `enc:v3` в комнате или ключ, которого нет ни в `MESSAGE_ENCRYPTION_KEY`, ни в `…_PREVIOUS`.

Перед шагом 7 решите по каждому виду: найти утерянный ключ и добавить его в `…_PREVIOUS`, либо удалить строки вручную, либо принять потерю (такие сообщения неудаляемы по тегу и остаются до удаления комнаты).

## Квота вложений

После смены ключа `qkey` пользователя меняется: старое окно не находится, пользователь получает свежее окно на 30 суток (кратковременное послабление квоты), а строки прежних `qkey` удаляет суточная задача `purgeUploadQuota` по сроку окна. Отдельного шага не нужно. Удаление аккаунта удаляет окна по `qkey` от текущего и всех `…_PREVIOUS` ключей.

## Откат

До шага 7 откат прост: верните прежний ключ в `MESSAGE_ENCRYPTION_KEY`, а новый добавьте в `…_PREVIOUS`; всё, что успело переписаться, читается новым ключом и по тегам нового ключа. Полный откат после шага 7 возможен только из бэкапа базы вместе с прежним ключом.
