# Защита `main` и настройки репозитория

Пошаговая настройка GitHub для репозитория `PortfolioBTS/masages`: защита ветки `main`, обязательные проверки, сканирование кода и секретов, права Actions и закрытый приём сообщений об уязвимостях. Это шаг 6 [чек-листа этапа 0](stage-0-checklist.md): делайте его после очистки истории git и первого push, когда CI хотя бы раз отработал на `main`.

Зачем. Код, который попадает в `main`, получает браузер каждого пользователя и сервер ([модель угроз](../threat-model.md), «Цепочка поставки»). Защита ветки не делает изменения безопасными сама по себе, но не даёт протолкнуть их мимо автоматических проверок, переписать историю или удалить ветку по ошибке.

## Порядок

1. Очистка истории git и первый force-push ([stage-0-checklist.md](stage-0-checklist.md), шаг 5). После включения защиты force-push в `main` будет запрещён.
2. Первый прогон CI на `main` (workflows `CI` и `CodeQL`). Имена проверок в настройках появляются только после него.
3. Настройки из этого документа.
4. Контрольная проверка (раздел в конце).

## 1. Ruleset для `main`

Settings, Rules, Rulesets, New ruleset, New branch ruleset. Rulesets и защита веток доступны в публичных репозиториях; в приватном репозитории на бесплатном плане их нет (нужен платный план). Если вы предпочитаете классический интерфейс, те же правила задаются через Settings, Branches, Branch protection rule: названия пунктов близки.

| Параметр | Значение |
|---|---|
| Ruleset name | `main` |
| Enforcement status | Active |
| Bypass list | пусто. На случай аварии можно добавить только владельца (роль Repository admin) с режимом «For pull requests only»: обход через PR, а не прямой push |
| Target branches | Include default branch |

Правила (Branch rules):

| Правило | Настройка | Зачем |
|---|---|---|
| Restrict deletions | включено | Нельзя удалить `main` |
| Block force pushes | включено | Нельзя переписать историю опубликованной ветки |
| Require a pull request before merging | включено; Required approvals: 0; Require conversation resolution before merging: включено | Любое изменение идёт через PR, и на нём бегут проверки. Одиночный мейнтейнер не может одобрить собственный PR, поэтому одобрения не требуются; обязательными делаются проверки. Когда появится второй мейнтейнер, поставьте 1 |
| Require status checks to pass | включено; Require branches to be up to date before merging: включено; проверки — по таблице ниже | Без зелёных проверок слияния нет, и устаревшая ветка пересобирается на свежем `main` |
| Require code scanning results | инструмент CodeQL; Security alerts: High or higher; Alerts: Errors | Находка CodeQL уровня High и выше блокирует слияние |

По желанию (усиливают защиту, но добавляют работу):

- Require linear history: в `main` нельзя сливать merge-коммитом, только squash или rebase.
- Require signed commits: каждый коммит подписан. Тогда подписывать нужно и все локальные коммиты, в том числе сделанные ИИ-агентами, иначе push отклонят. Включайте, только если настроена подпись.

### Обязательные проверки

Имена — часть контракта с `.github/workflows/`: переименование job молча снимет проверку с защиты (это охраняет `test/workflows.test.js`). Описание проверок — [docs/dev/ci.md](../dev/ci.md).

| Проверка | Файл | Когда делать обязательной |
|---|---|---|
| `unit (ubuntu-latest)` | ci.yml | сразу |
| `unit (windows-latest)` | ci.yml | сразу |
| `e2e` | ci.yml | когда в `main` есть `npm run test:e2e` и каталог `test/e2e/`; раньше job падает на «Missing script» |
| `audit` | ci.yml | сразу. Обязателен намеренно: новая уязвимость, опубликованная между созданием PR и слиянием, остановит и несвязанный PR, пока зависимость не обновлена или не внесено временное исключение |
| `workflows-lint` | ci.yml | сразу |
| `analyze (javascript-typescript)` | codeql.yml | сразу |
| `analyze (actions)` | codeql.yml | сразу |

Проверки появятся в поиске выбора после первого прогона. Если нужной нет в списке, проверьте на вкладке Actions, что workflow запускался на `main` или на PR.

## 2. Code security

Settings, Code security (в старых интерфейсах — Code security and analysis).

| Пункт | Значение | Комментарий |
|---|---|---|
| Dependency graph | включено | Нужен Dependabot |
| Dependabot alerts | включено | Оповещения об уязвимых зависимостях |
| Dependabot security updates | включено | Автоматические PR с исправлениями безопасности. Плановые обновления идут по `.github/dependabot.yml` (по понедельникам, с паузой на свежие версии) |
| Secret scanning | включено | Поиск ключей и токенов в репозитории |
| Push protection | включено | Не даёт отправить найденный секрет. Утёкший ранее `.env` уже убран из истории по шагу 5, но защита нужна от повторения |
| Private vulnerability reporting | включено | **Обязательно**: на него ссылаются [SECURITY.md](../../SECURITY.md) и `/.well-known/security.txt`. Проверка: на вкладке Security есть кнопка «Report a vulnerability» |
| Code scanning | CodeQL через workflow `codeql.yml` | «Default setup» CodeQL не включайте: он конфликтует с workflow и дублирует прогоны |

Dependabot читает PR от человека: перед слиянием смотрите заметки о выпуске ([docs/dev/ci.md](../dev/ci.md), «Закрепления»). Закрепление действий по SHA защищает от подмены тега, но не от вредоносного коммита в настоящем релизе.

## 3. Actions

Settings, Actions, General.

| Пункт | Значение |
|---|---|
| Actions permissions | Allow <владелец>, and select non-owner, actions and reusable workflows: отметить «Allow actions created by GitHub». Сейчас используются только `actions/*` и `github/codeql-action`, оба GitHub-owned. Новые сторонние действия добавляйте в список осознанно, закрепляя полным SHA |
| Workflow permissions | Read repository contents and packages permissions. Workflow'ы сами запрашивают больше только там, где нужно (CodeQL: `security-events: write`) |
| Allow GitHub Actions to create and approve pull requests | выключено |
| Fork pull request workflows | Require approval for first-time contributors (или для всех внешних участников) |

В CI нет секретов, поэтому запуск на PR из форков безопасен; это держится на том, что в `ci.yml` не появится шаг с секретом. Не добавляйте `pull_request_target` и секреты в workflow, который запускается на чужих PR.

## 4. Аккаунт и доступ

- Двухфакторная защита включена на аккаунте владельца GitHub (приложение-аутентификатор или ключ безопасности). Захват аккаунта равен подмене кода.
- Список коллабораторов (Settings, Collaborators) проверен, лишних нет. Права Write и выше есть только у тех, кому доверяете код.
- Токены и ключи SSH, выданные ИИ-агентам или сторонним сервисам, ограничены нужным репозиторием; ненужные отозваны.

## 5. Теги релизов (когда появится release.yml, волна 3)

Манифест релиза строится на теге (`v*`), и по тегу выкладывается сверяемая версия клиента. Чтобы тег нельзя было подвинуть или удалить после выпуска: Rules, New tag ruleset; target — теги `v*`; включить Restrict updates, Restrict deletions; Require signed commits по желанию. Название workflow и теги уточнит задача T3.3; до неё этот пункт пропустите.

## Контрольная проверка

1. Прямой push в `main` отклоняется: `git push origin main` из чистого клона возвращает отказ из-за правил ветки.
2. Тестовый PR: создайте ветку с пустым изменением и откройте PR. Видны все семь обязательных проверок; кнопка слияния неактивна, пока они не позеленели.
3. По желанию: красная проверка блокирует слияние. Для этого сломайте тест в ветке PR и не сливайте её.
4. На вкладке Security: Dependabot alerts, Code scanning, Secret scanning включены, «Report a vulnerability» доступна.
5. `https://<домен>/.well-known/security.txt` указывает на ту же страницу приёма отчётов ([deploy-railway.md](deploy-railway.md)).

## Повседневная работа

- Изменения идут через PR. Слияние — после зелёных проверок и вычитки diff. Для документов и мелких правок это те же проверки: они дешёвые.
- Красный `audit` без изменений в коде — сигнал обновить зависимости (`npm audit fix`, затем `npm test`) или внести временное исключение в `audit-allowlist.json` со сроком (правила — [docs/dev/ci.md](../dev/ci.md)). Не отключайте проверку.
- Если расписание CI замолчало (GitHub отключает его в публичном репозитории после 60 дней без активности), сделайте коммит или запустите workflow вручную на вкладке Actions.
- Аварийная правка (откат): PR с откатом, обход защиты только владельцем через bypass «For pull requests only». Прямой push в `main` не используйте даже в аварии: проверки нужны именно тогда.
- Переименование job в workflow сопровождайте правкой списка обязательных проверок в ruleset, иначе слияния заблокирует «ожидающая» проверка, которой больше нет.
