# Cloudflare: убрать или оставить только DNS

Решение по пункту 4.6 плана: перед Nyxo не должно стоять прокси Cloudflare. Допустимы два варианта: Cloudflare вообще не используется или используется только как DNS (серое облако, «DNS only»). Домен, который ведёт на Railway напрямую, — целевое состояние.

Если у вас нет своего домена и сервис открыт по адресу `*.up.railway.app`, Cloudflare в схеме не участвует, и делать здесь ничего не нужно. Следующие разделы — на случай, когда домен уже подключён через Cloudflare.

## Почему не прокси

В режиме прокси («оранжевое облако») Cloudflare стоит между браузером и Railway. Он завершает TLS и видит каждый запрос и ответ целиком ([модель угроз](../threat-model.md), раздел 2, «Cloudflare»):

- IP-адрес клиента, заголовки, cookie, пути и тела запросов. Содержимое E2EE-сообщений для него шифртекст, но метаданные (кто, когда, в какую комнату) он видит;
- ответы сервера, включая JavaScript клиента: он может изменить любой файл, и пользователь этого не заметит. Сверка кода ([threat-model.md](../threat-model.md), 6.1) ловит подмену, но не предотвращает её;
- по умолчанию Cloudflare предлагает вставку собственных скриптов (Rocket Loader, аналитика), кэширует содержимое и может показывать промежуточные страницы (проверка браузера), которые ломают WebSocket и приложение;
- это ещё один хост с полным доступом к метаданным, ещё одни логи ([logs-retention.md](logs-retention.md)) и ещё одна цель для юридического принуждения.

Преимущества прокси (скрытие IP сервера, защита от объёмного DoS, кэш) для Nyxo малоценны: местоположение сервера на Railway и так известно, объёмный DoS вне области, динамический трафик не кэшируется. Onion-адрес Cloudflare вообще обходит.

## Целевое состояние

Вариант А (рекомендуется): DNS only.

- Записи домена в Cloudflare указывают на Railway (CNAME на адрес, который показывает Railway при добавлении домена) с серым облаком, режим «DNS only».
- Cloudflare видит только DNS-запросы к вашему домену, не трафик пользователей.
- Включена двухфакторная защита на аккаунте Cloudflare: захват DNS равен подмене сервиса. Токены API, если они есть, ограничены нужной зоной и правами.
- По желанию включите DNSSEC (в Cloudflare и у регистратора) и CAA-записи, разрешающие только того издателя сертификатов, которого использует Railway (смотрите их документацию).

Вариант Б: убрать Cloudflare совсем и держать DNS у регистратора или другого DNS-провайдера. Всё, что сказано про DNS only, остаётся верным.

Вариант В (нежелательно): оставить прокси. Делайте это только осознанно и со всеми ограничениями ниже. Он нарушает допущение «хост не видит больше, чем нужно» из модели угроз, и в политике конфиденциальности Cloudflare нужно указать обработчиком данных ([docs/legal/privacy-policy.ru.md](../legal/privacy-policy.ru.md)).

## Как перевести на DNS only

1. Cloudflare, ваш домен, DNS, Records.
2. Для каждой записи, которая ведёт на Railway (A, AAAA, CNAME), нажмите на оранжевое облако: статус должен смениться на «DNS only» (серое).
3. Подождите, пока истечёт TTL, и проверьте (раздел «Проверка»).
4. Проверьте, что сертификат на домене действителен: TLS на домене выпускает Railway, и это работает, когда запись указывает на Railway напрямую. Если сертификат не выпустился, смотрите состояние домена в Railway (Settings, Networking).
5. Отключите в Cloudflare функции, которые больше не нужны для зоны (правила, Workers-маршруты, Page Rules, Web Analytics).

Если нужно оставить прокси хотя бы временно, снизьте вред: выключите Rocket Loader, Auto Minify, Email Address Obfuscation, Web Analytics (beacon), Scrape Shield и Always Online; поставьте режим SSL/TLS «Full (strict)» и минимальную версию TLS не ниже 1.2; отключите кэширование для динамических путей (`/api/*`, `/socket.io/*`, `/uploads/*`) и правила, которые подменяют содержимое. WebSocket должен быть разрешён. Это лишь уменьшает вред, но не отменяет то, что Cloudflare видит всё.

## Что делает приложение

- Проверка IP Cloudflare остаётся в коде: заголовок `CF-Connecting-IP` принимается только когда соединение пришло с адреса из диапазонов Cloudflare. В режиме DNS only он вообще не приходит, проверка ничего не делает и безвредна (roadmap, R11). Переменная `CF_IP_RANGES` нужна только, если Cloudflare сменит свои диапазоны и вы всё ещё используете прокси; при DNS only задавать её не нужно.
- Реальный IP клиента приложение берёт из последнего звена `X-Forwarded-For`, которое ставит край Railway (`trust proxy = 1`). Без Cloudflare лимиты по IP работают по настоящему адресу клиента.
- HSTS и политика `Secure` для cookie не зависят от Cloudflare. HSTS preload (`HSTS_PRELOAD=yes`) включайте только на своём домене, после проверки на hstspreload.org, когда https работает на всех поддоменах и редирект http на https есть у хостинга ([deploy-railway.md](deploy-railway.md)). Если поддомены остаются за Cloudflare с прокси, это отдельный риск: `includeSubDomains` затронет и их.
- Onion-адрес ([tor-service/README.md](../../tor-service/README.md)) не зависит от Cloudflare.

## Проверка

После переключения:

- [ ] `nslookup <домен>` (или `dig +short <домен>`) возвращает адреса Railway, а не адреса из диапазонов Cloudflare (например, `104.16.0.0/13`, `172.64.0.0/13`, `2606:4700::/32`).
- [ ] `curl -sI https://<домен>/` не содержит заголовков `cf-ray`, `cf-cache-status` и значения `server: cloudflare`.
- [ ] Сайт открывается, WebSocket соединяется (в консоли браузера нет ошибок), смоук пройден ([deploy-railway.md](deploy-railway.md)).
- [ ] В Cloudflare у зоны нет включённых прокси-записей, Workers и Web Analytics.
- [ ] Политика конфиденциальности не называет Cloudflare обработчиком трафика (остаётся только DNS, если он используется).

## Чего не делать

- Не включать Cloudflare Tunnel, Access, Zaraz, Workers и Pages для Nyxo: все они ставят Cloudflare в путь трафика или подмешивают скрипты.
- Не включать Bot Fight Mode и проверку браузера для API: они ломают клиент, а защиту от массовых регистраций даёт proof-of-work.
- Не включать логирование трафика на стороне Cloudflare (Logpush, Instant Logs).
