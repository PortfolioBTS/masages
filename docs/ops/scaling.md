# Масштабирование: одна реплика и что мешает нескольким

Nyxo рассчитан на один экземпляр приложения. Этот документ объясняет почему, что уже подготовлено к нескольким экземплярам, какие блокеры остались и что делать при росте нагрузки. Нагрузочных испытаний не проводилось, поэтому цифр пропускной способности здесь нет: не доверяйте любым числам, которых нет в замерах `/metrics`.

## Текущая схема

- Один экземпляр приложения (Railway, Replicas: 1) с volume для вложений.
- Один сервис PostgreSQL без реплик и отказоустойчивости.
- Один `tor-service` с volume для ключа onion-адреса (два tor с одним ключом конфликтуют).
- Падение процесса или деплой — короткий простой: Railway перезапускает процесс, клиенты переподключают сокеты сами. Для volume простой при деплое неизбежен ([deploy-railway.md](deploy-railway.md)).

## Почему не несколько реплик

Сервис с подключённым volume на Railway нельзя запустить в нескольких репликах: volume монтируется к одной копии. Даже без volume приложение к репликам не готово (таблица ниже). Поэтому точные лимиты вынесены в Postgres не ради масштабирования, а чтобы они переживали перезапуски и деплои (roadmap, R11).

## Что уже общее между экземплярами

| Что | Где живёт | Комментарий |
|---|---|---|
| Сессии | таблица `session` в Postgres | Подходит любому экземпляру |
| CSRF-токен | не хранится: подпись HMAC на ключе из `SESSION_SECRET`, привязка к сессии | Нужен одинаковый `SESSION_SECRET` у всех экземпляров |
| Точные лимиты: регистрация, вход по коду, выдача ключей, повторное предъявление PoW | `rl_counters`, `rl_buckets`, `pow_used` (UNLOGGED) | Ключи — HMAC; общий для экземпляров при одинаковом `SESSION_SECRET` |
| Миграции | advisory-блокировка в Postgres | Два одновременно стартующих экземпляра не мешают друг другу |
| Фоновые задачи с общим результатом (чистка аккаунтов и заявок, уборка лимитов) | advisory-блокировка: выполняется одним экземпляром | Задачи, помеченные `exclusive: false`, выполняет каждый экземпляр для своих данных |
| Данные: сообщения, комнаты, ключи | Postgres | Единственный источник истины |

## Блокеры реплик

| Блокер | В чём проблема | Что нужно сделать |
|---|---|---|
| Вложения на локальном диске (volume) | Файлы лежат в одной файловой системе: другой экземпляр их не увидит, а Railway не даёт реплики с volume | Вынести вложения в объектное хранилище, совместимое с S3: загрузка, отдача по ссылке, уборщик осиротевших файлов, обработка во временной папке. Изменения кода загрузки и отдачи |
| socket.io без адаптера | События реального времени (новое сообщение, прочтение, заявки, удаление) уходят только сокетам того процесса, который их породил. Пользователь на другом экземпляре их не получит | Подключить адаптер socket.io, общий для экземпляров (например, на LISTEN/NOTIFY Postgres: Redis в стеке нет). Добавить тест с двумя экземплярами |
| Привязка клиента к экземпляру для socket.io | Транспорт long-polling работает только если запросы одного клиента попадают на один экземпляр | Разрешить только websocket-транспорт или обеспечить привязку (sticky sessions); проверьте, что делает ваша платформа |
| Общий лимит `/api` в памяти (`apiLimiter`) | Счётчики на каждый экземпляр: суммарный лимит растёт в N раз | Принять как есть (лимит грубый) или перенести в `rl_counters` |
| Счётчики сокетов в памяти (на аккаунт — 10, на IP — 20) | Лимит действует на экземпляр, а не на сервис | То же: принять или считать в общем хранилище |
| Таймеры исчезающих сообщений (`scheduledDeletions`) и периодическая чистка | Таймеры процесса; чистка идёт в каждом экземпляре. Удаление идемпотентно, но событие об удалении получают только сокеты экземпляра, который удалил | Решается адаптером socket.io; либо чистку сделать задачей под блокировкой |
| Метрики `/metrics` | Счётчики одного процесса | Собирать метрики с каждого экземпляра отдельно и суммировать в мониторинге |
| Пул соединений Postgres | У каждого экземпляра свой пул (`PG_POOL_MAX`, по умолчанию 10, плюс отдельные соединения под блокировки задач) | Следить, чтобы суммарное число соединений не превышало `max_connections` базы |
| `tor-service` | Один tor на один ключ; приватный адрес приложения указывает на экземпляр, который назначит DNS платформы | Оставить одну копию `tor-service`; при репликах приложения проверить маршрутизацию на `ONION_PORT` каждого |

Состояние после падения самой базы: UNLOGGED-таблицы лимитов пустеют, лимиты начинаются заново; решение proof-of-work, выданное не больше 5 минут назад, можно предъявить повторно. Это следствие осознанного выбора таблиц без журнала ([модель угроз](../threat-model.md), 6.8).

## Что делать при росте нагрузки сейчас

Сначала измерьте: `GET /metrics` (формат Prometheus, по токену `METRICS_TOKEN`) и графики Railway.

| Признак | Причина | Действие |
|---|---|---|
| `nyxo_eventloop_lag_seconds` растёт, CPU упирается | Один процесс Node обрабатывает всё на одном потоке; тяжёлая работа — очистка метаданных вложений | Увеличить ресурсы сервиса приложения (вертикально) в Railway |
| `nyxo_pg_pool_connections` держится на максимуме, запросы ждут | Мал пул соединений | Поднять `PG_POOL_MAX`, не выходя за `max_connections` базы |
| `nyxo_limits_store_errors_total` растёт, ответы 503 `busy` | База недоступна или перегружена | Проверить Postgres: ресурсы, соединения, диск |
| Папка вложений заполнена | Мал volume | Увеличить volume; снизить `UPLOAD_QUOTA_MB`; сократить срок жизни сообщений (`DEFAULT_MESSAGE_EXPIRY_SECONDS`) |
| Память процесса растёт без плато | Утечка или слишком много одновременных сокетов | Посмотреть `nyxo_sockets_connected` и `nyxo_process_memory_bytes`; перезапуск как временная мера; заведите issue |
| Постоянная недоступность базы | Один экземпляр Postgres без отказоустойчивости | Увеличить ресурсы, проверить резервные копии ([backups.md](backups.md)); при необходимости перейти на управляемый Postgres с репликой |

## Порядок перехода на несколько реплик (если понадобится)

Решение за владельцем. Нужны все шаги, иначе пользователи получат «потерянные» события и рассинхронизацию:

1. Вынести вложения в объектное хранилище, убрать volume у сервиса приложения.
2. Подключить адаптер socket.io между экземплярами, зафиксировать транспорт websocket.
3. Решить судьбу общего лимита `/api` и счётчиков сокетов: принять или вынести в общее хранилище.
4. Одинаковые `SESSION_SECRET`, `MESSAGE_ENCRYPTION_KEY` и остальные секреты у всех экземпляров.
5. Добавить сквозной тест с двумя экземплярами (`suite.startServer` в харнессе сквозных тестов запускает ещё одну реплику на ту же базу, см. `docs/dev/testing.md`): сообщение, отправленное через один экземпляр, доходит до сокета другого; удаление по таймеру доходит до всех.
6. Включить вторую реплику, наблюдать метрики, затем увеличивать число.

До этого — одна реплика, и это документированное ограничение, а не недосмотр ([модель угроз](../threat-model.md), раздел 8).
