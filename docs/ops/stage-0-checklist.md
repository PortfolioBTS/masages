# Чек-лист этапа 0: что делает владелец

Эти шаги выполняет владелец проекта вручную, в Railway и GitHub. Порядок важен.

Реальных пользователей нет, все данные в базе тестовые (решение владельца от 2026-10-02). Поэтому новая версия при первом запуске на старой схеме один раз полностью очищает базу и создаёт новую схему ([deploy-railway.md](deploy-railway.md), раздел «Первый запуск»). Бэкап перед этапом 1 и перенос старых аккаунтов не нужны. Если в базе всё-таки окажется что-то ценное, снимите дамп по [backups.md](backups.md) до деплоя.

Пункты 0.1–0.6 — из исходного плана, 4.6 — про Cloudflare.

## Порядок

1. Подготовка и защита аккаунтов.
2. Секреты и база (0.1): сразу.
3. Переменные и сервисы Railway (0.2).
4. Финальное слияние кода — делает интегратор, не вы.
5. Очистка истории git от `.env` и первый push (0.6).
6. Защита `main` (0.4) — после первого прогона CI.
7. Cloudflare (4.6) и юрист (0.5) — параллельно с остальным.

Пункты 2.1, 2.2 и 3 можно делать уже сейчас: они не зависят от кода, а пароль базы утёк и её публичный адрес открыт. Новые `SESSION_SECRET` и `MESSAGE_ENCRYPTION_KEY` (пункт 2.3) задавайте прямо перед деплоем новой версии. Если у сервиса включён автодеплой из GitHub, force-push на шаге 5 сразу запустит деплой новой версии, поэтому переменные и volume к этому моменту должны быть готовы.

## 1. Подготовка

- [ ] Включена двухфакторная защита на GitHub и на Railway (приложение-аутентификатор или ключ безопасности). Захват любого из этих аккаунтов равен подмене кода и доступу ко всем секретам.
- [ ] Проверен список участников проекта Railway и коллабораторов репозитория: лишних нет.
- [ ] В базе действительно только тестовые данные. Если сомневаетесь, посмотрите состав в панели Railway (вкладка Data сервиса Postgres) и при необходимости снимите дамп.
- [ ] Менеджер паролей готов: туда кладутся новые секреты. В репозиторий и чаты секреты не попадают (`.env` в `.gitignore`).

## 2. Секреты и база (пункт 0.1)

В публичную историю git попал `.env` (коммит `d5cd834` от 15.07.2026): оттуда известны `SESSION_SECRET`, пароль Postgres и `INTERNAL_KEY_SERVER_SECRET`. Очистка истории (шаг 5) утечку не отменяет: копии могут быть у других людей и в кэшах. Поэтому секреты меняются в любом случае.

### 2.1. Приватный адрес базы и выключение TCP Proxy

Делайте в этом порядке, иначе приложение потеряет базу.

1. Откройте переменные приложения в Railway. Хост в `DATABASE_URL` должен оканчиваться на `.railway.internal`. Лучше всего переменная — ссылка: `${{Postgres.DATABASE_URL}}` (имя сервиса — как в вашем проекте). Если там публичный адрес (`…proxy.rlwy.net` и подобный), замените его на ссылку.
2. После деплоя убедитесь, что приложение работает.
3. В сервисе Postgres: Settings, Networking, удалите публичный TCP Proxy. После этого базу из интернета не достать.

### 2.2. Новый пароль Postgres

Так как данные тестовые, проще всего второй вариант.

- **Вариант А (рекомендуется): создать сервис Postgres заново.** Удалите старый сервис Postgres и создайте новый из шаблона Railway. Новый сервис получает новый пароль. Привяжите к нему `DATABASE_URL` приложения ссылкой. Данные при этом пропадают — это допустимо по решению владельца.
- **Вариант Б: сменить пароль в существующей базе.** Выполните внутри базы `ALTER USER <пользователь> PASSWORD '<новый>'`, затем обновите в сервисе Postgres переменные с паролем и строки подключения, а в приложении — `DATABASE_URL`. Одной правки переменной `POSTGRES_PASSWORD` недостаточно: образ Postgres читает её только при первом создании базы.

Новый пароль генерируйте случайным: `node -e "console.log(require('crypto').randomBytes(24).toString('base64url'))"`.

Проверка: `railway run npm run check-env` не печатает строк про совпадение с утёкшим значением, а сервер при старте пишет «Проверка настроек: всё в порядке».

### 2.3. Новые `SESSION_SECRET` и `MESSAGE_ENCRYPTION_KEY`

```
node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"   # SESSION_SECRET
node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"      # MESSAGE_ENCRYPTION_KEY
```

- `SESSION_SECRET`: после смены все сессии закончатся, а у временных аккаунтов нет пароля, так что войти заново нельзя. Здесь это безопасно: данные тестовые и при первом запуске новой версии сбросятся. Лучше менять вместе с деплоем новой версии: одно прерывание вместо двух. Смена также обнуляет лимиты, CSRF-токены и proof-of-work.
- `MESSAGE_ENCRYPTION_KEY`: env-check знает утёкшие значения только для `SESSION_SECRET`, пароля Postgres и `INTERNAL_KEY_SERVER_SECRET`, про этот ключ он ничего не скажет. Если он мог лежать в том же `.env`, считайте его скомпрометированным и замените. Старые сообщения после сброса не нужны, поэтому старый ключ не кладите в `MESSAGE_ENCRYPTION_KEY_PREVIOUS`: он только оставил бы утёкшее значение в окружении. Меняйте вместе с деплоем новой версии: пока работает старая версия, сообщения под новым ключом не откроются.
- Значения храните в менеджере паролей. Каждый секрет должен быть своим (env-check ругается на одинаковые).

Позже, с соответствующими волнами плана, понадобятся ещё `METRICS_TOKEN` (случайная строка) и `KT_SIGNING_KEY` (ключ подписи журнала ключей; его копию нужно хранить так же бережно, как секрет сессий). Подробности — в [deploy-railway.md](deploy-railway.md).

## 3. Переменные и сервисы Railway (пункт 0.2)

- [ ] `NODE_ENV=production` в сервисе приложения. Без этого cookie без `Secure`, нет HSTS, и env-check пишет ошибку.
- [ ] Удалены переменные удалённых функций: `INTERNAL_KEY_SERVER_SECRET`, `KEY_SERVER_URL`, `E2EE_KEY_STORE`, `ANON_SERVICE_URL`, `ANON_SERVICE_SECRET`. Сервер сам предупредит, если что-то осталось. После слияния этапа 1 удалите также `PASSWORD_PEPPER` и `HIBP_CHECK` (паролей больше нет).
- [ ] Удалены сами сервисы `e2ee-key-server` и `anon-service` в проекте Railway, если они там есть: код этих сервисов удалён из репозитория, ключи хранятся во встроенном хранилище.
- [ ] К сервису приложения подключён volume для вложений; `UPLOADS_DIR` указывает на него или есть `RAILWAY_VOLUME_MOUNT_PATH`. Без volume вложения пропадают при каждом деплое.
- [ ] Остальные переменные заданы по таблице из [deploy-railway.md](deploy-railway.md).

Проверка: в логе деплоя строка «Проверка настроек: всё в порядке».

## 4. Финальное слияние

Все волны плана сливает интегратор в локальную ветку `main` ([docs/dev/roadmap.md](../dev/roadmap.md)). До этого момента на GitHub ничего не отправляется. К шагу 5 нужны: `npm test` зелёный, сквозные тесты зелёные, рабочее дерево чистое.

## 5. Очистка истории git от `.env` и первый push (пункт 0.6)

Делается после финального слияния и до первого push. Причина: `git filter-repo` переписывает хэши коммитов, поэтому все локальные коммиты нужно переписать вместе, а на GitHub отправить уже чистую историю. Делайте это до включения защиты `main`, иначе force-push будет запрещён.

### 5.0. Предусловия

- [ ] Секреты из шага 2 уже заменены.
- [ ] Все ветки слиты в локальную `main`, `npm test` зелёный.
- [ ] Остались только нужные ветки и теги (`git branch`, `git tag`): временные ветки `wt/*` удалены, иначе `--all` на шаге 8 отправит и их.
- [ ] Защита `main` на GitHub ещё не включена.
- [ ] Понятно, что открытые PR и ссылки на старые коммиты после этого перестанут работать.

### 5.1. Порядок действий

Команды — для Git Bash.

1. **Копия на случай ошибки.** Скопируйте папку репозитория целиком вне его и создайте комплект: `git bundle create ..\nyxo-before-filter.bundle --all`. Копия содержит утечку: храните её только локально и удалите, когда убедитесь, что всё в порядке.
2. **Установите git-filter-repo:** `pip install git-filter-repo` (нужен Python 3). Проверка: `git filter-repo --version`.
3. **Сделайте свежий клон-зеркало локального репозитория:** `git clone --mirror --no-local <путь к репозиторию> nyxo-clean.git`, затем `cd nyxo-clean.git`. Если filter-repo пишет «not a fresh clone», повторите клонирование заново, а не добавляйте `--force`.
4. **Найдите, что вырезать.** `git log --all --full-history --oneline -- .env` покажет коммиты с `.env`. Ключ `--full-history` обязателен: без него git скрывает ветку истории, где файл потом пропал при слиянии, и в нашем репозитории команда печатает пустой результат при том, что файл в истории есть. Проверьте и другие файлы с секретами: `git log --all --name-only --format= | sort -u | grep -Ei "\.env|\.pem|\.key|secret"`.
5. **Вырежьте:** `git filter-repo --invert-paths --path .env` (добавьте `--path <файл>` для каждого лишнего файла из шага 4).
6. **Проверьте:**
   - `git log --all --full-history --oneline -- .env` ничего не печатает;
   - дерево последнего коммита не изменилось: `git rev-parse main^{tree}` в зеркале и в исходном репозитории даёт один и тот же хэш (`.env` в последнем коммите нет, он в `.gitignore`);
   - при желании поищите старые значения секретов во всей истории: `git log --all --oneline -S"<старое значение>"` не должен находить ничего.
7. **Подключите GitHub.** filter-repo удаляет адрес `origin`: `git remote add origin https://github.com/PortfolioBTS/masages.git`.
8. **Отправьте.** Это и есть первый push:
   ```
   git push origin --force --all
   git push origin --force --tags
   ```
   Не используйте `--mirror`: GitHub не принимает перезапись своих служебных веток `refs/pull/*`.
9. **Уберите остатки на GitHub.** Старые коммиты остаются доступны через ветки, PR и кэш:
   - удалите на GitHub все ветки со старой историей (в том числе `dependabot/*`), закройте или удалите PR и issue, где есть утёкшие значения;
   - напишите в поддержку GitHub (support.github.com/contact) с просьбой очистить кэшированные представления и ссылки на PR для коммитов со старой историей: укажите репозиторий и хэш `d5cd834`;
   - проверьте, что `https://github.com/PortfolioBTS/masages/commit/d5cd834` отвечает 404 (после очистки кэша поддержкой).
10. **Пересоздайте клоны.** Рабочие копии на всех машинах и в worktree клонируйте заново из GitHub. Старые клоны содержат прежнюю историю: не делайте из них push.
11. **Уберите утёкшее.** Удалите зеркало, комплект `nyxo-before-filter.bundle` и копию из шага 1, когда проверите, что новая история рабочая.
12. **Поправьте текст в коде.** В `lib/env-check.js` сообщения ссылаются на коммит `d5cd834`; после перезаписи такого коммита не будет. Замените ссылку на описание («значение из `.env`, попавшего в публичную историю git») отдельным коммитом.
