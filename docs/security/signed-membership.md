## 1. Что решено

1. Сервер задаёт список участников комнаты и этого не меняет: он по-прежнему может **убрать** участника. Но клиент отправляет свой Sender Key только тем участникам, чей допуск подтверждён: подписью участника, которому клиент доверяет, подписью по ссылке с секретом, либо ручным решением пользователя. «Призрак», которого сервер добавил сам, ключа не получает.
2. Три вида сертификатов (подпись Ed25519 identity-ключом или ключом приглашения, метка домена `nyxo-member-cert-v1\0`): допуск (`vouch`), приглашение (`invite`), вход по приглашению (`join`). Формат — бинарный, фиксированный, раздел 6.
3. Вход без одобрения возможен **только** по ссылке `#join=<КОД>.<секрет>`. Секрет в фрагменте на сервер не уходит. Код без секрета (набран руками, утёк в логи) превращается в заявку на одобрение участником. Роли ключей: `секрет → seed → ключ приглашения`, его открытая часть лежит в сертификате приглашения.
4. Новичок получает первоначальное доверенное множество `V` из сертификата, а не от сервера: по сертификату допуска (якорь — ключ одобрившего) или по сертификату приглашения (якорь — ключ, выведенный из секрета ссылки; это внешняя точка опоры, MITM сервера при первом контакте для входа по ссылке закрыт).
5. Выход участника и удаление аккаунта не подписываются: управляет сервер. Он может только убрать участника (отказ в обслуживании), но не добавить читателя; при любом исчезновении участника ключ комнаты ротируется (уже есть).
6. «Хэш взгляда» на ключи участников в SKDM (`ext.view`) ловит расхождение: сервер показал разным участникам разные ключи одного человека.
7. Ручное «Доверять участнику» действует **только на этом устройстве** и сертификата не публикует (но снимок, который подписывающий кладёт в допуск или приглашение, включает все ключи его `V`, в том числе подтверждённые вручную). Автоматическое поручительство при уходе подписавшего (раздел 9.5) публикует новые сертификаты допуска.
8. Словарь статусов клиента объединяет два рабочих плана (раздел 4): `members[].status ∈ {self, confirmed, unconfirmed}`, `how ∈ {creator, approved, invite, vouched, manual}`.

## 2. Цели и не-цели

### Цели

- **Ц1.** Сервер не может заставить честный клиент отправить Sender Key новому, неподтверждённому участнику, не получив для этого подпись доверенного участника или секрет ссылки.
- **Ц2.** Новичок при входе по ссылке не доверяет серверу в вопросе «кто в группе»: ключи существующих участников сверяются со снимком, подписанным пригласившим.
- **Ц3.** Сертификат нельзя перенести в другую комнату, выдать за сертификат другого человека или предъявить повторно после выхода без ведома тех, кто видел выход (в пределах свежести).
- **Ц4.** Расхождение «участники видят разные ключи» (раздвоение сервера) замечается, если у жертвы есть хотя бы один честный путь к другому участнику.
- **Ц5.** Сервер хранит минимум: сертификаты только текущих участников и только пока они состоят в комнате; вечного журнала нет.
- **Ц6.** Старые клиенты не поддерживаются (R0); формат E2EE-конверта сообщений не меняется. Меняются SKDM (необязательное поле `ext`) и правила, кому клиент отправляет ключ.

### Не-цели

- **Н1.** Защита от злонамеренного **участника**: любой участник может одобрить кого угодно (поведение продукта сегодня), а участник с ключом комнаты может переслать его хоть кому.
- **Н2.** Подпись удаления и подтверждение того, что ушедший действительно ушёл. Сервер может не убирать ушедшего из списка; только при сговоре с ним ушедший продолжит получать ключи (раздел 12).
- **Н3.** Защита первого контакта при одобрении заявки: сервер может подставить «заявителя» с чужими ключами. Одобряющий видит ключи заявителя и код безопасности; решение человека (раздел 12, строка 1).
- **Н4.** Защита изолированной группы, которой целиком показан поддельный мир: новичок по одобрению принимает ключ одобрившего с сервера (TOFU).
- **Н5.** Анонимность допуска: сервер знает, кто кого одобрил (он обрабатывает запрос) и хранит пару в сертификатах, пока субъект в комнате.
- **Н6.** Роли и права (владелец, администратор). Все участники равны, как сейчас.
- **Н7.** Исключение участника другим участником. Такой функции нет.

## 3. Модель угроз

| Кто | Что видит или умеет | Что даёт этот дизайн | Что остаётся |
|---|---|---|---|
| Работающий злонамеренный сервер | список участников, заявки, identity-ключи (key-store), сертификаты, очередь key-share | не может заставить честный клиент отправить ключ «призраку»; не может подменить ключ участника, названный в снимке; не может подделать сертификат допуска или входа | может убрать участника, скрыть сертификаты (тогда участник «не подтверждён»), показать заявителя с чужими ключами (решает человек), раздвоить мир изолированной группе |
| Бывший участник в сговоре с сервером | знает ключ комнаты на момент ухода | клиенты, видевшие выход, ротируют ключ и отзывают сертификаты ушедшего | клиент, которому сервер скрыл выход, продолжит отправлять ключи (Н2) |
| Злонамеренный участник | может одобрять и приглашать | его допуск ограничен его же подписью: поручиться он может за кого угодно | вред ограничен тем, что любой участник и так может раскрыть ключ комнаты |
| Читатель дампа БД | сертификаты текущих участников: id комнаты, субъекта и подписавшего, минута допуска, снимок ключей | сертификаты не содержат приватных данных, секрета ссылки и текста; после выхода строки удаляются | граф «кто кого одобрил» для текущих участников; минута допуска |
| Утёкшая ссылка с секретом | любой, у кого она есть, может войти (так и задумано) | лечится поворотом приглашения; ограничение срока (до 30 дней), лимит участников | вошедший посторонний получит ключи от тех, кто примет его join-сертификат; участники видят «по приглашению {имя}» |
| Утечка только кода (без секрета) | сервер и логи знают код | войти напрямую нельзя: код без секрета даёт заявку | заявку должен одобрить человек |

### Что сервер может и не может подделать

| Может | Не может |
|---|---|
| добавить в `room_participants` любую учётную запись (призрака) | заставить честного участника отправить призраку Sender Key: нет сертификата, подписанного подтверждённым участником, и нет join-сертификата по ссылке |
| убрать участника из списка или из очереди key-share | добавить читателя; убрать участника незаметно для тех, кто смотрит на список (ключ ротируется) |
| скрыть сертификат от части клиентов | подделать сертификат: подпись проверяется закреплённым identity-ключом подписавшего (или ключом приглашения) |
| подставить клиенту другие identity-ключи участника X | протащить их мимо снимка (`memkey`, 16 байт SHA-256) и мимо закреплённых ключей: ключи субъекта сверяются с сертификатом, а ключи участников — со снимком |
| повторить сертификат вышедшего участника | заставить клиента принять его, если клиент видел выход (список `revokedCerts`) или сертификат старше 30 дней |
| показать заявителя с чужими ключами | подписать за одобряющего: одобрение — действие человека на устройстве |
| отдать новичку чужой сертификат допуска | выдать его за адресованный новичку: ключи субъекта в сертификате должны совпасть с ключами самого новичка |
| подменить поле `ext.view` в SKDM | изменить SKDM: он внутри AEAD попарного канала, привязанного к identity обеих сторон |

## 4. Решения и отличия от рабочих планов

| Что | Решение | Откуда расхождение |
|---|---|---|
| Идентификаторы в сертификате | `u32` (комнаты и пользователи — `INTEGER`) | план криптографии (раздел 8): `u64`; шире не нужно, согласуется с тегами [sealed-sender.md](sealed-sender.md) и метками прозрачности |
| Статусы участников | `status ∈ {self, confirmed, unconfirmed}`, `how ∈ {creator, approved, invite, vouched, manual}`, `by` | план клиента (5.4): `self/confirmed/unconfirmed` и `how`; план криптографии: `verified/legacy`, `unverifiedMembers`, `vouchForMember`. Побеждает словарь клиента; значение `legacy` не нужно (старых комнат нет, R0) |
| Метка «Создатель группы» у другого участника | не показывается; создатель виден только у себя («Вы создали группу») | сервер не хранит и не подписывает создателя; метка у чужого участника была бы неподтверждённым утверждением сервера |
| Ручное «Доверять участнику» | локальное решение, сертификат не публикуется | план криптографии (раздел 8): «вручную ... любой проверенный участник» мог публиковать vouch; публикация усиливала бы ошибку одного человека на всю группу |
| Хэш взгляда | считается по **списку сервера** с закреплёнными ключами (все участники), а не по доверенному множеству `V` | план криптографии: по `V`. При разном `V` у участников сверка отключалась бы чаще, чем нужно |
| Удалённые подписанты | сервер удаляет сертификаты ушедших подписантов; клиенты не принимают сертификат, чей подписант уже вышел из комнаты; оставшиеся участники автоматически поручаются заново (9.5) | план криптографии: «кто не успел проверить X, подтвердит вручную»; без автоматического поручительства группа ломалась бы после ухода одобрившего |
| Схема сервера | таблица и столбцы — прямо в DDL (R0). `CREATE TABLE IF NOT EXISTS`/`ADD COLUMN IF NOT EXISTS` плана не нужны | план криптографии; R0. Запасной путь — раздел 15 |
| Блокировка | `rooms FOR NO KEY UPDATE`, как в [message-ordering.md](message-ordering.md) §8 | — |
| Прокси ключей | сертификаты обслуживают `lib/e2ee-groups.js` и `lib/key-store.js` напрямую | план упоминал key-server; прокси удалён в T0.2 |
| Поле `ext` в SKDM | общий контейнер R9 из T3.1; здесь определён ключ `view` | roadmap R9 |
| Размер снимка | не более 1024 участников (сертификат не более 17 КБ) | план: `N ≤ 1024`; `MAX_INVITE_MAX_MEMBERS = 1000` в `lib/invites.js` |

Метки домена (реестр общий, раздел 1.1 плана криптографии; здесь только используемые):

| Метка | Где |
|---|---|
| `nyxo-member-cert-v1\0` (с нулевым байтом) | вход подписи сертификата (Ed25519) |
| `nyxo-memkey-v1` | `memkey` — короткий отпечаток пары ключей участника |
| `nyxo-view-ids-v1`, `nyxo-view-v1` | хэш взгляда на состав и на ключи |
| `nyxo-invite-seed-v1` | HKDF `info`: секрет ссылки → seed ключа приглашения |

Правило реестра: подпись identity-ключом всегда `метка\0 ‖ поля фиксированной длины`; проверяющий сверяет точную длину. Для хэшей метка без нулевого байта допустима: за ней идут только поля фиксированной длины либо один список в конце.

## 5. Протокол по шагам

### 5.1 Создание комнаты

Создатель: `V = {я}`, `how = creator`. Сертификатов нет. Комната создаётся как сейчас (`POST /api/chats`).

### 5.2 Вход по одобрению (заявка)

```
J (заявитель)             Сервер                       A (участник, V_A)
  — код без секрета ——>   заявка join_requests
                                          —— GET join-requests ——>  видит J и его identity-ключи
                                                                    сверяет код безопасности (по желанию)
                                                                    подписывает vouch(A→J, снимок V_A)
                          <—— POST approve {cert} ———————————————
                          addRoomMember (одной транзакцией со вставкой сертификата)
J <—— joinRequestDecided
J: ensureRoomSession: находит vouch с subject = я, проверяет (6.4), строит V_J
```

Условия: у заявителя есть identity-ключи в key-store (иначе одобрение блокируется с объяснением «пользователь ещё не настроил шифрование»); `approve` без сертификата отвергается (400 `cert-required`).

### 5.3 Вход по ссылке (приглашение)

Приглашающий (любой участник, `requireApproval = false`):

```
s = 16 случайных байт                                    (секрет, остаётся на устройстве и в ссылке)
seed = HKDF-SHA256(ikm = s, salt = 32 нулевых байта, info = "nyxo-invite-seed-v1", L = 32)
(ik_priv, invitePub) = Ed25519 из seed                   (раздел 6.5)
cert_invite = invite(room, issuedMin, nonce, actor = я, invitePub, expiresMin, снимок V_я),
              подписи: sig — моим identity-ключом, sig2 — ключом приглашения
POST /api/chats/:chatId/invite/rotate { …, inviteCert }  → rooms.invite_cert = cert_invite
ссылка: https://host/#join=<КОД>.<base64url(s)>
```

Входящий (у него ссылка):

```
parseInviteInput → { code, secret }                       (public/lib/invite.js; секрет НЕ нормализуется)
POST /api/chats/join/preview { code } → { roomId, roomName, inviteCert, … }
проверка: invitePub, выведенный из secret, равен invitePub в сертификате; roomId совпадает; срок не истёк;
          подпись приглашающего действительна по ключу в сертификате (ключ закрепится позже, 6.4)
cert_join = join(room, issuedMin, nonce, subject = я (id, ключи), ref = SHA-256(cert_invite)),
            подписи: sig — ключом приглашения, sig2 — моим identity-ключом
POST /api/chats/join { code, joinCert } → сервер проверяет (7.2), addRoomMember, сохраняет сертификат
V_J = {я} ∪ {участники из снимка приглашения, ключи которых на сервере совпали с memkey} ∪ {приглашающий}
секрет и ключ приглашения стираются из памяти и из адресной строки (consumeJoinFragment)
```

### 5.4 Код без секрета

Вход по коду без `joinCert` — всегда заявка (200 `{ success:true, pending:true, requestId }`), даже если в комнате `requireApproval = false`. Интерфейс объясняет разницу: «Ссылка с секретом впускает сразу; код без ссылки отправляет заявку».

### 5.5 Поручительство после ухода подписавшего

Участник C, у которого в `V` есть X с `how ∈ {approved, invite, vouched}`, `by = A`, видит, что A вышел из комнаты (`removedMembers`). Если на сервере для X нет действительного сертификата допуска от текущего участника и ни одного допуска, подписанного самим C, C отправляет `POST member-certs` с новым `vouch(C→X, снимок V_C)` (автоматически, без вопроса). Не больше 50 поручительств на событие ухода, не чаще одного на пару (C, X). Сервер хранит не более 4 сертификатов допуска на субъекта; лишние отвергает ответом 200 `{ success:true, stored:false }`. Поручительство передаёт уровень доверия, который C уже принял по цепочке сертификатов; если у C X подтверждён только вручную (`how = manual`), поручительство не публикуется.

### 5.6 Выход и удаление аккаунта

Подписей нет. Сервер: удаляет участника и все сертификаты, где он субъект или подписавший. Клиенты по `roomMembersChanged` видят, что участника нет в списке: удаляют его из `V`, заносят хэш его сертификата в `revokedCerts`, ротируют свой Sender Key до рассылки (поведение 5.2 уже есть).

## 6. Сертификаты

### 6.1 Макет (big-endian, без разделителей)

| Смещение | Размер | Поле | `vouch` (1) | `invite` (2) | `join` (3) |
|---|---|---|---|---|---|
| 0 | 8 | magic `"NYXOMC01"` | да | да | да |
| 8 | 1 | kind | 1 | 2 | 3 |
| 9 | 4 | `roomId` u32 | да | да | да |
| 13 | 4 | `issuedMin` u32, минуты от эпохи Unix | да | да | да |
| 17 | 16 | `nonce`, случайные | да | да | да |
| 33 | 4 | `subjectId` u32 | допускаемый | 0 | входящий |
| 37 | 32 | `subjectSignPub` | да | нули | да |
| 69 | 32 | `subjectDhPub` | да | нули | да |
| 101 | 4 | `actorId` u32 | одобряющий | приглашающий | 0 |
| 105 | 32 | `actorKey` | identity Ed25519 одобряющего | identity Ed25519 приглашающего | `invitePub` |
| 137 | 32 | `ref` | нули | `invitePub` | SHA-256 всего сертификата приглашения |
| 169 | 4 | `expiresMin` u32 | 0 | срок приглашения | 0 |
| 173 | 2 | `snapN` u16 | N | N | 0 |
| 175 | 16·N | `snap` — отсортированные по возрастанию, без повторов `memkey` | снимок `V` одобряющего, включая его самого | снимок `V` приглашающего, включая его самого | пусто |
| 175+16N | 64 | `sig` | да | да | да |
| 239+16N | 64 | `sig2` | нет | да | да |

Длина: `vouch` — `239 + 16N`; `invite`, `join` — `303 + 16N`. Предел `N ≤ 1024` (сертификат не больше 17 КБ). Любая другая длина — отказ.

Подписи:

```
msg  = "nyxo-member-cert-v1\0" ‖ cert[0 .. 175+16N)         // всё до подписей, включая kind и room
vouch:   sig  = Ed25519(identity_signing_key(actor), msg)
invite:  sig  = Ed25519(identity_signing_key(actor), msg);   sig2 = Ed25519(ik_priv, msg)
join:    sig  = Ed25519(ik_priv, msg);                       sig2 = Ed25519(identity_signing_key(subject), msg)
```

- `kind`, `roomId` и все ключи входят в подписываемые байты: сертификат одного вида или одной комнаты не превращается в другой.
- Ed25519 по RFC 8032, проверка строгая (отвергаются неканонические подписи, ключи малого порядка).
- `certHash = SHA-256(весь сертификат, включая подписи)`; `ref` в `join` — `certHash` сертификата приглашения.

### 6.2 `memkey`

```
memkey(signPub, dhPub) = SHA-256("nyxo-memkey-v1" ‖ signPub[32] ‖ dhPub[32])[0..16]
```

Второй прообраз за 2^128: подменить ключи участника X на другие с тем же `memkey` нельзя. Сопоставление «два ключа с одним `memkey`» (2^64) возможно только для пар, обе половины которых выбирает злоумышленник; в снимке такие пары ничего не дают: ключ атакующего заведомо его собственный.

### 6.3 Хэш взгляда (`ext.view`)

```
ids  = SHA-256("nyxo-view-ids-v1" ‖ u32be(id₁) ‖ … ‖ u32be(idₖ))[0..16]
keys = SHA-256("nyxo-view-v1"     ‖ u32be(id₁) ‖ memkey₁ ‖ … ‖ u32be(idₖ) ‖ memkeyₖ)[0..16]
```

Участники (включая отправителя key-share и получателя) — в порядке возрастания id. `memkeyᵢ` — по **закреплённым** ключам; для участника без ключей на сервере — 16 нулевых байт. В SKDM лежит как `"ext": { "view": { "ids": <base64 16 байт>, "keys": <base64 16 байт> } }` внутри AEAD key-share. Контейнер `ext` вводит T3.1 (R9): объект, неизвестные ключи игнорируются, сериализация не длиннее 1024 байт; ключи `prev` (план 5.2), `view` (этот документ), `kt` ([key-transparency.md](key-transparency.md)). `parseSkdm` сегодня отбрасывает неизвестные поля — это меняется.

### 6.4 Проверка сертификата клиентом

`validateCert(cert, expectSubject)` в `verifyMembershipLocked`. Общие условия (для всех видов): длина и `magic`; `kind` известен; `roomId` равен комнате; `snapN ≤ 1024`, `snap` строго возрастает; `issuedMin` ∈ `[now − 30 суток; now + 10 минут]`; `certHash` не входит в `revokedCerts`.

`vouch(A→X)`:

1. `A` — доверенный участник (`A ∈ V`, `A ≠ X`), присутствует в текущем списке сервера (иначе подписант вышел).
2. `actorKey` равен закреплённому `peer:A.signPub`; закрепление не в состоянии `pending` («ключ изменился»).
3. `sig` проверена по `actorKey`.
4. `subjectSignPub`, `subjectDhPub` равны закреплённым ключам X; если закрепления ещё нет — ключам X, которые сообщает сервер (и они закрепятся). Несовпадение с серверными ключами — отказ и статус «ключ изменился».
5. Если `X = я`: ключи в сертификате равны моим собственным identity-ключам. Иначе сертификат выдан не мне (подмена заявителя) — отказ и предупреждение пользователю.

`join(X)`:

1. Сертификат приглашения `I` присутствует (в `aux` или в `rooms.invite_cert`), `SHA-256(I) = ref`, и `I` проходит проверку `invite` ниже.
2. `actorKey` в `join` равен `I.ref` (`invitePub`); `sig` проверена этим ключом.
3. `issuedMin(join) ∈ [I.issuedMin; I.expiresMin + 10 минут]`.
4. Ключи субъекта — как в `vouch`, п. 4–5; `sig2` проверена по `subjectSignPub`.

`invite`:

1. Приглашающий `A ∈ V`, присутствует в списке, `actorKey = peer:A.signPub`, закрепление не `pending`; `sig` проверена по `actorKey`. (Для первой проверки новичка условие заменено: 9.2.)
2. `sig2` проверена по `ref` (`invitePub`).
3. `expiresMin − issuedMin ≤ 30 суток`.

### 6.5 Ключ приглашения из секрета

```
seed = HKDF-SHA256(ikm = s[16], salt = 32 нулевых байта, info = "nyxo-invite-seed-v1", L = 32)
импорт: PKCS#8 = 302e020100300506032b657004220420 ‖ seed    (extractable: true)
```

## 7. Схема БД и API

### 7.1 Схема (итоговая, R0)

```sql
CREATE TABLE room_member_certs (
  room_id    INTEGER NOT NULL REFERENCES rooms(id) ON DELETE CASCADE,
  subject_id INTEGER NOT NULL,                  -- нет FK: удаляет приложение вместе с аккаунтом/выходом
  actor_id   INTEGER NOT NULL,                  -- для join: 0
  kind       SMALLINT NOT NULL CHECK (kind IN (1, 3)),   -- 1 vouch, 3 join (invite хранится в rooms)
  cert       BYTEA NOT NULL CHECK (octet_length(cert) <= 17500),
  aux        BYTEA,                             -- join: копия сертификата приглашения
  PRIMARY KEY (room_id, subject_id, actor_id, kind)
);
CREATE INDEX idx_rmc_subject ON room_member_certs (subject_id);
CREATE INDEX idx_rmc_actor   ON room_member_certs (actor_id);
-- rooms: invite_cert BYTEA NULL, CHECK (invite_cert IS NULL OR octet_length(invite_cert) <= 17500)
```

- Времени нет: минута допуска лежит внутри сертификата. Строки удаляются: когда субъект или подписавший выходит или удаляет аккаунт; при повороте или выключении приглашения (`invite_cert → NULL`; уже сохранённые `join` остаются, у них копия в `aux`); при удалении комнаты (каскад).
- Не более 4 сертификатов допуска на `(room_id, subject_id)`; не более 1 `join` на субъекта (PK).
- Блокировки: сертификат вставляется в той же транзакции `addRoomMember` (после `rooms FOR NO KEY UPDATE`, [message-ordering.md](message-ordering.md) §8.2); удаление при выходе и удалении аккаунта — после `chats`, до `messages` ([sealed-sender.md](sealed-sender.md) §12).
- Таблица создаётся в `initDatabase`; столбец `invite_cert` — в `CREATE TABLE rooms`.

### 7.2 Маршруты

| Маршрут | Изменение |
|---|---|
| `GET /api/chats/:chatId/participants` | добавить `certs: [{ subjectId, actorId, kind, cert (base64), aux? }]` и `invite: base64 \| null` |

Ошибки возвращают `{ success:false, code, message }` ([message-ordering.md](message-ordering.md) §14). Хранилище ключей устройства, на комнату:

## 9. Клиент: алгоритмы

### 9.1 `verifyMembershipLocked` (внутри `ensureRoomSession`)

Сетевые вызовы (`participants`, `identities`) выполняются **до** блокировки; сама сверка идёт в одной секции `withLock`.

```
вход: S — список сервера (id, имя), C — сертификаты и invite, K — ключи участников (serverIdentities)
1. Ушедшие: для X ∈ V, X ∉ S, X ≠ я: удалить из V; certHash X в revokedCerts; пометить «нужна ротация»
   (существующая логика removedMembers).
2. Закрепление ключей (checkPeersWithServer): статусы unknown/unverified/verified/changed.
3. Для X с «ключ изменился» (pending): из V удалить; повторно подтвердить можно только после acceptPeerIdentityChange.
4. Замыкание, пока V растёт:
   для каждого X ∈ S \ V, X ≠ я: для каждого сертификата c с subjectId = X:
       если validateCert(c, X) → V ∪= {X}, how/by/certHash из c; прервать перебор сертификатов для X.
5. Новичок без V (V = {я}, есть сертификат с subjectId = я): «якорная» проверка (9.2).
6. unconfirmed = S \ V \ {я}.
7. Результат: members[], unconfirmed[], viewMismatch (после обработки key-share).
```

Сложность: одна проверка сертификата — одна-две проверки подписи; число сертификатов на участника ограничено 4. Замыкание останавливается за не более чем `|S|` проходов.

### 9.2 Первоначальное доверенное множество новичка

- **По одобрению.** Берётся сертификат допуска с `subjectId = я`: `actorId = A`, `A ∈ S`. Условия пп. 2–5 из 6.4, но п. 1 заменён: якорем служит ключ A, который сообщает сервер (TOFU), он закрепляется. Если ключи субъекта в сертификате не равны моим собственным, сертификат отвергается (подмена заявителя), пользователь предупреждён. Дальше `V = {я, A} ∪ { X ∈ S : memkey(ключи X, закреплённые или от сервера) ∈ snap }` (`how = vouched`, `by = A`; сам A — `how = approved`, `by = A`).
- **По ссылке.** Якорем служит ключ приглашения, выведенный из секрета (внешняя точка опоры). Условие 1 проверки `invite` (6.4) для новичка заменено: приглашающий A ещё не закреплён, поэтому сертификат принимается, если `sig2` проверена **моим** выведенным `invitePub` (его мог создать только знающий секрет), `sig` проверена ключом `actorKey` из сертификата, A есть в списке сервера и ключ A, который сообщает сервер, равен `actorKey` (иначе — подмена приглашающего, отказ и предупреждение). После успешного `join` ключ A закрепляется как `peer:A`, и `V = {я, A} ∪ { X ∈ S : memkey(X) ∈ snap(invite) }`. `how = invite`, `by = A`. Подмена ключа любого X из снимка сервером невозможна: потребовался бы второй прообраз `memkey`. Подмена самого A невозможна: сертификат подписан его ключом и ключом приглашения, выведенным из секрета, которого сервер не знает.

Bootstrap выполняется один раз на комнату: клиент сохраняет `inviteCert` и `joinCert` в `membership.bootstrap`, переданный в `ensureRoomSession` сразу после успешного входа. После перезагрузки страницы bootstrap берётся из сохранённого `members:<room>`, секрет не нужен.

### 9.3 Приглашающий: создание и показ ссылки

`client.signInvite(roomId, { ttlSeconds })` создаёт `s`, сертификат и возвращает `{ cert, secret }`. Секрет:

- не отправляется на сервер ни в каком виде (в запросе только сертификат);
- сохраняется в `inviteSecret:<room>` на устройстве, которое повернуло приглашение (чтобы показать ссылку позже);
- другим участникам не передаётся: чужая «Показать ссылку» выдаёт **код без секрета** (он даёт заявку). Чтобы выдать ссылку с секретом, участник поворачивает приглашение сам (старая ссылка перестаёт действовать, как и сейчас). Вопрос 5 раздела 17.
- не пишется в логи, `localStorage`, адресную строку и в аналитику; в памяти — на время показа.

### 9.4 Отправка ключа комнаты

`prepareShareForPeer` вызывается только для `V` (остальные возвращаются в `unconfirmed` без запроса bundle и без отметки `sharedWith2`). В SKDM кладётся `ext.view` (6.3). Когда участник становится подтверждённым, следующий `ensureRoomSession` отправляет ему ключ. Если ключ не дошёл ни до одного участника, а другие есть, отправка блокируется, как в 5.8.

Входящий SKDM от неподтверждённого отправителя принимается (индекс отправителей [sealed-sender.md](sealed-sender.md) §9.2 пополняется), но результат расшифровки его сообщений несёт `unverifiedSender: true`; интерфейс помечает такие сообщения.

### 9.5 Автоматическое поручительство

Срабатывает, когда `ensureRoomSession` вернул `removedMembers` и в `V` есть X с `by = ушедший` и `how ∈ {approved, invite, vouched}`; X всё ещё в `S`; на сервере для X нет допуска, подписанного текущим участником, кроме C. Тогда C подписывает `vouch(C→X)` (снимок — свой `V`) и отправляет `member-certs`. После этого `by` у C для X остаётся прежним (нужно для текста), `certHash` — новый. Пакет — не более 50 сертификатов.

### 9.6 Сверка взглядов

Когда SKDM применён (`applyShare`) и в нём есть `ext.view`:

```
mine = view(S, закреплённые ключи)        (6.3)
если view.ids ≠ mine.ids → записать «расхождение составов», выйти (список сервера у сторон разный: идут изменения)
если view.keys = mine.keys → ничего
иначе:
  перепроверить ключи участников с сервером (checkPeersWithServer);
  если у любого участника status = changed → подавить (расхождение объясняется сменой ключа, уже показанной пользователю);
  иначе → поднять 'view-mismatch' (не чаще раза в сутки на пару комната–отправитель).
```

Интерфейс: «Участники группы видят разные ключи шифрования (возможна подмена сервером). Сверьте коды безопасности». Тревога информативная: отправка не блокируется (SKDM уже принят по аутентифицированному каналу).

### 9.7 Ручное подтверждение

`client.trustMember(roomId, userId)`: добавить в `V` с `how = manual`, `by = null`; сертификат не публикуется. При следующем одобрении или приглашении этот участник попадёт в подписываемый снимок вместе с остальными ключами `V`. Предусловие: ключи участника закреплены и не `pending`. `acceptPeerIdentityChange(peerId)` для участника из `S` дополнительно подтверждает его вручную (решение человека о новом ключе). Подтверждение не отменяется, пока участник состоит в комнате с теми же ключами.

## 12. Граничные случаи и атаки

| № | Ситуация | Исход |
|---|---|---|
| 1 | Сервер подставляет «заявителя» с чужими ключами | одобряющий видит код безопасности и решает; одобрив, подписывает за чужие ключи. Новичок увидит несовпадение ключей субъекта со своими (6.4 п. 5) и откажется. Предел Н3 |
| 2 | Призрак: сервер добавил учётную запись в `room_participants` | сертификата нет, ключ не отправляется, статус «не подтверждён», баннер |
| 3 | Сервер скрывает сертификат у участника B | X для B «не подтверждён»; ключ не отправляется, пока пользователь не нажмёт «Доверять» или сертификат не появится |
| 4 | Повтор сертификата после выхода субъекта | отвергается у видевших выход (`revokedCerts`); остальные принимают в пределах 30 суток |
| 5 | Подписавший вышел | его сертификаты удалены сервером; клиенты не принимают сертификат ушедшего; поручительство 5.5 |
| 6 | Несколько одобрений одной заявки | первый коммит выигрывает под блокировкой комнаты; второй получает «Заявка не найдена»; допусков на субъекта не больше 4 |
| 7 | Участник сменил identity-ключ | ключи в сертификате не совпадают с серверными: `unconfirmed` и «ключ изменился»; после `acceptPeerIdentityChange` участник подтверждён вручную |
| 8 | Утечка ссылки | входит любой, у кого она есть, до поворота; новый вход видят все (лента, имя пригласившего); поворот отзывает |
| 9 | Ссылка после поворота | сервер: код другой → 400; `invite_cert` другой → `bad-cert` |
| 10 | Код без секрета в комнате без одобрения | заявка |
| 11 | Срок приглашения истёк | предпросмотр отдаёт `null`; join с просроченным `I` отвергается и сервером, и клиентами |
| 12 | Часы подписавшего спешат более чем на 10 минут | сертификат у других «из будущего»: не принимается до наступления времени; клиент повторяет сверку при следующем `ensureRoomSession` |
| 13 | Комната из 1000 участников | снимок 16 КБ; сертификат не больше 17 КБ; тело запроса `approve`/`rotate` — лимит 20 КБ |
| 14 | Сервер скрывает выход участника | клиент продолжает отправлять ему ключи (Н2) |
| 15 | Участник выходит и возвращается | новый допуск; старые сертификаты удалены сервером; `revokedCerts` хранит хэш прежнего |
| 16 | Расхождение `ext.view.ids` | сверка ключей пропускается; повторится при следующем SKDM |
| 17 | Сервер подменяет `ext.view` | невозможно: AEAD key-share |
| 18 | Оба `ids` и `keys` совпали у лжеца и у жертвы | атака раздвоения, где сервер даёт жертве и честным участникам одинаковые ключи подмены, не видна; нужны коды безопасности |
| 19 | Одновременный вход двух людей по ссылке | `addRoomMember` сериализует вступления; `V` у каждого ведёт своё замыкание |
| 20 | Сертификат вставлен, вступление откатилось | сертификат и вступление — одна транзакция |

## 13. Тесты

### Протокольные (`test/membership.protocol.test.js`, `fake-server` с сертификатами и злонамеренными методами)

- Призрак без сертификата: попадает в `unconfirmed`, ключ не отправлен, сообщения призрака помечены `unverifiedSender`; чтение призраком запрещено (ключа у него нет).
- `vouch` от доверенного: участник подтверждён, ключ отправлен; `vouch` от недоверенного — нет.
- Подмена ключей субъекта в сертификате; подмена серверных ключей; сертификат другой комнаты; сертификат другого вида (подпись `join` как `vouch`); обрезанные и удлинённые сертификаты; `snap` не по возрастанию; `snapN` больше 1024.
- Сертификат вышедшего: отвергается; повтор после выхода: отвергается при `revokedCerts`, принимается без записи только пока свеж (30 суток); пограничные значения свежести (±10 минут, 30 суток).
- Вход по ссылке: валидный; без секрета — заявка; подменённый `invitePub`; приглашение другой комнаты; просроченное; секрет не нормализуется (регистр).
- Bootstrap: по снимку новичок исключает участника с подменённым ключом; подмена ключа самого A невозможна.
- Смена identity: участник неподтверждён до нового допуска или `acceptPeerIdentityChange`.
- Поручительство: после ухода одобрившего оставшиеся подтверждают X; ручное подтверждение не публикуется.
- `ext.view`: расхождение при равных `ids` даёт тревогу; при разных `ids` — нет; при `changed` — подавляется; сервер не может подменить (искажение SKDM отвергается AEAD).
- Контрольные векторы раздела 6.6.
- Существующий тест «удаление → ротация» проходит без изменений; секрет ссылки не встречается ни в одном исходящем запросе fake-сервера.

### Серверные (`makeFakeApp`, `makeFakeDb`) и сквозные (Postgres)

- `approve` без сертификата — 400; сертификат не от сессии, не для заявителя, с чужими ключами, чужой комнаты — отказ.
- `join` без `joinCert` — заявка, даже при `requireApproval = false`; с неверной подписью, `ref`, чужим субъектом — `bad-cert`.
- `rotate` без `inviteCert` при `requireApproval = false` — 400; выключение и поворот обнуляют `invite_cert`, `join` остаются.
- Выход и удаление аккаунта удаляют сертификаты (оба направления); каскад при удалении комнаты.
- Лимит: не более 4 допусков на субъекта.
- Параллельные одобрения и выход подписавшего — без `40P01` в ответах.

## 14. Выкат

- Схема — в DDL `initDatabase` (R0). Старых комнат нет: у каждой комнаты с самого начала известны `V` создателя и сертификаты.
- Клиент и сервер выкатываются вместе. Старая вкладка при отправке в комнату получает 400 `client-outdated`, `approve` без сертификата — 400 `cert-required`.
- Новые ограничения (одобрение, вход по коду) требуют обновления «Как это работает», подсказок в окне приглашения и README (T5.1).
- Откат релиза — по R0: остановить сервис, удалить базу, развернуть прежнюю версию.

## 15. Запасной путь: если T4.2 выкатывается поверх рабочей базы

Нужен, только если версия до T4.2 уже выкачена и в ней есть настоящие комнаты (вопрос 1).

- `lib/migrations/04NN-signed-membership.js`, идемпотентная: `CREATE TABLE room_member_certs`, `ALTER TABLE rooms ADD COLUMN invite_cert`.
- Существующие комнаты: у клиента нет `members:<room>` с сертификатами. При первом запуске нового клиента `V` = локальный `members:<room>` (если есть) или весь список сервера, `how = manual`, `by = null` — комната «переходит» на текущий состав как на доверенный; новые добавления требуют сертификатов. Это ослабление действует только для состава на момент обновления и показывается пользователю один раз.
- Старые ссылки без секрета становятся заявками (так и в основном пути).

## 16. Ворота G4

Предупреждения о составе группы: призрак, добавленный через БД, не получает ключ и виден в окне участников как «не подтверждён»; баннер и лента показывают текст; одобрение и вход по ссылке подписываются; повороты не ломают чтение истории.

## 17. Открытые вопросы
