## 1. Что решено

1. Сервер задаёт список участников комнаты `S` и этого не меняет: он по-прежнему может **убрать** участника. Но клиент отправляет свой Sender Key только тем участникам, чей допуск подтверждён: подписью участника, которому клиент доверяет, подписью по ссылке с секретом, либо ручным решением пользователя. «Призрак», которого сервер добавил сам, ключа не получает.
2. Четыре вида сертификатов (подпись Ed25519 identity-ключом или ключом приглашения, метка домена `nyxo-member-cert-v1\0`): допуск (`vouch`, 1), приглашение (`invite`, 2), вход по приглашению (`join`, 3) и повторный допуск (`revouch`, 4). Формат — бинарный, **фиксированной длины** (271 или 335 байт), раздел 6. Снимок состава в сертификате представлен подписанным хэшем; сам снимок отдаётся только тому, кому он нужен: субъекту допуска и вошедшему по приглашению (в ответе на `POST /join`, не по коду).
3. Вход без одобрения возможен **только** по ссылке `#join=<КОД>.<секрет>`. Секрет в фрагменте на сервер не уходит. Код без секрета (набран руками, утёк в логи) превращается в заявку на одобрение участником. Роли ключей: `секрет → seed → ключ приглашения`, его открытая часть лежит в сертификате приглашения.
4. Новичок получает первоначальное доверенное множество `V` из сертификата, а не от сервера: по сертификату допуска (якорь — ключ одобрившего) или по сертификату приглашения (якорь — ключ, выведенный из секрета ссылки; это внешняя точка опоры, MITM сервера при первом контакте для входа по ссылке закрыт). **Якорная проверка выполняется только при локальной записи намерения входа `joinIntent:<room>`**, которую клиент создаёт сам при входе по ссылке или отправке заявки и расходует один раз; никогда — для создателя комнаты и никогда, если `V` комнаты уже записывался (9.2). **Вид сертификата определяется способом входа:** вход по ссылке подтверждает только `join` с `ref`, равным сохранённому хэшу приглашения, заявка — только `vouch`; иначе явный допуск подменил бы сильный якорь (секрет ссылки) слабым (ключ, который сообщает сервер).
5. Выход участника и удаление аккаунта не подписываются: управляет сервер. Он может только убрать участника (отказ в обслуживании), но не добавить читателя. Отзыв идёт **по субъекту**: клиент ведёт `removed:<room>` (id → минута выхода) и отвергает сертификаты этого субъекта и подписанные им, выданные не позже выхода.
6. «Хэш взгляда» на ключи участников в SKDM (`ext.view`) ловит расхождение: сервер показал разным участникам разные ключи одного человека. Это верно только при настоящих закреплённых ключах обеих сторон канала (раздел 3, строка про `ext.view`).
7. Ручное «Доверять участнику» действует **только на этом устройстве**, сертификата не публикует и **не попадает в снимок**, который подписывающий кладёт в допуск или приглашение. Передать доверие группе можно только явным действием «Поручиться за участника». Автоматическое поручительство при уходе подписавшего (9.5) публикует отдельный вид сертификата — повторный допуск — и подписано честно: «после выхода {прежний подписавший}».
8. Словарь статусов клиента объединяет два рабочих плана (раздел 4): `members[].status ∈ {self, confirmed, unconfirmed}`, `how ∈ {creator, approved, invite, vouched, revouched, manual}`.
9. Свой ключ комнаты ротируется, если получатель текущего ключа перестал быть адресатом: вышел из `S`, выпал из `V` (отзыв: ключ изменился и не принят, `changed`), исключён из рассылки (`log-mismatch`) или сменил ключи. Кому ключ отправлен, видно из **журнала доставок** собственного ключа `{id, memkey}`, который ведётся только на добавление; отметки рассылки (`sharedWith2`) решение о ротации не определяют (9.1). События уровня человека (`changed`, `log-mismatch`) проверяются во всех общих комнатах.

## 2. Цели и не-цели

### Цели

- **Ц1.** Сервер не может заставить честный клиент отправить Sender Key новому, неподтверждённому участнику, не получив для этого подпись доверенного участника или секрет ссылки.
- **Ц2.** Новичок при входе по ссылке не доверяет серверу в вопросе «кто в группе»: ключи существующих участников сверяются со снимком, подписанным пригласившим (хэш снимка внутри сертификата).
- **Ц3.** Сертификат нельзя перенести в другую комнату, выдать за сертификат другого человека или предъявить повторно после выхода без ведома тех, кто видел выход (в пределах свежести): отзыв по субъекту, не по одному хэшу.
- **Ц4.** Расхождение «участники видят разные ключи» (раздвоение сервера) замечается, если у жертвы есть хотя бы один честный путь к другому участнику.
- **Ц5.** Сервер хранит минимум: сертификаты только текущих участников и только пока они состоят в комнате; вечного журнала нет.
- **Ц6.** Старые клиенты не поддерживаются (R0); формат E2EE-конверта сообщений не меняется. Меняются SKDM (необязательное поле `ext`) и правила, кому клиент отправляет ключ.
- **Ц7.** Объём ответов о составе линеен по числу участников: сертификат фиксированной длины, снимок отдаётся только его адресату, сертификаты других участников — отдельным запросом и только для тех, кого клиент ещё не подтвердил (`S \ V`, раздел 7.2).

### Не-цели

- **Н1.** Защита от злонамеренного **участника**: любой участник может одобрить кого угодно (поведение продукта сегодня), а участник с ключом комнаты может переслать его хоть кому.
- **Н2.** Подпись удаления и подтверждение того, что ушедший действительно ушёл. Сервер может не убирать ушедшего из списка; только при сговоре с ним ушедший продолжит получать ключи (раздел 12).
- **Н3.** Защита первого контакта при одобрении заявки: сервер может подставить «заявителя» с чужими ключами. Одобряющий видит ключи заявителя и код безопасности; решение человека (раздел 12, строка 1).
- **Н4.** Защита изолированной группы, которой целиком показан поддельный мир: новичок по одобрению принимает ключ одобрившего с сервера (TOFU).
- **Н5.** Анонимность допуска: сервер знает, кто кого одобрил (он обрабатывает запрос) и хранит пару в сертификатах, пока субъект в комнате.
- **Н6.** Роли и права (владелец, администратор). Все участники равны, как сейчас.
- **Н7.** Исключение участника другим участником. Такой функции нет.

## 3. Модель угроз

| Кто | Что видит или умеет | Что даёт этот дизайн | Что остаётся |
|---|---|---|---|
| Работающий злонамеренный сервер | список участников, заявки, identity-ключи (key-store), сертификаты, очередь key-share | не может заставить честный клиент отправить ключ «призраку»; не может подменить ключ участника, названный в снимке; не может подделать сертификат допуска или входа; не может навязать якорную проверку создателю или участнику, у которого уже есть `V` | может убрать участника, скрыть сертификаты (тогда участник «не подтверждён»), показать заявителя с чужими ключами (решает человек), раздвоить мир изолированной группе |
| Бывший участник в сговоре с сервером | знает ключ комнаты на момент ухода | клиенты, видевшие выход, ротируют ключ и отзывают сертификаты ушедшего (по субъекту, 30 суток) | клиент, которому сервер скрыл выход, продолжит отправлять ключи (Н2) |
| Злонамеренный участник | может одобрять и приглашать | его допуск ограничен его же подписью: поручиться он может за кого угодно | вред ограничен тем, что любой участник и так может раскрыть ключ комнаты |
| Читатель дампа БД | сертификаты текущих участников: id комнаты, субъекта и подписавшего, минута допуска, хэш снимка; снимки допусков (16 байт `memkey` на участника) | сертификаты не содержат приватных данных, секрета ссылки и текста; после выхода строки удаляются | граф «кто кого одобрил» для текущих участников; минута допуска; `memkey` участников |
| Утёкшая ссылка с секретом | любой, у кого она есть, может войти (так и задумано) | лечится поворотом приглашения; ограничение срока (до 720 ч при входе без одобрения), лимит участников | вошедший посторонний получит ключи от тех, кто примет его join-сертификат; участники видят «по приглашению {имя}». **Отзыв поворотом действует только при честном сервере:** недобросовестный сервер вправе принять `join` по старому сертификату приглашения, и клиенты его примут (проверка сертификата не знает об отзыве) |
| Утечка только кода (без секрета) | сервер и логи знают код | войти напрямую нельзя: код без секрета даёт заявку; ссылка с секретом, поданная в комнату с одобрением, — тоже заявка | заявку должен одобрить человек. **Предпросмотр по коду выдаёт сертификат приглашения, то есть раскрывает пригласившего (id, identity-ключ), число участников его `V` (`snapN`) и хэш снимка любому, у кого есть код.** Сам снимок по коду не выдаётся: `memkey` v2 — функция id и открытых ключей, по каталогу ключей он обратим, поэтому снимок отдаётся в ответе на `POST /join` только владельцу `join`-сертификата, подписанного ключом приглашения (то есть знающему секрет) |
| Сервер возвращает в комнату бывшего участника P без сертификата, пока жив сертификат приглашения, выданного до выхода P (до 30 суток) | P состоит в снимке такого приглашения; знает всё, что знал при выходе | видевшие выход имеют `removed` для P и подтверждают его только по новому допуску | **вошедшие по этой ссылке после выхода P `removed` для P не имеют** (выход они не видели) и подтверждают его по снимку, то есть отправят ему свои ключи. Предел принят: действует только для бывших участников из снимка, только пока жив сертификат приглашения (до 720 ч), не касается тех, кто видел выход. Лечится поворотом ссылки после ухода участника; вопрос 17 |

### Что сервер может и не может подделать

| Может | Не может |
|---|---|
| добавить в `room_participants` любую учётную запись (призрака) | заставить честного участника отправить призраку Sender Key: нет сертификата, подписанного подтверждённым участником, и нет join-сертификата по ссылке |
| убрать участника из списка или из очереди key-share | добавить читателя; убрать участника незаметно для тех, кто смотрит на список (ключ ротируется) |
| скрыть сертификат от части клиентов | подделать сертификат: подпись проверяется закреплённым identity-ключом подписавшего (или ключом приглашения) |
| подставить клиенту другие identity-ключи участника X | протащить их мимо снимка (`memkey`, 16 байт SHA-256 от id и ключей) и мимо закреплённых ключей: ключи субъекта сверяются с сертификатом, а ключи участников — со снимком |
| завести учётную запись-клон с теми же identity-ключами, что у X | выдать клон за подтверждённого: `memkey` зависит от id, а новичок с ключами, уже стоящими у другого участника, остаётся неподтверждённым; понизить самого X клоном тоже нельзя: кто уже в `V` по id, там и остаётся (6.2) |
| повторить сертификат вышедшего участника | заставить клиента принять его, если клиент видел выход (`removed:<room>` по субъекту) или сертификат старше 30 дней |
| показать заявителя с чужими ключами | подписать за одобряющего: одобрение — действие человека на устройстве |
| отдать новичку чужой сертификат допуска | выдать его за адресованный новичку: ключи субъекта в сертификате должны совпасть с ключами самого новичка |
| подсунуть создателю или участнику с готовым `V` сертификат от «своего» человека | заставить принять его за якорь: без `joinIntent` якорной проверки нет (9.2) |
| подсунуть вошедшему по ссылке вместо `join` явный `vouch` от «своего» участника | заменить сильный якорь (секрет ссылки) слабым (ключ, который сообщает сервер): для `via: 'invite'` годится только `join` с `ref`, равным сохранённому хэшу приглашения (9.2) |
| подменить поле `ext.view` в SKDM | изменить SKDM **при настоящих закреплённых ключах**: он внутри AEAD попарного канала, привязанного к identity обеих сторон. Если identity-ключ собеседника подменён до первого закрепления (первый контакт, TOFU), сервер сам терминирует канал и может писать любой `ext.view`: `view` защищает от расхождения при уже закреплённых ключах, а не от MITM при первом контакте |

## 4. Решения и отличия от рабочих планов

| Что | Решение | Откуда расхождение |
|---|---|---|
| Идентификаторы в сертификате | `u32` (комнаты и пользователи — `INTEGER`) | план криптографии (раздел 8): `u64`; шире не нужно, согласуется с тегами [sealed-sender.md](sealed-sender.md) и метками прозрачности |
| Статусы участников | `status ∈ {self, confirmed, unconfirmed}`, `how ∈ {creator, approved, invite, vouched, revouched, manual}`, `by` | план клиента (5.4): `self/confirmed/unconfirmed` и `how`; план криптографии: `verified/legacy`, `unverifiedMembers`, `vouchForMember`. Побеждает словарь клиента; значение `legacy` не нужно (старых комнат нет, R0); `revouched` добавлено ревью (М6) |
| Метка «Создатель группы» у другого участника | не показывается; создатель виден только у себя («Вы создали группу») | сервер не хранит и не подписывает создателя; метка у чужого участника была бы неподтверждённым утверждением сервера |
| Ручное «Доверять участнику» | локальное решение, сертификат не публикуется, в снимок не входит; передача доверия группе — явное «Поручиться за участника» (5.5) | план криптографии (раздел 8): «вручную ... любой проверенный участник» мог публиковать vouch; первая редакция этого документа включала ручных в снимок, и ошибка одного человека распространялась на каждого новичка (ревью М4) |
| Хэш взгляда | считается по **списку сервера** с закреплёнными ключами (все участники), а не по доверенному множеству `V` | план криптографии: по `V`. При разном `V` у участников сверка отключалась бы чаще, чем нужно |
| `memkey` | `SHA-256("nyxo-memkey-v2" ‖ u32be(id) ‖ signPub ‖ dhPub)[0..16]`, привязан к id; две записи с одинаковыми ключами — обе неподтверждённые | реестр плана криптографии: `nyxo-memkey-v1` без id. При v1 клон-призрак с теми же ключами имел тот же `memkey` и считался подтверждённым по снимку (ревью М2) |
| Снимок в сертификате | подписан только хэш: `snapN u16 ‖ snapHash[32]`, `snapHash = SHA-256("nyxo-snap-v1" ‖ u16be(N) ‖ memkey₁ ‖ … ‖ memkeyₙ)`; сертификат фиксированной длины; снимок хранится рядом и отдаётся только субъекту допуска и вошедшему по приглашению (в ответе `POST /join`, не в предпросмотре по коду, повторное ревью 7) | первая редакция: снимок внутри сертификата (до 17 КБ), и ответ `participants` вёл к квадратичному трафику, 16 МБ на комнату из 1000 человек (ревью М5) |
| Удалённые подписанты | сервер удаляет сертификаты ушедших подписантов; клиенты не принимают сертификат ушедшего подписанта и отзывают по субъекту (`removed:<room>`); оставшиеся участники автоматически подписывают **повторный допуск** (9.5) | план криптографии: «кто не успел проверить X, подтвердит вручную»; без автоматического поручительства группа ломалась бы после ухода одобрившего. Первая редакция использовала обычный `vouch` и список `revokedCerts` по хэшам (ревью М3, М6) |
| Якорная проверка новичка | только при `joinIntent:<room>`, один раз; вид сертификата определён способом входа (`invite` — только `join` с `ref` = хэшу приглашения из `joinIntent`, `request` — только `vouch`) | первая редакция запускала её при любом `V = {я}` и сертификате для меня: сервер мог подсунуть «подтверждённого» создателю или участнику, от которого скрыл остальных (ревью М1, блокер); без привязки к способу входа явный допуск подменял якорь по секрету слабым (повторное ревью 3) |

## 5. Протокол по шагам

### 5.1 Создание комнаты

Создатель: `V = {я}`, `how = creator`, `bootstrapDone = true` записываются сразу. Сертификатов нет, `joinIntent` не создаётся (якорная проверка создателю не применяется ни при каких условиях, 9.2). Комната создаётся как сейчас (`POST /api/chats`).

### 5.2 Вход по одобрению (заявка)

```
J (заявитель)             Сервер                       A (участник, V_A)
  — код без секрета ——>   заявка join_requests
  J: joinIntent:<room> = { via:'request' }  (запись на устройстве J при нажатии «Отправить заявку»)
                                          —— GET join-requests ——>  видит J и его identity-ключи (и kt)
                                                                    сверяет код безопасности (по желанию)
                                                                    подписывает vouch(A→J, хэш снимка V_A)
                          <—— POST approve {cert, snap} —————————
                          addRoomMember (одной транзакцией со вставкой сертификата и снимка)
J <—— joinRequestDecided
J: ensureRoomSession: находит vouch (kind 1; другие виды при via:'request' не годятся) с subject = я, проверяет (6.4), забирает снимок для себя, строит V_J (9.2)
```

Условия: у заявителя есть identity-ключи в key-store (иначе одобрение блокируется с объяснением «пользователь ещё не настроил шифрование»); `approve` без сертификата или без снимка отвергается (400 `cert-required`, `snap-required`).

### 5.3 Вход по ссылке (приглашение)

Приглашающий (любой участник, `requireApproval = false`):

```
s = 16 случайных байт                                    (секрет, остаётся на устройстве и в ссылке)
seed = HKDF-SHA256(ikm = s, salt = 32 нулевых байта, info = "nyxo-invite-seed-v1", L = 32)
(ik_priv, invitePub) = Ed25519 из seed                   (раздел 6.5)
cert_invite = invite(room, issuedMin, nonce, actor = я, invitePub, expiresMin, хэш снимка V_я без ручных),
              подписи: sig — моим identity-ключом, sig2 — ключом приглашения
POST /api/chats/:chatId/invite/rotate { …, inviteCert, inviteSnap }  → rooms.invite_cert, invite_snap, invite_actor_id
inviteSecret:<room> = { s, certHash }                    (на этом устройстве; ссылку показывают только при совпадении certHash, 9.3)
ссылка: https://host/#join=<КОД>.<base64url(s)>
```

Входящий (у него ссылка):

```
parseInviteInput → { code, secret }                       (public/lib/invite.js; секрет НЕ нормализуется)
POST /api/chats/join/preview { code } → { roomId, roomName, inviteCert, … }     (снимка в предпросмотре нет: по коду он не выдаётся, раздел 3)
проверка: invitePub, выведенный из secret, равен invitePub в сертификате; roomId совпадает; срок не истёк;
          sig2 проверена этим invitePub; sig действительна по ключу actorKey из сертификата (ключ закрепится позже, 6.4)
joinIntent:<room> = { via:'invite', at, inviteHash = SHA-256(inviteCert) }      (запись на устройстве; создаётся действием пользователя «Войти по ссылке»
                                                                                 после этой проверки; inviteHash — приглашение, проверенное секретом, 9.2)
cert_join = join(room, issuedMin, nonce, subject = я (id, ключи), ref = SHA-256(cert_invite)),
            подписи: sig — ключом приглашения, sig2 — моим identity-ключом
POST /api/chats/join { code, joinCert } → сервер проверяет (7.2), addRoomMember, сохраняет сертификат, отвечает { …, inviteSnap }
joinIntent.inviteSnap = inviteSnap, если SHA-256("nyxo-snap-v1" ‖ u16be(N) ‖ inviteSnap) равен snapHash в сертификате (иначе ошибка «приглашение повреждено»);
                                                                                (запись в joinIntent переживает перезагрузку страницы)
V_J = {я} ∪ {участники из снимка приглашения, ключи которых на сервере совпали с memkey} ∪ {приглашающий}   (9.2)
секрет и ключ приглашения стираются из памяти и из адресной строки (consumeJoinFragment)
```

Секрет после входа не нужен: проверка после перезагрузки опирается на `inviteHash` из `joinIntent` (хэш приглашения, которое уже проверено секретом), на `inviteSnap` оттуда же и на `join` с `ref = inviteHash` (9.2). Если ответ на `POST /join` потерян, `joinIntent` остаётся без `inviteSnap`; повторный `POST /join` тем же `joinCert` (клиент хранит его в `joinIntent`) от уже вошедшего возвращает тот же ответ, пока `rooms.invite_cert` не изменился. После поворота приглашения снимка получить нельзя: якорная проверка невозможна, участники остаются неподтверждёнными до ручного решения (предел, вопрос 18).

Если ссылка с секретом предъявлена в комнату, где нужно одобрение (`invite_cert = NULL`): сервер отвечает заявкой, `joinCert` не принимается, секрет игнорируется и стирается (клиент записывает `joinIntent` с `via:'request'`, без `inviteHash` и `inviteSnap`).

### 5.4 Код без секрета

Вход по коду без `joinCert` — всегда заявка (200 `{ success:true, pending:true, requestId }`), даже если в комнате `requireApproval = false`. Интерфейс объясняет разницу: «Ссылка с секретом впускает сразу; код без ссылки отправляет заявку».

### 5.5 Поручительство

**Повторный допуск после ухода подписавшего (автоматически, 9.5).** Участник C, у которого в `V` есть X с `how ∈ {approved, invite, vouched, revouched}`, `by = A`, видит, что A вышел из комнаты (`removedMembers`). C не подписывает сразу: задача кладётся в сохранённую очередь `revouch:<room>` (не больше 50 задач за проход), срок исполнения сдвигается на `min(rank, 30) × 2 минуты`, где `rank` (от 0) — позиция C в списке `S \ {X, A}`, упорядоченном по возрастанию `SHA-256("nyxo-revouch-v1" ‖ u32be(X) ‖ u32be(id))`. Ранг считается по списку сервера `S`, а не по `V`: клиент не знает чужого локального `V` и не может выяснить, у кого X тоже с `by = A`; тот, у кого X не подтверждён таким путём, просто не ставит задачу, а оставшиеся действуют не позже чем через час. Порядок зависит от X, поэтому нагрузка по разным субъектам распределяется между участниками, а не ложится на одного с младшим id. К сроку клиент перечитывает сертификаты X (`GET member-certs?subjects=X`): если для X уже есть действительный допуск (`vouch` или `revouch`) от текущего участника, задача снимается, а у C запись X в `V` обновляется (`how`, `by`, `certHash` — из найденного допуска); иначе C подписывает `revouch(C→X)` со ссылкой `ref` на хэш исходного допуска (для X, подтверждённого по снимку, — `certHash` сертификата, в `snapHash` которого вошёл `memkey(X)`: допуска X отдельным сертификатом не было) и отправляет `POST member-certs`. Не чаще одного на пару (C, X); сервер хранит не более 4 допусков (`vouch` и `revouch` вместе) на субъекта, лишние отвергает ответом 200 `{ success:true, stored:false }`. Повторный допуск **передаёт** уровень доверия, который C уже принял по цепочке сертификатов, и не означает новой проверки: в интерфейсе он подписан как «Повторно подтверждён {C} после выхода {A}». Если у C X подтверждён только вручную (`how = manual`), автоматического допуска нет.

**Явное поручительство (ручное, 9.5).** Действие «Поручиться за участника» на карточке участника из `V`: C подписывает обычный `vouch(C→X, хэш снимка V_C без ручных)` и отправляет `POST member-certs`. Это единственный способ передать группе доверие, принятое вручную. Перед подписью интерфейс предупреждает: «Вы подпишете, что знаете {имя}. Остальные участники начнут отправлять ему ключи». Действие необратимо для опубликованного сертификата (он живёт, пока C и X в комнате).

### 5.6 Выход и удаление аккаунта

Подписей нет. Сервер: удаляет участника и все сертификаты, где он субъект или подписавший; если он автор приглашения комнаты (`rooms.invite_actor_id`), обнуляет `invite_cert`, `invite_snap`, `invite_actor_id` — код остаётся и принимает только заявки (ревью М7). Клиенты по `roomMembersChanged` видят, что участника нет в списке: удаляют его из `V`, записывают `removed:<room>[id] = минута`, ротируют свой Sender Key до рассылки (9.1). Устройство автора приглашения при выходе, повороте, выключении и при ответе сервера `invite: null` удаляет `inviteSecret:<room>`.

**Собственный выход.** Клиент, выходящий из комнаты (и удаляющий аккаунт), стирает на устройстве записи комнаты, связанные с составом: `trusted:<room>` (вместе с `bootstrapDone`), `removed:<room>`, `revouch:<room>`, `joinIntent:<room>`, `viewPending:<room>`, `viewDiv:<room>:*`, `delivered:<room>:*`, `inviteSecret:<room>`. Повторный вход в ту же комнату начинается заново: новый `joinIntent` и якорная проверка (9.2). Иначе `bootstrapDone` от прежнего членства запрещал бы якорь, а прежний `V` и `removed` описывали бы комнату, которую устройство уже не наблюдало. Цена: вернувшийся не помнит, кто вышел за время его отсутствия (предел, раздел 12, строка 31).

### 6.1 Макет (big-endian, без разделителей, фиксированная длина)

| Смещение | Размер | Поле | `vouch` (1) | `invite` (2) | `join` (3) | `revouch` (4) |

| 0 | 8 | magic `"NYXOMC01"` | да | да | да | да |
| 8 | 1 | kind | 1 | 2 | 3 | 4 |
| 9 | 4 | `roomId` u32 | да | да | да | да |
| 13 | 4 | `issuedMin` u32, минуты от эпохи Unix | да | да | да | да |
| 17 | 16 | `nonce`, случайные | да | да | да | да |
| 33 | 4 | `subjectId` u32 | допускаемый | 0 | входящий | допускаемый |
| 37 | 32 | `subjectSignPub` | да | нули | да | да |
| 69 | 32 | `subjectDhPub` | да | нули | да | да |
| 101 | 4 | `actorId` u32 | одобряющий | приглашающий | 0 | подписавший повторный допуск |
| 105 | 32 | `actorKey` | identity Ed25519 одобряющего | identity Ed25519 приглашающего | `invitePub` | identity Ed25519 подписавшего |
| 137 | 32 | `ref` | нули | `invitePub` | SHA-256 всего сертификата приглашения | `certHash` исходного допуска, не нули |
| 169 | 4 | `expiresMin` u32 | 0 | срок приглашения | 0 | 0 |
| 173 | 2 | `snapN` u16 | N, 1…1024 | N, 1…1024 | 0 | 0 |
| 175 | 32 | `snapHash` | хэш снимка `V` одобряющего (без ручных), включая его самого | хэш снимка `V` приглашающего (без ручных), включая его самого | нули | нули |
| 207 | 64 | `sig` | да | да | да | да |
| 271 | 64 | `sig2` | нет | да | да | нет |

Длина: `vouch` и `revouch` — **271 байт**; `invite` и `join` — **335 байт**. Любая другая длина — отказ. Поля, не используемые видом, — нули (в таблице «нули», «0»); клиент и сервер отвергают сертификат с ненулевым значением в неиспользуемом поле (ревью М11): иначе в сертификат можно протащить произвольные байты под подписью.

Хэш снимка и сам снимок:

```
snap     = memkey₁ ‖ … ‖ memkeyₙ         // отсортированные по возрастанию, без повторов, N ≤ 1024; 16·N байт
snapHash = SHA-256("nyxo-snap-v1" ‖ u16be(N) ‖ snap)
```

Подписывается только `snapHash`. Сам снимок (до 16 КБ) хранится на сервере **рядом** с сертификатом и отдаётся только субъекту допуска (`vouch`) или вошедшему по приглашению (в ответе на `POST /join`; в предпросмотре по коду его нет), раздел 7.2. Принявший снимок проверяет `N = snapN` и `SHA-256("nyxo-snap-v1" ‖ u16be(N) ‖ snap) = snapHash` до любого использования.

Подписи:

```
msg  = "nyxo-member-cert-v1\0" ‖ cert[0 .. 207)             // всё до подписей, включая kind, room и snapHash
vouch:   sig  = Ed25519(identity_signing_key(actor), msg)
revouch: sig  = Ed25519(identity_signing_key(actor), msg)
invite:  sig  = Ed25519(identity_signing_key(actor), msg);   sig2 = Ed25519(ik_priv, msg)
join:    sig  = Ed25519(ik_priv, msg);                       sig2 = Ed25519(identity_signing_key(subject), msg)
```

- `kind`, `roomId`, все ключи и `snapHash` входят в подписываемые байты: сертификат одного вида или одной комнаты не превращается в другой, а снимок нельзя подменить.
- **Строгая проверка Ed25519** (ревью М11, повторное ревью 2) — явная, одна и та же функция в `lib/membership-certs.js` и `public/lib/membership.js`. Для каждого открытого ключа (`actorKey`, `subjectSignPub`, `invitePub`) и для точки `R` подписи (первые 32 байта):
  1. декодирование по RFC 8032 §5.1.3: длина 32 байта; `y < p` (каноническая кодировка); корень `x` существует; **если `x = 0` при бите знака 1 — отказ** (п. 4 RFC: так выглядят `01 00…00 80` и `ec ff…ff ff`);
  2. точка **не малого порядка**: `[8]P ≠ O` на декодированной точке. Это закрывает все восемь точек порядка 1, 2, 4, 8 без таблицы кодировок (канонические кодировки — в 6.6, для тестов);
  3. для подписи `S < L`.

  Платформенный `verify` (Web Crypto, Node) принимает ключи малого порядка и ещё одну некорректную кодировку: единичную точку `01 00…00` и единичную точку с битом знака `01 00…00 80` (OpenSSL при `x = 0` бит знака не проверяет). С любой из них как с ключом пара `R = 01 00…00`, `S = 0` «подходит» к любому сообщению (два отрицательных вектора, 6.6). Поэтому проверка явная, а не «строго по RFC 8032»; описание «`y < p` плюс восемь точек малого порядка» неполно: ключ `01 00…00 80` имеет `y = 1 < p` и не входит в список восьми канонических кодировок (там `01 00…00`), поэтому проверка по такому списку его пропускает. Его отвергает пункт 1 и, если декодер бит знака при `x = 0` не проверяет, пункт 2 (декодированная точка — единичная, `[8]P = O`). Реализация обязана выполнять оба пункта, а не выбирать один.
- `certHash = SHA-256(весь сертификат, включая подписи)`; `ref` в `join` — `certHash` сертификата приглашения; `ref` в `revouch` — `certHash` исходного допуска.

### 6.2 `memkey`

```
memkey(id, signPub, dhPub) = SHA-256("nyxo-memkey-v2" ‖ u32be(id) ‖ signPub[32] ‖ dhPub[32])[0..16]
```

`memkey` **привязан к id** (ревью М2). Раньше (`nyxo-memkey-v1`) в хэш входили только ключи, и сервер, заведя учётную запись-клон с теми же identity-ключами, что у участника X, получал для клона тот же `memkey`, который стоит в снимке, и клон считался подтверждённым. Теперь у клона другой id и другой `memkey`; кроме того, действует **правило дубликатов** (повторное ревью 5). Если в списке сервера `S` несколько участников (не считая меня) имеют одинаковые `(signPub, dhPub)`:

- **кто уже в `V` по id, там и остаётся**; клиент показывает предупреждение `duplicate-keys`, но не понижает участника и не ротирует ключ: иначе сервер, заведя клон, мог бы выбить из `V` любого и вызвать ротации во всех общих комнатах, а ручное подтверждение (9.7) переставало бы быть постоянным;
- **не подтверждается новичок с чужими ключами:** ни замыканием по сертификатам, ни снимком якоря, ни `revouch`, даже если `memkey` стоит в снимке (клиент не пытается угадать, чьи это ключи); остаётся «Доверять участнику» с предупреждением, решает человек;
- если ни один из группы в `V` не входит, не подтверждается никто из них, пока пользователь не решит сам (так сервер может задержать автоматическое подтверждение нового участника клоном его ключей; это отказ в обслуживании, который сервер и так умеет, предел принят).

Второй прообраз за 2^128: подменить ключи участника X на другие с тем же `memkey` нельзя. Сопоставление «два ключа с одним `memkey`» (2^64) возможно только для пар, обе половины которых выбирает злоумышленник; в снимке такие пары ничего не дают: ключ атакующего заведомо его собственный.

### 6.3 Хэш взгляда (`ext.view`)

```
ids  = SHA-256("nyxo-view-ids-v1" ‖ u32be(id₁) ‖ … ‖ u32be(idₖ))[0..16]
keys = SHA-256("nyxo-view-v1"     ‖ u32be(id₁) ‖ memkey₁ ‖ … ‖ u32be(idₖ) ‖ memkeyₖ)[0..16]
```

Участники (включая отправителя key-share и получателя) — в порядке возрастания id. `memkeyᵢ` — по **закреплённым** ключам (6.2). Три особых случая: (1) у участника нет ключей на сервере — 16 нулевых байт; (2) ключи на сервере есть, а закрепления у меня ещё нет (первого контакта не было) — по ключам, которые сообщает сервер, то есть по тем, что закрепятся при первом контакте: у честных сторон значения совпадают, а раздвоение при ещё не закреплённом участнике тоже видно; (3) состояние `changed` (ключ изменился, новый ключ сервера не принят) — берётся **прежний закреплённый** ключ, а не новый ключ сервера (9.6). В SKDM лежит как `"ext": { "view": { "ids": <base64 16 байт>, "keys": <base64 16 байт> } }` внутри AEAD key-share.

Контейнер `ext` вводит T3.1 (R9): объект, неизвестные ключи игнорируются, сериализация не длиннее **2048 символов** (константа `MAX_EXT_CHARS` в `public/e2ee.js`; первая редакция называла 1024 байта); ключи `prev` (план 5.2), `view` (этот документ), `kt` ([key-transparency.md](key-transparency.md)). Правила разбора: `prev` — условие SKDM, испорченный `prev` отвергает SKDM целиком; `view` и `kt` — справочные подсказки: испорченное или неполное поле **отбрасывается, в консоль пишется предупреждение, SKDM принимается**. `parseSkdm` сегодня отбрасывает неизвестные поля — это меняется.

### 6.4 Проверка сертификата клиентом

`validateCert(cert, expectSubject)` в `verifyMembershipLocked`.

Константы времени (единые для всех проверок):

| Константа | Значение | Где |
|---|---|---|
| `FRESH` | 30 суток | клиент: `issuedMin ≥ now − FRESH` для принимаемого сертификата |
| `SKEW` | 10 минут | клиент: `issuedMin ≤ now + SKEW`; `join.issuedMin ∈ [I.issuedMin − SKEW; I.expiresMin + SKEW]` (нижняя граница нужна, когда часы приглашающего спешат: вход сразу после выдачи приглашения иначе «раньше» приглашения) |
| `SERVER_WINDOW` | ±10 минут | сервер: `issuedMin` присланного сертификата (`vouch`, `revouch`, `join`, `invite`) лежит в `[now − 10 мин; now + 10 мин]`; иначе 400 `bad-cert-time` (сертификат создаётся действием «сейчас», старый — это повтор) |
| `INVITE_MAX` | 720 часов | `expiresMin − issuedMin ≤ INVITE_MAX`; `INVITE_TTL_HOURS` при `requireApproval = false` ограничивается этим значением. Сервер при `invite/rotate` сверяет **длительность** `expiresMin − issuedMin` с выбранным сроком (±1 минута), а не абсолютное время с `code_expires_at` (7.2) |

Общие условия (для всех видов): точная длина по виду и `magic`; `kind` известен; `roomId` равен комнате; неиспользуемые поля — нули; для видов со снимком `1 ≤ snapN ≤ 1024`, для остальных `snapN = 0`; строгая проверка ключей и подписей Ed25519 (6.1); `issuedMin ∈ [now − FRESH; now + SKEW]`; **отзыв по субъекту:** для каждого из `subjectId` и `actorId`, присутствующего в `removed:<room>` с минутой выхода `m`, сертификат отвергается, если `issuedMin ≤ m` (сертификат субъекта, выданный не позже его выхода, и сертификат, подписанный ушедшим не позже выхода; после возвращения новые сертификаты принимаются).

`vouch(A→X)`:

1. `A` — доверенный участник (`A ∈ V`, `A ≠ X`), присутствует в текущем списке сервера (иначе подписант вышел).
2. `actorKey` равен закреплённому `peer:A.signPub`; у A нет состояния `changed` (ключ изменился и не принят пользователем) и нет `log-mismatch` ([key-transparency.md](key-transparency.md) §7.3): подпись ключа, подмена которого подозревается, не принимается. Участник из `V` с `log-mismatch` остаётся в `V`, но новые допуски от него не принимаются; KT-статус `pending` (ключ ещё ждёт журнала) допуск не блокирует.
3. `sig` проверена по `actorKey`.
4. `subjectSignPub`, `subjectDhPub` равны закреплённым ключам X; если закрепления ещё нет — ключам X, которые сообщает сервер (и они закрепятся). Несовпадение с серверными ключами — отказ и статус «ключ изменился».
5. Если `X = я`: ключи в сертификате равны моим собственным identity-ключам. Иначе сертификат выдан не мне (подмена заявителя) — отказ и предупреждение пользователю.

`revouch(C→X)`: те же условия, что у `vouch` (пп. 1–5, подписавший — `C`), плюс `ref ≠ 0` (исходный допуск; клиент его не проверяет — сертификат удалён вместе с вышедшим подписавшим — и честно показывает «повторно подтверждён»). Снимка нет.

`join(X)`:

1. Сертификат приглашения `I` присутствует (в `aux` или в `rooms.invite_cert`), `SHA-256(I) = ref`, и `I` проходит проверку: **все общие условия, кроме нижней границы свежести** `issuedMin ≥ now − FRESH` (приглашение могло быть выдано 20 суток назад, а вход состояться вчера), — длина и `magic`, `kind`, `roomId`, нули в неиспользуемых полях, `snapN`, строгая проверка Ed25519, `issuedMin ≤ now + SKEW` и **отзыв по субъекту, в том числе `removed` для `I.actorId`** (приглашение, подписанное ушедшим не позже его выхода, отвергается и тянет за собой `join`) — **плюс** пп. 1–3 проверки `invite` ниже. Свежесть самого `join` проверяется по общему условию.
2. `actorKey` в `join` равен `I.ref` (`invitePub`); `sig` проверена этим ключом.
3. `issuedMin(join) ∈ [I.issuedMin − SKEW; I.expiresMin + SKEW]`.
4. Ключи субъекта — как в `vouch`, п. 4–5; `sig2` проверена по `subjectSignPub`.

`invite`:

1. Приглашающий `A ∈ V`, присутствует в списке, `actorKey = peer:A.signPub`; у A нет состояния `changed` и нет `log-mismatch` (как в `vouch`, п. 2); `sig` проверена по `actorKey`. (Для первой проверки новичка условие заменено: 9.2.)
2. `sig2` проверена по `ref` (`invitePub`).
3. `expiresMin − issuedMin ≤ INVITE_MAX`.

## 7. Схема БД и API

### 7.1 Схема (итоговая, R0)

```sql
CREATE TABLE room_member_certs (
  room_id    INTEGER NOT NULL REFERENCES rooms(id) ON DELETE CASCADE,
  subject_id INTEGER NOT NULL,                  -- нет FK: удаляет приложение вместе с аккаунтом/выходом
  actor_id   INTEGER NOT NULL,                  -- для join: 0
  kind       SMALLINT NOT NULL CHECK (kind IN (1, 3, 4)),   -- 1 vouch, 3 join, 4 revouch (invite хранится в rooms)
  cert       BYTEA NOT NULL CHECK (octet_length(cert) IN (271, 335)),
  aux        BYTEA CHECK (aux IS NULL OR octet_length(aux) = 335),   -- join: копия сертификата приглашения
  snap       BYTEA CHECK (snap IS NULL OR (octet_length(snap) % 16 = 0 AND octet_length(snap) <= 16384)),   -- vouch: снимок субъекту
  PRIMARY KEY (room_id, subject_id, actor_id, kind)
);
CREATE INDEX idx_rmc_subject ON room_member_certs (subject_id);
CREATE INDEX idx_rmc_actor   ON room_member_certs (actor_id);
-- rooms: invite_cert BYTEA NULL CHECK (invite_cert IS NULL OR octet_length(invite_cert) = 335),
--        invite_snap BYTEA NULL CHECK (invite_snap IS NULL OR (octet_length(invite_snap) % 16 = 0 AND octet_length(invite_snap) <= 16384)),
--        invite_actor_id INTEGER NULL   -- автор приглашения (без FK): по нему выход автора обнуляет invite_*
```

- Времени нет: минута допуска лежит внутри сертификата. Строки удаляются: когда субъект или подписавший выходит или удаляет аккаунт; при повороте или выключении приглашения (`invite_cert`, `invite_snap`, `invite_actor_id` → NULL; уже сохранённые `join` остаются, у них копия в `aux`); при выходе или удалении аккаунта автора приглашения (то же обнуление, код остаётся и принимает только заявки); при удалении комнаты (каскад).
- Не более 4 допусков (`vouch` и `revouch` вместе) на `(room_id, subject_id)`; не более 1 `join` на субъекта (PK).
- Порядок блокировок — общий, [message-ordering.md](message-ordering.md) §8.1: `users → rooms → room_participants → chats → room_member_certs → user_left_rooms → upload_quota → messages`. Вставка сертификата при вступлении — в той же транзакции `addRoomMember` (после `rooms FOR NO KEY UPDATE`); удаление при выходе и удалении аккаунта — после `chats`, до `user_left_rooms` и `messages` ([sealed-sender.md](sealed-sender.md) §12).
- **Транзакция `member-certs`** (ревью М13): без неё сертификат мог бы вставиться после выхода субъекта или подписавшего и остаться навсегда.

```
BEGIN
  users(я)  FOR KEY SHARE                                           // я = actor = сессия; нет строки → 401
  rooms     FOR NO KEY UPDATE                                       // выход берёт FOR UPDATE: порядок решает блокировка
  SELECT user_id FROM room_participants WHERE room_id = $r AND user_id IN (actor, subject)   // оба обязаны быть, иначе 404 not-participant
  SELECT count(*) FROM room_member_certs WHERE room_id = $r AND subject_id = $s AND kind IN (1, 4)   // не больше 4, иначе 200 stored:false
  INSERT INTO room_member_certs … ON CONFLICT DO NOTHING            // дубль → stored:false
COMMIT
```

- **Транзакции вступления `approve` и `join`** (повторное ревью 13): те же правила блокировок и проверки **после** взятия блокировки комнаты, а не до неё: значения, прочитанные раньше, к моменту блокировки могли устареть.

`approve` (порядок как у вступления в [message-ordering.md](message-ordering.md) §8.2):

```
BEGIN
  users(заявитель) FOR KEY SHARE                                    // как в addRoomMember; подписавший (сессия) отдельной блокировки users не берёт
  rooms            FOR NO KEY UPDATE
  SELECT 1 FROM room_participants WHERE room_id = $r AND user_id = actorId
         // actorId обязан быть участником ПОСЛЕ блокировки комнаты, иначе 404 not-participant: подписавший мог выйти между
         // проверкой подписи и вставкой, и сертификат с несуществующим подписавшим остался бы навсегда (выход удаляет строки только своих)
  заявка существует и не обработана
  addRoomMember(заявитель); INSERT room_member_certs (vouch, snap)
COMMIT
```

`join`:

```
BEGIN
  users(я)  FOR KEY SHARE                                           // я = входящий = сессия
  rooms     FOR NO KEY UPDATE
  читаются rooms.invite_cert, invite_snap, code_expires_at и лимит участников — здесь, под блокировкой, в той же транзакции, что и
         addRoomMember: поворот или выключение приглашения не успеют между проверкой joinCert и вставкой
  проверка joinCert по прочитанным значениям (ref, подписи, время)
  addRoomMember; INSERT room_member_certs (join, aux = invite_cert)
COMMIT
ответ: { …, inviteSnap = прочитанный invite_snap }
```

- Таблица создаётся в `initDatabase`; столбцы `invite_*` — в `CREATE TABLE rooms`.

Есть: `kind = 3`, `ref = SHA-256(rooms.invite_cert)`, подпись `invitePub`, `sig2` по ключу субъекта, `subjectId` — сессия, ключи равны `identity_keys`, `issuedMin ∈ [I.issuedMin − SKEW; I.expiresMin + SKEW]` (границы те же, что у клиента, 6.4) и в `SERVER_WINDOW`; иначе 400 `bad-cert` / `bad-cert-time`. `rooms.invite_cert`, `invite_snap` и `code_expires_at` читаются после `rooms FOR NO KEY UPDATE`, в той же транзакции, что и `addRoomMember` (7.1). **Ответ при успехе содержит `inviteSnap` (base64)** — копию `rooms.invite_snap`: его получает только тот, чей `joinCert` подписан ключом приглашения. Повторный `POST /join` от уже вошедшего с тем же `joinCert` (совпадает с сохранённой строкой `join`) возвращает тот же ответ, пока `rooms.invite_cert` не изменился; иначе 409 `already-member` |
| `DELETE /api/chats/:chatId`, `deleteUserAccount` | удалить сертификаты, где субъект или подписавший — пользователь; если он `invite_actor_id` комнаты — обнулить `invite_cert`, `invite_snap`, `invite_actor_id` |

**Лимит тела запроса.** Для `approve`, `invite/rotate` и `POST member-certs` — **32 КБ**. Снимок на 1000 участников — 16 000 байт, в base64 около 21,3 тыс. символов (максимум для 1024 участников — 21 848), плюс сертификат (до 448 символов) и JSON: общий лимит 20 КБ их не вмещает. Для остальных маршрутов лимит прежний (повторное ревью 10).

Все проверки сервера — защита в глубину против ошибок клиента и случайного мусора; доверия серверу они не добавляют (раздел 3). Все изменяющие запросы несут `proto: 4` (message-ordering.md §14.1). Ошибки возвращают `{ success:false, code, message }` ([message-ordering.md](message-ordering.md) §14). Сертификаты сервер не пересылает через сокет: событие `roomMembersChanged` заставляет клиентов запросить `participants` заново.

## 9. Клиент: алгоритмы

### 9.1 `verifyMembershipLocked` (внутри `ensureRoomSession`)

Сетевые вызовы (`participants`, `identities`) выполняются **до** блокировки; сама сверка идёт в одной секции `withLock`, внутри которой сети нет.

```
вход: S — список сервера (id, имя), S_prev = members:<room> (прежний список), C — сертификаты и invite, K — ключи участников (serverIdentities);
      сертификаты других участников запрашиваются заранее (member-certs?subjects=…, вне блокировки) для S \ V и для X ∈ V, у которых
      подписавший (by) вышел из комнаты (шаг 4а);
      V = trusted:<room>.list, R = removed:<room>
1. Ушедшие: для ВСЕХ X ∈ S_prev \ S, X ≠ я, независимо от членства в V: удалить из V (если там был); R[X] = текущая минута;
   пометить «нужна ротация» (существующая логика removedMembers). Записывать R только для X ∈ V нельзя: неподтверждённый
   ушедший тоже может вернуться с повторённым сертификатом. R[X] ставится и для X, замеченных ушедшими по roomMembersChanged.
2. Закрепление ключей (checkPeersWithServer): статусы unknown/unverified/verified/changed.
3. Отзыв: для X с «ключ изменился и не принят» (changed): из V удалить. Это единственная причина выпадения из V при X ∈ S («отзыв»);
   выход подписавшего V не меняет (5.5, 9.5). Повторно подтвердить можно только после acceptPeerIdentityChange.
3а. Дубликаты ключей (6.2): для каждой группы участников S (кроме меня) с одинаковыми (signPub, dhPub): кто уже в V по id — остаётся
    в V; остальные члены группы («новички с чужими ключами») помечаются и не подтверждаются на шагах 4, 5 и 4а; предупреждение 'duplicate-keys'.
4. Замыкание, пока V растёт:
   для каждого X ∈ S \ V, X ≠ я, не помеченного в 3а: для каждого сертификата c с subjectId = X:
       если validateCert(c, X) (6.4, с учётом R) → V ∪= {X}, how/by/certHash из c; прервать перебор сертификатов для X.
4а. Обновление ссылок на ушедшего подписавшего: для X ∈ V, у которого by ∉ S (подписавший вышел) и how ∈ {approved, invite, vouched, revouched}:
    если есть действительный допуск (vouch или revouch, 6.4) от текущего участника из V — how/by/certHash у X обновляются
    (how = 'vouched' или 'revouched', by — новый подписавший). Иначе X остаётся в V со старой записью, а повторный допуск ставится в очередь (9.5).
5. Якорная проверка новичка (9.2) — только при выполнении ВСЕХ условий 9.2; иначе шаг пропускается.
6. unconfirmed = S \ V \ {я}.
7. Правило ротации (ниже).
8. Результат: members[], unconfirmed[], duplicateKeys[], viewMismatch (после обработки key-share, 9.6).
```

**Правило ротации (повторное ревью 1; общее с [key-transparency.md](key-transparency.md) §7.3).**

- **Адресаты.** `recipients = (V ∩ S) \ {я}` без участников с `log-mismatch`, парами `{ id, memkey(id, закреплённые ключи участника) }`. Участник в состоянии `changed` уже выпал из `V` (шаг 3); `duplicate-keys` из `V` не исключает; KT-статус `pending` (ключ ещё не подтверждён журналом) ни из `V`, ни из рассылки не исключает ([key-transparency.md](key-transparency.md) §7.3).
- **Журнал доставок** `delivered:<room>:<senderKeyId>` — пары `{ id, memkey }` тех, кому текущий ключ отправлялся. Запись добавляется в `prepareShareForPeer` в той же секции `withLock`, где готовится key-share, **до** сетевого вызова: если запрос ушёл, а ответ потерян или вкладка закрылась, ключ мог дойти, и журнал это учитывает. Журнал ведётся **только на добавление**: отметки рассылки `sharedWith2`, которые стирают `answerKeyRequests` (сервер может вызвать их запросом ключа) и `acceptPeerIdentityChange`, в него не входят и решения о ротации не определяют; они нужны только для переотправки.
- **Правило.** Если в журнале текущего ключа есть пара `{ id, memkey }`, которой нет среди текущих `recipients` с тем же `id` и тем же `memkey`, — ключ **ротируется до рассылки**, и новый ключ получают только текущие адресаты. Пара выпадает, если участник вышел из `S` (причина `member-left`), выпал из `V` (`changed`), получил `log-mismatch` или **сменил ключи** (тот же `id`, другой `memkey`: прежний ключ ушёл по старым identity-ключам, которые участник мог потерять или которыми владеет посторонний). Ротация, которой нет причины в журнале (получатель выбыл, а ключ ему не отправляли), не нужна.
- **Уровень человека и уровень комнаты.** События, относящиеся к человеку (`changed`, `log-mismatch`, принятие нового ключа), запускают проверку правила **во всех общих комнатах** (список — `members:<room>`; проверка локальная, без сети). Выход из одной комнаты ротирует ключ только этой комнаты.
- **Новый ключ.** Его `entitled` — `recipients` (пары) на момент создания (9.4); журнал нового ключа пуст; журнал и отметки старого удаляются при ротации. Иначе получивший ключ раньше продолжал бы читать новые сообщения.
- **Существующий порядок.** Причина ротации `member-left` и порядок «ротация до рассылки» не меняются; сравнение с `members:<room>` как единственное основание ротации заменено проверкой по журналу.

Сложность: одна проверка сертификата — одна-две проверки подписи; число сертификатов на участника ограничено 4 допусками и одним `join`. Замыкание останавливается за не более чем `|S|` проходов.

### 9.2 Первоначальное доверенное множество новичка

**Когда выполняется (ревью М1, блокер).** Якорная проверка запускается только если выполняются **все** условия:

1. на устройстве есть `joinIntent:<room>` (создан действием пользователя: «Войти по ссылке» или «Отправить заявку») и не истёк;
2. `trusted:<room>.bootstrapDone` не записан (для комнаты ещё ни разу не записывалось `V`);
3. `V = {я}`;
4. на сервере есть сертификат с `subjectId = я`, **вид которого определён способом входа** (`joinIntent.via`, повторное ревью 3):
   - `via: 'request'` — только `vouch` (`kind = 1`); `join` и `revouch` не годятся;
   - `via: 'invite'` — только `join`, у которого `ref` равен `joinIntent.inviteHash` (хэшу приглашения, проверенного секретом ссылки при входе, 5.3); явный `vouch` или `revouch` для меня не годятся, даже действительные: иначе явный допуск «своего» участника подменил бы сильный якорь (секрет ссылки) слабым (ключ, который сообщает сервер). Материал (`inviteHash`, `inviteSnap`, `joinCert`) берётся из `joinIntent`, а не из памяти страницы.

**Никогда** она не выполняется: для создателя комнаты (у него `bootstrapDone` записан при создании, `joinIntent` не создаётся); если `V` комнаты уже записывался (`bootstrapDone`); без `joinIntent` — в том числе при сертификате «для меня», подсунутом сервером. Иначе сервер, показав создателю или участнику, от которого скрыл остальных, сертификат от «своей» учётной записи, получал бы в `V` этого человека (и его снимок) без участия пользователя.

Запись `V` и расход намерения — в **одной секции `withLock`**: сначала пишется `trusted:<room>` с `bootstrapDone: true`, затем удаляется `joinIntent:<room>`. Падение между шагами оставляет оба признака, и `bootstrapDone` запрещает повтор. Если сертификат не прошёл проверку, `V` не пишется, намерение не расходуется, пользователь видит причину.

**Пока `joinIntent` жив, `trusted:<room>` и `bootstrapDone` не пишет никто, кроме самой якорной проверки** (повторное ревью 4). Обычный `ensureRoomSession` в это время держит `V = {я}` в памяти (все остальные неподтверждены, замыкание по сертификатам ничего не добавит: подписавшего в `V` нет), но в хранилище `V` не записывает: иначе первая же запись `V = {я}` с `bootstrapDone: true` навсегда отключила бы якорь, если вкладка перезагрузилась между входом и проверкой. Намерение заканчивается одним из способов: расход якорной проверкой; истечение (30 суток); собственный выход из комнаты (5.6); отказ сервера (заявка отклонена, `join` вернул ошибку); ручное подтверждение участника (9.7; пользователь отказывается от якоря, намерение отменяется, `V` пишется вместе с `bootstrapDone`).

- **По одобрению** (`via: 'request'`). Берётся `vouch` с `subjectId = я`: `actorId = A`, `A ∈ S`. Условия пп. 2–5 из 6.4, но п. 1 заменён: якорем служит ключ A, который сообщает сервер (TOFU), он закрепляется. Если ключи субъекта в сертификате не равны моим собственным, сертификат отвергается (подмена заявителя), пользователь предупреждён. Снимок берётся из `snaps` ответа `participants` (адресован мне), проверяется `snapN` и `snapHash`. Дальше `V = {я, A} ∪ { X ∈ S : memkey(X.id, ключи X, закреплённые или от сервера) ∈ snap }` (`how = vouched`, `by = A`; сам A — `how = approved`, `by = A`); правило дубликатов 6.2 применяется после.
- **По ссылке** (`via: 'invite'`). Якорем служит ключ приглашения, выведенный из секрета (внешняя точка опоры): секрет проверил приглашение при входе (5.3), в `joinIntent` остался его хэш `inviteHash`. Берётся `join` с `subjectId = я` и `ref = inviteHash`; сертификат приглашения `I` — его копия `aux`, `SHA-256(aux) = inviteHash`. Секрет после входа не нужен. Условие 1 проверки `invite` (6.4) для новичка заменено: приглашающий A ещё не закреплён, поэтому `I` принимается, если подписи `sig` (по `actorKey` из сертификата) и `sig2` (по `I.ref`, который при входе был сверен с `invitePub`, выведенным из секрета) действительны, A есть в списке сервера и ключ A, который сообщает сервер, равен `actorKey` (иначе — подмена приглашающего, отказ и предупреждение). Остальные проверки `join` (6.4, пп. 2–4) и общие условия для `I` — как при обычной проверке. Снимок `joinIntent.inviteSnap` (из ответа `POST /join`, 5.3) проверяется по `snapHash` сертификата. После успешной проверки ключ A закрепляется как `peer:A`, и `V = {я, A} ∪ { X ∈ S : memkey(X.id, ключи X) ∈ snap(invite) }`. `how = invite`, `by = A`. Подмена ключа любого X из снимка сервером невозможна: потребовался бы второй прообраз `memkey`. Подмена самого A невозможна: сертификат подписан его ключом и ключом приглашения, выведенным из секрета, которого сервер не знает.

В снимок A попадают только участники его `V` с `how ≠ manual` (или `vouchedByMe`), так что доверие, принятое A вручную, новичку не передаётся (ревью М4).

Bootstrap выполняется один раз на комнату. Его материал (`inviteHash`, `inviteSnap`, `joinCert`) хранится в `joinIntent` и переживает перезагрузку страницы; `membership.bootstrap`, переданный в `ensureRoomSession` сразу после входа, — только ускорение. После расхода намерения bootstrap берётся из сохранённого `trusted:<room>`, секрет не нужен. Потеря локальных данных (очистка хранилища при живой сессии) возвращает комнату в состояние без `V`: якорной проверки нет (нет `joinIntent`), все участники «не подтверждены», восстановить доверие можно ручным подтверждением либо повторным входом (новая заявка или ссылка создаёт новый `joinIntent`).

**Возраст снимка.** Снимок приглашения живёт до `INVITE_MAX` (720 ч) и в якорной проверке принимается без дополнительного ограничения возраста. Бывший участник, вышедший после выдачи приглашения и возвращённый сервером без сертификата, подтверждается вошедшими по этой ссылке (у них нет `removed`); предел записан в разделе 3 и разделе 12, строка 30, вопрос 17.

### 9.3 Приглашающий: создание и показ ссылки

`client.signInvite(roomId, { ttlSeconds })` создаёт `s`, сертификат и снимок и возвращает `{ cert, snap, secret }`; в хранилище кладётся `inviteSecret:<room> = { s, certHash }`. Секрет:

- не отправляется на сервер ни в каком виде (в запросе только сертификат и снимок);
- сохраняется на устройстве, которое повернуло приглашение (чтобы показать ссылку позже), вместе с `certHash`. **Ссылку показывают только если `certHash` равен `SHA-256(participants.invite)`**, то есть сертификат на сервере тот же, что был при создании ссылки. Иначе (приглашение повернул другой участник, выключено, подменено) показ ссылки скрыт, а секрет удаляется: мёртвая или подставленная ссылка не показывается как рабочая (ревью М14);
- другим участникам не передаётся: чужая «Показать ссылку» выдаёт **код без секрета** (он даёт заявку). Чтобы выдать ссылку с секретом, участник поворачивает приглашение сам (старая ссылка перестаёт действовать, как и сейчас). Вопрос 5 раздела 17;
- удаляется с устройства при выходе, при повороте и выключении приглашения, при ответе сервера `invite: null` и вместе с историей комнаты;
- не пишется в логи, `localStorage`, адресную строку и в аналитику; в памяти — на время показа.

### 9.4 Отправка ключа комнаты

`prepareShareForPeer` вызывается только для адресатов — `recipients` из 9.1 (подтверждённые `V ∩ S`, без `log-mismatch`; участник в состоянии `changed` уже не в `V`); остальные возвращаются в `unconfirmed` без запроса bundle и без отметки `sharedWith2`. `log-mismatch` ([key-transparency.md](key-transparency.md) §7.3) не исключает участника из `V`, а только из рассылки; KT-статус `pending` не исключает ни из `V`, ни из рассылки. `overrideLogMismatch` возвращает его в адресаты: текущий ключ он получает как новичок, с текущей итерации, а право на ключ с начала эпохи появляется со следующей ротации (`entitled`, ниже). В SKDM кладётся `ext.view` (6.3). Когда участник становится подтверждённым, следующий `ensureRoomSession` отправляет ему ключ. Если ключ не дошёл ни до одного участника, а другие есть, отправка блокируется, как в 5.8.

**Журнал доставок (повторное ревью 1).** `prepareShareForPeer` в той же секции `withLock`, где готовит key-share, и до сетевого вызова добавляет в `delivered:<room>:<senderKeyId>` пару `{ id, memkey }`, где `memkey` посчитан по закреплённым ключам получателя, по которым шифруется share. Запись не снимается ни при ошибке сети, ни при `answerKeyRequests`, ни при `acceptPeerIdentityChange`; по ней правило ротации (9.1) узнаёт, кто мог получить ключ. `answerKeyRequests` отвечает на запрос ключа **только текущим `recipients`** (сейчас — любому из `members:<room>`, то есть списку сервера `S`): запрос от неподтверждённого, от участника с `log-mismatch` или от того, кого нет в списке, не снимает отметку рассылки и не расходует кулдаун; переотправку получает только адресат. Даже если сервер вызовет запрос ключа от постороннего, на ротацию это не влияет: она определяется журналом, а не отметками.

**Кто получает ключ с начала эпохи (`entitled`, ревью М9, повторное ревью 1).** При создании нового ключа комнаты множество `entitled` (получатели ключа с начала эпохи) равно `recipients` **на момент создания ключа**, парами `{ id, memkey }`, а не `V` и не составу `S`. Не `V`: в `V` остаётся участник с `log-mismatch`, и он получил бы весь ключ с начала эпохи. Пара, а не id: `prepareShareForPeer` выдаёт ключ с начала эпохи, только если пара `{ id, memkey }` получателя совпадает с записью в `entitled`; участник, сменивший ключи, и участник, подтверждённый позже (призрак, которого пользователь потом принял), получают ключ как новички — с текущей итерации — и не читают уже отправленные сообщения эпохи. В коде это правка `knownMemberIdsLocked` (сейчас возвращает весь список `members:<room>`) и `rotateRoomKeyLocked` / `ensureRoomSession` (сейчас `entitledNow` — все, кроме меня).

**`unverifiedSender`.** Входящий SKDM от неподтверждённого отправителя принимается (индекс отправителей [sealed-sender.md](sealed-sender.md) §9.2 пополняется), но результат расшифровки его сообщений несёт `unverifiedSender: true`; интерфейс помечает такие сообщения. Флаг **вычисляется при каждой расшифровке по текущему `V`**, а не хранится в индексе: после подтверждения участника пометка исчезает без перешифровки, после выпадения из `V` — появляется.

### 9.5 Повторный допуск и явное поручительство

**Повторный допуск (автоматически).** Срабатывает, когда в `V` есть X с `by = ушедший` (подписавшего больше нет в `S`; обычно это `removedMembers` текущего `ensureRoomSession`) и `how ∈ {approved, invite, vouched, revouched}`; X всё ещё в `S`, а шаг 4а (9.1) не нашёл для него допуска от текущего участника. Клиент C не подписывает сразу, а кладёт задачи `{ x, orig, due }` в `revouch:<room>` (не больше 50 за проход; остальные — при следующем `ensureRoomSession`). `orig` — `certHash` исходного допуска X из записи `trusted` (для подтверждённого по снимку — сертификат, давший снимок: у X отдельного допуска не было, 5.5). `due = сейчас + min(rank, 30) × 2 минуты`, `rank` (от 0) — позиция C в списке `S \ {X, A}`, упорядоченном по возрастанию `SHA-256("nyxo-revouch-v1" ‖ u32be(X) ‖ u32be(id))`: клиент не знает чужого локального `V`, поэтому ранг считается по списку сервера, а не по «участникам `V`, у которых X тоже с `by = A`». Когда срок наступил (проверка при `ensureRoomSession` и по таймеру открытой вкладки):

```
1. перечитать сертификаты X (GET member-certs?subjects=X) — вне withLock;
2. если для X есть действительный допуск (vouch или revouch, 6.4) от текущего участника из V — снять задачу и в короткой секции
   withLock обновить у себя запись X в V: how ('vouched' или 'revouched'), by (подписавший найденного допуска), certHash (иначе запись
   держала бы ушедшего подписавшего, и задача ставилась бы заново при каждом ensureRoomSession; то же делает шаг 4а в 9.1);
3. иначе подписать revouch(C→X, ref = orig, снимка нет), POST member-certs { subjectId, cert };
   в короткой секции withLock: certHash у C для X — новый, how = 'revouched', by = C, задача снята.
```

Это сдерживает «лавину»: без очереди и задержки каждый из N участников подписывал бы по допуску на каждого из M участников ушедшего (N·M запросов при лимите 4 допусков на субъекта). Повторный допуск **не новая проверка**, а перенос уже принятого доверия, поэтому он отдельного вида и в интерфейсе подписан честно (раздел 10). Для X, подтверждённого C только вручную (`how = manual`), автоматического допуска нет.

**Явное поручительство.** `client.vouchForMember(roomId, userId)` — действие пользователя «Поручиться за участника» (в окне участников у каждого участника из `V`, особенно подтверждённого вручную). Подписывается обычный `vouch(C→X)` со снимком `V_C` без ручных, отправляется `POST member-certs`. После успеха у C для X ставится `vouchedByMe: true`: с этого момента X входит в снимки, которые C подписывает. До явного действия доверие, принятое вручную, остаётся локальным.

### 9.6 Сверка взглядов

Сеть внутри `withLock` запрещена (ревью М8). Когда SKDM применён (`applyShare`) и в нём есть `ext.view`, **в блокировке** только записывается задача в `viewPending:<room>` (раздел 8): `{ sender, view, at }`. Дальше `runViewChecks()` **вне блокировки**:

```
mine = view(S, закреплённые ключи)        (6.3); для участника в состоянии changed берётся ПРЕЖНИЙ закреплённый ключ, а не новый ключ сервера;
                                          для ещё не закреплённого участника с ключами на сервере — серверные ключи (6.3, случай 2)
если view.ids ≠ mine.ids:
    viewDiv:<room>:<sender> = { count + 1, since (если не было) }
    если count ≥ 3 подряд или now − since > 24 часа → мягкое уведомление 'view-ids-diverged' (не чаще раза в сутки на пару):
       «Состав группы у {имя} отличается от вашего. Возможно, сервер показывает участникам разные списки»; отправка не блокируется
    выйти (список сервера у сторон разный: идут изменения; сверка ключей при разных ids бессмысленна)
    // проверка счётчика стоит ДО выхода: иначе после «выйти» уведомление недостижимо и расхождение ids отключало бы сверку без следа
иначе viewDiv сбросить;
    если view.keys = mine.keys → ничего
    иначе:
      checkPeersWithServer (сеть, вне блокировки);
      короткая секция withLock: если у любого участника status = changed → подавить (расхождение объясняется сменой ключа, уже показанной
      пользователю); иначе → поднять 'view-mismatch' (не чаще раза в сутки на пару комната–отправитель).
```

Без счётчика расхождения `ids` вечное «ids не равны» отключало бы сверку ключей без следа: сервер или участник мог бы держать свой список разным навсегда. Интерфейс `view-mismatch`: «Участники группы видят разные ключи шифрования (возможна подмена сервером). Сверьте коды безопасности». Тревога информативная: отправка не блокируется (SKDM уже принят по аутентифицированному каналу). Оговорка из раздела 3 действует: `view` защищает при настоящих закреплённых ключах, не от MITM при первом контакте.

### 9.7 Ручное подтверждение

`client.trustMember(roomId, userId)`: добавить в `V` с `how = manual`, `by = null`; сертификат не публикуется, в снимки (приглашение, допуск) участник **не входит**, пока пользователь явно не поручится (9.5). Предусловие: ключи участника закреплены и не в состоянии `changed`. `acceptPeerIdentityChange(peerId)` для участника из `S` дополнительно подтверждает его вручную (решение человека о новом ключе). Подтверждение не отменяется, пока участник состоит в комнате с теми же ключами: ни клон с такими же ключами (правило дубликатов оставляет подтверждённого в `V`, 6.2), ни сервер этого не отменят. Если на устройстве есть живой `joinIntent` комнаты, ручное подтверждение отменяет намерение (9.2): пользователь отказывается от якорной проверки, интерфейс предупреждает об этом.

## 12. Граничные случаи и атаки

| № | Ситуация | Исход |
|---|---|---|
| 1 | Сервер подставляет «заявителя» с чужими ключами | одобряющий видит код безопасности и решает; одобрив, подписывает за чужие ключи. Новичок увидит несовпадение ключей субъекта со своими (6.4 п. 5) и откажется. Предел Н3 |
| 2 | Призрак: сервер добавил учётную запись в `room_participants` | сертификата нет, ключ не отправляется, статус «не подтверждён», баннер |
| 3 | Сервер скрывает сертификат у участника B | X для B «не подтверждён»; ключ не отправляется, пока пользователь не нажмёт «Доверять» или сертификат не появится |
| 4 | Повтор сертификата после выхода субъекта | отвергается у видевших выход: в `removed:<room>` минута выхода субъекта, сертификаты не новее её отвергаются (в том числе с другим хэшем и ранее неизвестные); остальные принимают в пределах 30 суток |
| 5 | Подписавший вышел | его сертификаты удалены сервером; клиенты не принимают сертификаты ушедшего не новее его выхода; оставшиеся подписывают повторный допуск (9.5) |
| 6 | Несколько одобрений одной заявки | первый коммит выигрывает под блокировкой комнаты; второй получает «Заявка не найдена»; допусков на субъекта не больше 4 |
| 7 | Участник сменил identity-ключ | ключи в сертификате не совпадают с серверными: `unconfirmed` и «ключ изменился»; после `acceptPeerIdentityChange` участник подтверждён вручную |
| 8 | Утечка ссылки | входит любой, у кого она есть, до поворота; новый вход видят все (лента, имя пригласившего); поворот отзывает **при честном сервере** |
| 9 | Ссылка после поворота | честный сервер: код другой → 400; `invite_cert` другой → `bad-cert`. **Недобросовестный сервер** вправе принять `join` по старой паре «сертификат приглашения + секрет»: клиенты примут и такой `join` (старый сертификат приглашения подписан и не истёк). Отзыв поворотом не криптографический (раздел 3) |
| 10 | Код без секрета в комнате без одобрения | заявка. Ссылка с секретом в комнате с одобрением — тоже заявка |
| 11 | Срок приглашения истёк | предпросмотр отдаёт `null`; join с просроченным `I` отвергается и сервером, и клиентами |
| 12 | Часы подписавшего спешат более чем на 10 минут | сертификат у других «из будущего»: не принимается до наступления времени; клиент повторяет сверку при следующем `ensureRoomSession`. Сервер отвечает 400 `bad-cert-time`, если `issuedMin` вне ±10 минут от его времени: клиент с часами, отставшими больше чем на 10 минут, не может публиковать сертификаты, пока не поправит время. Часы, сбитые на 3–10 минут, допустимы: `invite/rotate` сверяет длительность срока, а не абсолютное время, а `join.issuedMin` проверяется с запасом `SKEW` в обе стороны (6.4, 7.2) |
| 13 | Комната из 1000 участников | снимок 16 КБ хранится и отдаётся только адресату; сертификат 271–335 байт; ответ `participants` содержит список и только сертификаты самого запрашивающего (десятки килобайт); сертификаты других — `member-certs?subjects=` по не более 200 id, не более ≈ 0,47 МБ за запрос и только для `S \ V` (со всеми сертификатами ответ был бы ≈ 2,3 МБ); тело запроса `approve`/`rotate`/`member-certs` — лимит 32 КБ (снимок 16 000 байт ≈ 21,3 тыс. символов base64 + сертификат + JSON; 20 КБ не хватало) |
| 14 | Сервер скрывает выход участника | клиент продолжает отправлять ему ключи (Н2) |
| 15 | Участник выходит и возвращается | новый допуск (`issuedMin` позже выхода); старые сертификаты удалены сервером и отвергаются клиентами по `removed` |
| 16 | Расхождение `ext.view.ids` | сверка ключей пропускается; повторится при следующем SKDM; три подряд или более суток расхождения — мягкое уведомление (9.6) |
| 17 | Сервер подменяет `ext.view` | при настоящих закреплённых ключах невозможно (AEAD key-share); при подмене ключа до первого закрепления сервер терминирует канал и может писать любой `ext.view` (раздел 3) |
| 18 | Оба `ids` и `keys` совпали у лжеца и у жертвы | атака раздвоения, где сервер даёт жертве и честным участникам одинаковые ключи подмены, не видна; нужны коды безопасности |
| 19 | Одновременный вход двух людей по ссылке | `addRoomMember` сериализует вступления; `V` у каждого ведёт своё замыкание |
| 20 | Сертификат вставлен, вступление откатилось | сертификат и вступление — одна транзакция |
| 21 | **Сервер показывает создателю комнаты сертификат «для него» от своей учётной записи** | у создателя `bootstrapDone`, `joinIntent` нет: якорной проверки нет, учётная запись остаётся «не подтверждена» (тест М1) |
| 22 | **Сервер скрывает от участника P остальных и показывает один «подтверждённый» сертификат** | у P уже записан `V` (`bootstrapDone`): якорная проверка не запускается; новый участник проходит только замыкание по сертификатам подписантов из `V` (тест М1) |
| 23 | Сервер заводит клон X (те же identity-ключи, другой id) | `memkey` клона отличается и в снимке не значится; клон — новичок с чужими ключами, остаётся неподтверждённым; X, уже стоящий в `V`, там остаётся (предупреждение `duplicate-keys`, ротации нет). Если X ещё не в `V`, не подтверждается ни X, ни клон, пока решает человек (6.2) |
| 24 | Подписавший вышел, остальные N участников одновременно подписывают повторный допуск | очередь `revouch` с задержкой `min(rank, 30) × 2 мин` (ранг по хэшу `X ‖ C` среди `S \ {X, A}`) и перечитыванием сертификатов перед подписью: первый подписывает, остальные снимают задачи и обновляют `how`/`by`/`certHash` у себя |
| 25 | Вышел автор приглашения | `invite_cert`, `invite_snap`, `invite_actor_id` обнулены; код принимает только заявки; устройство автора удаляет секрет |
| 26 | Очистка локальных данных при живой сессии | `V` и `bootstrapDone` утрачены, `joinIntent` нет: все участники «не подтверждены»; восстановление — ручное подтверждение либо повторный вход (9.2) |
| 27 | Сертификат с ненулевым неиспользуемым полем, ключ малого порядка (в том числе `01 00…00 80`: `x = 0` при бите знака 1), `S ≥ L` | отвергается клиентом и сервером (6.1, два отрицательных вектора) |
| 28 | Гонка: вставка сертификата и выход субъекта или подписавшего | транзакция `member-certs` (7.1) сериализуется блокировкой `rooms`: второй видит отсутствие участника и получает 404 |
| 29 | Предпросмотр по коду | отдаёт сертификат приглашения (id и ключ пригласившего, `snapN`, `snapHash`) любому, у кого есть код; снимок по коду не отдаётся, он приходит в ответе на `POST /join` (раздел 3) |
| 30 | Бывший участник P вышел после выдачи приглашения, сервер вернул его в комнату без сертификата | видевшие выход не подтверждают P (`removed`); **вошедшие по этой ссылке после выхода P `removed` не имеют и подтверждают P по снимку** (до 720 ч). Предел принят (раздел 3, вопрос 17); лечится поворотом ссылки после ухода участника |
| 31 | Участник вышел из комнаты и вернулся | локальные `trusted`, `removed`, `revouch`, `bootstrapDone` стёрты (5.6): вход заново с `joinIntent` и якорем. Предел: вернувшийся не помнит, кто вышел за время отсутствия, и принимает повтор старого допуска такого человека (в пределах 30 суток) |
| 32 | Сервер вызывает запрос ключа от постороннего или участник принимает новый ключ собеседника (отметки `sharedWith2` стираются) | на ротацию не влияет: решение по журналу доставок `{id, memkey}`; постороннему (не из `recipients`) ключ не переотправляется; смена ключей получателя (`memkey` другой) ротирует ключ (9.1) |
| 33 | Потеря ответа на `POST /join` | `joinIntent` остаётся без `inviteSnap`; повторный `POST /join` тем же `joinCert` возвращает тот же ответ, пока приглашение не повернули; иначе якорная проверка невозможна, участники неподтверждены (вопрос 18) |
| 34 | Сервер подсовывает вошедшему по ссылке явный `vouch` вместо `join` | для `via: 'invite'` годится только `join` с `ref = inviteHash`: `vouch` игнорируется, якорь не подменяется (9.2) |

## 13. Тесты

### Протокольные (`test/membership.protocol.test.js`, `fake-server` с сертификатами и злонамеренными методами)

- Призрак без сертификата: попадает в `unconfirmed`, ключ не отправлен, сообщения призрака помечены `unverifiedSender`; чтение призраком запрещено (ключа у него нет).
- `vouch` от доверенного: участник подтверждён, ключ отправлен; `vouch` от недоверенного — нет.
- **Якорь (М1, блокер):** (а) создатель комнаты; сервер возвращает сертификат допуска с `subjectId = создатель`, подписанный «призраком» со снимком, — призрак и участники снимка остаются `unconfirmed`, `V = {я}`; (б) участник с записанным `V`, у которого сервер скрыл остальных и показал один сертификат «для него» — якорная проверка не запускается; (в) без `joinIntent` при `V = {я}` и подсунутом сертификате — не запускается; (г) с `joinIntent` и верным сертификатом (по одобрению, по ссылке) — запускается, расходует намерение в той же секции `withLock`, повторный вызов безвреден (`bootstrapDone`); (д) падение между записью `V` и расходом намерения — повтор запрещён `bootstrapDone`; (е) **вид сертификата по способу входа (повторное ревью 3):** при `via: 'invite'` явный `vouch` или `revouch` для меня игнорируется и `V` не пишется, `join` с `ref`, не равным `inviteHash`, отвергается; при `via: 'request'` игнорируются `join` и `revouch`; (ж) **материал bootstrap (повторное ревью 4):** перезагрузка страницы между входом по ссылке и первой проверкой — `joinIntent` с `inviteHash` и `inviteSnap` сохранился, проверка проходит без секрета; обычный `ensureRoomSession` при живом `joinIntent` не пишет `trusted:<room>` и `bootstrapDone`; ручное подтверждение при живом `joinIntent` отменяет его; (з) собственный выход стирает `trusted`, `removed`, `revouch`, `bootstrapDone`, `joinIntent` комнаты, повторный вход снова идёт с якорем.
- **Снимок (М4, М5):** `snapHash` в сертификате совпадает с хэшем снимка, полученного отдельно; подменённый снимок отвергается; ручной участник не попадает в подписываемый снимок, после `vouchForMember` попадает; `ensureRoomSession` у новичка не видит чужие снимки.
- **memkey и дубликаты (М2, повторное ревью 5):** клон-призрак с теми же ключами, но другим id не подтверждается снимком; сервер добавляет клон ключей участника X, который уже в `V` (в том числе подтверждённого вручную), — X остаётся в `V`, остаётся получателем ключа, ротации нет, предупреждение `duplicate-keys`; клон (новичок с чужими ключами) `unconfirmed`; если X и клон оба вне `V`, не подтверждён ни один.
- **Отзыв (М3):** `removed` ставится для **каждого** ушедшего из прежнего `S`, в том числе неподтверждённого (9.1, п. 1); сертификат субъекта после его выхода отвергается, даже с другим хэшем (новый nonce, `issuedMin` не позже выхода); сертификат, подписанный ушедшим не позже выхода, отвергается; после возвращения сертификат с `issuedMin` позже выхода принимается; записи старше 30 суток исчезают, предел 5000.
- Подмена ключей субъекта в сертификате; подмена серверных ключей; сертификат другой комнаты; сертификат другого вида (подпись `join` как `vouch`); обрезанные и удлинённые сертификаты (другая длина вида); ненулевые неиспользуемые поля; `snapN` ноль у `vouch`, `snapN` больше 1024.
- **Ed25519 (М11, повторное ревью 2):** ключ малого порядка (восемь канонических кодировок порядка 1, 2, 4, 8 из 6.6), `y ≥ p`, **`x = 0` при бите знака 1 (`01 00…00 80` и `ec ff…ff ff`)**, `S ≥ L` — отказ на клиенте и в `lib/membership-certs.js`; оба отрицательных вектора 6.6 принимаются платформенным `verify`, но отвергаются явной проверкой; настоящие ключи A и J из 6.6 и случайные пары проходят. Пункты 1 и 2 проверки (6.1) тестируются по отдельности: декодирование с отказом при `x = 0` и бите знака 1 и проверка `[8]P ≠ O` — отдельными функциями, чтобы отказ одной не маскировал отсутствие другой.
- **Повторный допуск (М6, повторное ревью 8):** после ухода одобрившего оставшиеся ставят задачи в `revouch:<room>` (не больше 50), задержка `min(rank, 30) × 2 мин`, где `rank` — позиция в `S \ {X, A}` по `SHA-256("nyxo-revouch-v1" ‖ X ‖ C)` (результат не зависит от чужого локального `V`; для разных X первыми идут разные участники), перед подписью сертификаты X перечитываются и при наличии допуска от другого участника задача снимается **и у себя обновляются `how`/`by`/`certHash`** (повторных задач после этого нет); в итоге на субъекта не больше 4 допусков; `how = revouched`; `orig` для подтверждённого по снимку — `certHash` сертификата, давшего снимок (`ref ≠ 0`); для `manual` автоматического допуска нет; очередь переживает перезагрузку.
- Сертификат вышедшего: отвергается; повтор после выхода: отвергается по `removed`, принимается без записи только пока свеж (30 суток); пограничные значения свежести (±10 минут, 30 суток); вложенный `I` в `join` проходит все общие условия, кроме нижней границы свежести (длина, `magic`, нули, `snapN`, строгая Ed25519, `issuedMin ≤ now + SKEW`, **`removed` для `I.actorId`**) и пп. 1–3 проверки `invite`, а сам `join` — и нижнюю границу тоже (повторное ревью 9); `join.issuedMin` на границах `I.issuedMin − SKEW` и `I.expiresMin + SKEW` принимается, за ними — нет (повторное ревью 11).
- Вход по ссылке: валидный; без секрета — заявка; ссылка с секретом в комнату с одобрением — заявка; подменённый `invitePub`; приглашение другой комнаты; просроченное; срок больше 720 ч отвергается; секрет не нормализуется (регистр); `inviteSecret` с `certHash`: ссылка не показывается, если сертификат на сервере другой, секрет удаляется при выходе, повороте, `invite: null`.
- Bootstrap: по снимку новичок исключает участника с подменённым ключом; подмена ключа самого A невозможна.
- Смена identity: участник неподтверждён до нового допуска или `acceptPeerIdentityChange`.
- **Подписавший в `changed` или `log-mismatch` (повторное ревью 6):** `vouch`, `revouch` и `invite` от такого участника не принимаются, его прежние подтверждённые остаются в `V`; KT-статус `pending` подписавшего допуск не блокирует и из рассылки не исключает.
- Явное поручительство: `vouchForMember` публикует `vouch`; ручное подтверждение само по себе не публикуется.
- **Ротация (повторное ревью 1):** получатель текущего ключа перестаёт быть адресатом (вышел, `changed`, `log-mismatch`, сменил ключи) — ключ ротируется до рассылки по журналу доставок `{id, memkey}`, в общих комнатах тоже; **стирание отметок `sharedWith2` (`answerKeyRequests`, `acceptPeerIdentityChange`, в том числе запрос ключа, вызванный сервером) ротацию не отключает**; запрос ключа от постороннего не снимает отметку и не расходует кулдаун; запись в журнале делается до сетевого вызова (обрыв после отправки не теряет её); журнал только растёт; смена ключей получателя (`memkey` другой при том же `id`) ротирует; `entitled` нового ключа равен `recipients` (пары) на момент создания: участник, подтверждённый позже, участник с `log-mismatch` и участник, сменивший ключи, не получают ключ с начала эпохи; существующий тест «удаление → ротация» проходит без изменений.
- **`ext` и `view`:** испорченное `ext.view` или `ext.kt` отбрасывается с предупреждением, SKDM принят; испорченный `prev` отвергает SKDM; размер 2048 символов; расхождение при равных `ids` даёт тревогу; при разных `ids` — нет, но три подряд или сутки дают мягкое уведомление; при `changed` — подавляется; для `changed` берётся прежний закреплённый ключ, для ещё не закреплённого участника с ключами на сервере — серверные (6.3); уведомление `view-ids-diverged` достижимо (счётчик проверяется до выхода); `viewPending` — одна запись на отправителя, не больше 100; сеть в `withLock` не вызывается (инструментированный `fetch`); сервер не может подменить `view` при закреплённых ключах (искажение SKDM отвергается AEAD).
- `unverifiedSender` вычисляется при расшифровке и исчезает после подтверждения участника.
- Контрольные векторы раздела 6.6.
- Существующий тест «удаление → ротация» проходит без изменений; секрет ссылки не встречается ни в одном исходящем запросе fake-сервера.

### Серверные (`makeFakeApp`, `makeFakeDb`) и сквозные (Postgres)

- `approve` без сертификата — 400 `cert-required`, без снимка — `snap-required`; сертификат не от сессии, не для заявителя, с чужими ключами, чужой комнаты, `issuedMin` вне ±10 минут (`bad-cert-time`), неверный `snapHash` — отказ. **Гонка «выход подписавшего + `approve`» (повторное ревью 13):** участие `actorId` проверяется после `rooms FOR NO KEY UPDATE`; в обоих порядках двух соединений таблица сертификатов не содержит строки с несуществующим подписавшим.
- `join` без `joinCert` — заявка, даже при `requireApproval = false`; с неверной подписью, `ref`, чужим субъектом — `bad-cert`; в комнату без `invite_cert` — заявка. **Гонка «поворот приглашения + `join`»:** `rooms.invite_cert` читается под `rooms FOR NO KEY UPDATE`, `join` по уже повёрнутому сертификату не проходит. `join` на границах `I.issuedMin − SKEW` и `I.expiresMin + SKEW` принимается, за ними — `bad-cert-time`. Ответ содержит `inviteSnap` только при действительном `joinCert`; повторный `POST /join` тем же `joinCert` возвращает тот же ответ, после поворота приглашения — 409 `already-member`. `join/preview` не содержит `inviteSnap`.
- `rotate` без `inviteCert` при `requireApproval = false` — 400; срок больше 720 ч — 400; **клиентские часы, сбитые на ±3, ±9 минут (внутри `SERVER_WINDOW`), — принимается** (сверяется длительность `expiresMin − issuedMin` с точностью ±1 минута, а не абсолютное время), длительность, отличающаяся на 2 минуты, — 400; выключение и поворот обнуляют `invite_cert`, `invite_snap`, `invite_actor_id`, `join` остаются.
- Выход и удаление аккаунта удаляют сертификаты (оба направления); выход автора приглашения обнуляет `invite_*`, код остаётся и принимает только заявки; каскад при удалении комнаты.
- Лимит: не более 4 допусков (`vouch` и `revouch`) на субъекта.
- **Транзакция `member-certs` (М13):** вставка при субъекте или подписавшем, которых уже нет в комнате, — 404 и пустая таблица; гонка «выход + `member-certs`» в обоих порядках (два соединения) не оставляет строк; порядок блокировок `users → rooms → room_participants → room_member_certs`.
- **Размеры (повторное ревью 10):** `approve`, `rotate`, `member-certs` принимают тело со снимком на 1000 участников (≈ 21,3 тыс. символов base64) и на 1024 (≈ 21,8 тыс.) и отвечают 413 на тело больше 32 КБ; ответ `participants` на комнате из 1000 участников не содержит чужих сертификатов (проверка порядка величины); `GET member-certs?subjects=` — до 200 id, больше — 400, ответ на 200 субъектов с четырьмя допусками и `join` не больше ≈ 0,5 МБ; снимки есть только у адресата.
- Параллельные одобрения и выход подписавшего — без `40P01` в ответах.

## 14. Выкат

- Схема — в DDL `initDatabase` (R0). Старых комнат нет: у каждой комнаты с самого начала известны `V` создателя и сертификаты.
- Клиент и сервер выкатываются вместе. Старая вкладка получает 400 `client-outdated` на изменяющие запросы без общего признака версии `proto: 4` (message-ordering.md §14.1); `approve` без сертификата — 400 `cert-required`.
- Новые ограничения (одобрение, вход по коду, вход без одобрения не дольше 720 ч) требуют обновления «Как это работает», подсказок в окне приглашения и README (T5.1).
- Откат релиза — по R0: остановить сервис, удалить базу, развернуть прежнюю версию.

## 15. Запасной путь: если T4.2 выкатывается поверх рабочей базы

Нужен, только если версия до T4.2 уже выкачена и в ней есть настоящие комнаты (вопрос 1).

- `lib/migrations/04NN-signed-membership.js`, идемпотентная: `CREATE TABLE room_member_certs`, `ALTER TABLE rooms ADD COLUMN invite_cert, invite_snap, invite_actor_id`.
- Существующие комнаты: у клиента нет `trusted:<room>`. При первом запуске нового клиента `V` = весь список сервера `S`, `how = manual`, `by = null`, `bootstrapDone` записывается — комната «переходит» на текущий состав как на доверенный; новые добавления требуют сертификатов. Это ослабление действует только для состава на момент обновления и показывается пользователю один раз; в снимки такие участники не входят (`manual`).
- Старые ссылки без секрета становятся заявками (так и в основном пути).

## 16. Ворота G4

Предупреждения о составе группы: призрак, добавленный через БД, не получает ключ и виден в окне участников как «не подтверждён»; баннер и лента показывают текст; одобрение и вход по ссылке подписываются; повороты не ломают чтение истории; сервер не может навязать якорь создателю или участнику с готовым `V`.

## Приложение: что менять в коде

Сервер:

- DDL: `room_member_certs` (`kind` 1, 3, 4; `snap`; проверки длины), `rooms.invite_cert`, `invite_snap`, `invite_actor_id` и `CHECK`; удаление при выходе и удалении аккаунта; `lib/membership-certs.js` (новый): разбор фиксированных макетов, `verifyCert`, строгая проверка Ed25519 (6.1: каноничность `y < p`, `x = 0` при бите знака 1 — отказ, `[8]P ≠ O`, `S < L`; для ключей и точки `R`), лимиты, `snapHash`.
- Маршруты раздела 7.2 (`server.js`: `approve`, `join`, `join/preview`, `invite/rotate`, `invite/disable`, `join-requests`; `lib/e2ee-groups.js`: `participants` (только свои сертификаты), `GET member-certs?subjects=`, `POST member-certs` в транзакции 7.1; `approve` и `join` — транзакции вступления 7.1; `join` отдаёт `inviteSnap`, `join/preview` — нет); лимит тела 32 КБ у `approve`, `invite/rotate`, `POST member-certs`; `invite/rotate` сверяет длительность срока; `proto: 4` во всех изменяющих запросах (включая `invite/disable`); ограничение `INVITE_TTL_HOURS` значением 720 ч при `requireApproval = false`.

Клиент:

- `public/lib/membership.js` (новый, UMD, чистые функции): разбор и сборка сертификатов, `memkey` v2, `snapHash`, хэш взгляда, ключ приглашения из секрета, строгая проверка Ed25519, проверка снимка. Запись в `CLIENT_SCRIPTS` теста `test/client-static.test.js`.
- `public/e2ee.js`: `verifyMembershipLocked` (без сети в блокировке), `joinIntent` (с `inviteHash`, `inviteSnap`)/`bootstrapDone`, `removed` (для всех ушедших из прежнего `S`), стирание записей комнаты при собственном выходе, отправка ключа только `recipients`, журнал доставок `delivered:<room>:<senderKeyId>` (запись в `prepareShareForPeer` до сети), `entitled` = пары `{id, memkey}` из `recipients` на момент создания ключа (правки `knownMemberIdsLocked`, сейчас возвращающей весь `S`, и `rotateRoomKeyLocked` / `ensureRoomSession`, где `entitledNow` — все, кроме меня), правило ротации по журналу (`answerKeyRequests` отвечает только `recipients`; `acceptPeerIdentityChange` и `answerKeyRequests` стирают `sharedWith2`, но не журнал), `ext.view` и правила разбора `ext` (2048 символов, отбрасывание справочных полей), `runViewChecks`, `signApproval`, `signInvite`, `prepareJoin`, `trustMember`, `vouchForMember`, очередь `revouch`, `getMembers`; `parseSkdm` — поле `ext`; `keyConflicts` не нужен.
- `public/script.js`: окно участников (в том числе «Поручиться за участника»), лента, баннер, окно приглашения (ссылка по `certHash`), одобрение с подписью и снимком, разбор `#join=` (секрет передаётся в `prepareJoin`, затем стирается).
