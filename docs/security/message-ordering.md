## 1. Что решено

1. Порядок сообщений внутри области (комнаты или чата с ботом) задаёт `messages.seq`. Его выдаёт триггер `BEFORE INSERT` из счётчика в строке области. `created_at` и `id` порядка не задают.
2. `messages.id` — случайное целое из `[1 000 000; 2^31−1]`. Id сообщения комнаты выбирает клиент (`clientMessageId`) до шифрования и кладёт внутрь E2EE-содержимого (`mid`).
3. Повтор запроса после обрыва связи идемпотентен. Конфликт id — 409, клиент выбирает новый id и шифрует заново.
4. Id удалённого сообщения нельзя занять 30 дней («надгробие»).
5. Время хранится грубо: минуты, пять минут, час, день — по таблице раздела 11. Точное время сообщения — только внутри конверта (`ts`).
6. Все операции над одной комнатой берут блокировки в одном порядке: `users → rooms → room_participants → chats → room_member_certs → user_left_rooms → upload_quota → messages` (таблицы волны 4 — в §8.1); журнал ключей — отдельный домен `kt_state → identity_keys → kt_pending`. При взаимной блокировке (`40P01`) операция повторяется один раз.
7. Две вкладки одного аккаунта не шифруют одновременно: `createClient({ lock })` на Web Locks.
8. Старый клиент получает 400 `client-outdated`: без `clientMessageId` в отправке и без общего признака версии `proto: 4` в изменяющих запросах волны 4 (§14.1). Перенумерации, переходных режимов и миграций нет (R0).

## 2. Цели и не-цели

### Цели

- **Ц1.** Сообщения внутри области упорядочены одинаково у всех участников, хотя `created_at` хранится с точностью до минуты.
- **Ц2.** `messages.id` не раскрывает ни числа сообщений на сервере, ни темпа его роста, ни порядка сообщений.
- **Ц3.** Номер сообщения известен клиенту до шифрования и входит в зашифрованное содержимое: сервер не может выдать конверт или правку одного сообщения за другое.
- **Ц4.** Поминутная и посекундная хронология активности не восстанавливается по дампу базы, бэкапу и тому с файлами (насколько это совместимо с работой функций).
- **Ц5.** Отправка, вступление, выход и удаление аккаунта в одной комнате не блокируют друг друга намертво. Граница видимости истории у новичка точна: он видит ровно то, что отправлено после его вступления.
- **Ц6.** Повтор того же запроса после обрыва связи не создаёт дубля.

### Не-цели

- **Н1.** Скрыть порядок и время от работающего сервера: он видит каждый запрос в момент его прихода.
- **Н2.** Доказуемо честный порядок. Сервер может переставить, задержать или скрыть сообщение, и клиент в общем случае этого не заметит (раздел 9.6, решение не принимать подсказку R5).
- **Н3.** Скрыть порядок вставки от того, у кого есть физический доступ к Postgres: порядок строк в куче, `xmin`, WAL и сам счётчик `msg_seq` его раскрывают.
- **Н4.** Перенос или перенумерация старых сообщений. По R0 реальных данных нет, при первом запуске новой версии база создаётся заново.
- **Н5.** Изменение формата E2EE-конверта, AAD и подписи. `seq` не входит ни в AAD, ни в подпись, ни в содержимое: он присваивается уже после шифрования.
- **Н6.** Защита от пропажи сообщений (цепочка хэшей сообщений). Это не делается.

## 3. Модель угроз

| Кто | Что видит или умеет | Что даёт этот дизайн | Что остаётся |
|---|---|---|---|
| Читатель дампа или бэкапа БД, без переменных окружения | id, `seq`, `created_at` до минуты, размеры | id случайный и порядка не несёт. Счётчик начинается со случайной базы: новичок не узнаёт, сколько сообщений было до него. Точное время не хранится | `seq` упорядочивает сообщения внутри комнаты; разность `seq` — число сообщений между двумя; минутные метки дают грубую хронологию |
| Тот, у кого физический доступ к Postgres | порядок кортежей, `xmin`, WAL | ничего | порядок вставки виден (Н3) |
| Работающий злонамеренный сервер | каждый запрос с точным временем, куками, сокетом, IP | `mid` закрывает выдачу конверта под чужим номером и перенос правки; `edits` закрывает откат правки и смену автора правки у тех, кто видел прежнюю версию | порядок, `seq`, задержки, скрытие сообщений (Н2); откат правки для клиента, который не видел новую |
| Злонамеренный участник комнаты | выбирает id своих сообщений сам | занять id нельзя, если он занят или стоит в надгробии. Запись `edits` хранит автора по `mid`: повторное использование чужого `mid` даёт `'sender-mismatch'` | узкое окно гонки с удалением (раздел 12, строка 8); спам сообщениями |
| Старая вкладка или старый клиент | шлёт запрос без `clientMessageId` | 400 `client-outdated` с просьбой обновить страницу | вкладки, закреплённые service worker, после первого релиза: совместимость API на один релиз (раздел 14) |

### Что сервер может и не может подделать

| Может | Не может |
|---|---|
| выдать сообщения в другом порядке, скрыть или задержать их | выдать конверт под другим id: `mid` внутри содержимого не совпадёт с id строки, получатель покажет `'id-mismatch'` |
| выдать клиенту более старую версию правки, если клиент не видел новую | выдать старую версию правки клиенту, который видел новую: `'stale-edit'` |
| вставить в строку любой настоящий конверт любого участника этой комнаты | подделать конверт: подпись ключа отправителя и AEAD проверяет получатель |
| хранить и отдавать `reply_to_id` как угодно, спрятать цитату | приписать сообщению участника чужую цитату: id цитаты подписан отправителем внутри содержимого (`re`), несовпадение — цитата не показывается |
| назначить любой `created_at` и `seq` | повлиять на показ времени больше, чем на ±10 минут: `ts` из конверта используется только в этих пределах |
| отказать в обслуживании | перенести конверт в другую комнату: `roomId` входит в AAD и подпись (формат не меняется) |

## 4. Решения и отличия от рабочих планов

| Что | Решение | Откуда расхождение |
|---|---|---|
| Тип и формат id | `INTEGER`, строка из цифр `^[1-9]\d{6,9}$`, не больше `2147483647` | план криптографии предлагал 22 символа base64url, план сервера оставлял генерацию на сервере; верен roadmap R1 |
| Кто выбирает id | клиент для комнат, сервер для чата с ботом | roadmap R1 |
| Блокировка строки комнаты в `addRoomMember` | `FOR NO KEY UPDATE`, как в коде сегодня. Достаточно: она конфликтует с `UPDATE rooms SET msg_seq` в триггере отправки. `FOR UPDATE` остаётся в выходе из комнаты и удалении комнаты | roadmap R1 пишет «`rooms FOR UPDATE`»; `FOR UPDATE` без нужды блокирует внешние ключи (`KEY SHARE`) всех вставок, ссылающихся на комнату. Подтвердить у интегратора (раздел 15, вопрос 1) |
| Блокировка `users` при отправке | берёт приложение явно, а не триггер | план сервера брал её в триггере по `NEW.user_id`. В строках сообщений комнат `user_id` отсутствует (R8), поэтому триггер ничего не узнает |
| Отправка в комнату: проверка участия | внутри транзакции под `rooms FOR NO KEY UPDATE`: `users KEY SHARE → rooms → проверка room_participants → INSERT` | первая редакция брала только `users`; проверка до транзакции оставляла гонку «выход без сообщений + отправка» (ревью С4, [sealed-sender.md](sealed-sender.md) §8.5) |
| Внешний ключ `messages.chat_id` | `ON DELETE CASCADE` | в первой редакции — `ON DELETE SET NULL`, как в коде. `SET NULL` нарушил бы `CHECK messages_author_scope` для строк чата с ботом (`room_id IS NULL ⇒ chat_id IS NOT NULL`) при удалении строки `chats`; для комнатных строк `chat_id` и так `NULL` (ревью, раздел 4; [sealed-sender.md](sealed-sender.md) §5) |
| Общий признак версии клиента | поле `proto: 4` во всех изменяющих запросах волны 4 (§14.1) | отдельные маркеры (`sealed: true`, `cert-required` как признак версии) заменяются одним |
| Надгробия | таблица `message_tombstones`, запись делает триггер `AFTER DELETE` на `messages` | roadmap R1 описывает только поведение; триггер не оставляет пути удаления без надгробия (таймер, автор, удаление аккаунта, каскад комнаты) |
| Подсказка о перестановке (R5 плана криптографии) | не принимается как предупреждение пользователю | при двух вкладках шифрование и отправка не атомарны, порядок итераций и порядок `seq` расходятся и у честного сервера (раздел 9.6) |
| Колонка `messages.time` (`HH:MM` в часовом поясе сервера) | рекомендуется убрать: дублирует `created_at`, раскрывает пояс сервера | в roadmap не упомянута; решение интегратора (вопрос 2) |
| Переходная прослойка `msgSeq(m) = m.seq ?? m.id`, `orderMode`, `?before=<id>` в течение релиза | не нужны | R0: старых клиентов и старых данных нет |
| Миграции: `UPDATE messages SET seq = id`, пересчёт `visible_from_id`, удаление soft-delete | не нужны | R0 |

## 5. Данные (итоговая схема, R0)

Всё ниже вносится прямо в `CREATE TABLE` и `initDatabase`, без `ALTER`-миграций. Каталог `lib/migrations` понадобится только после первого релиза.

### 5.1 Функции

```sql
-- Уже есть: nyxo_random_id(target regclass) — случайный id из [1 000 000; 2^31−1]
-- с проверкой занятости. Для messages добавляется DEFAULT (id комнатных сообщений
-- присылает клиент, DEFAULT нужен чату с ботом).

-- База счётчика: равномерно из [0; 2^30). 2^32 делится на 2^30 без остатка — смещения нет.
CREATE OR REPLACE FUNCTION nyxo_random_seq_base() RETURNS integer
LANGUAGE sql VOLATILE AS $$
  SELECT (('x' || substr(replace(gen_random_uuid()::text, '-', ''), 1, 8))::bit(32)::bigint % 1073741824)::integer
$$;
```

Запас до переполнения `INTEGER`: `2^31−1 − 2^30 = 2^30` (около 1,07 млрд сообщений в одной области). При переполнении вставка падает с ошибкой `22003`, и это ошибка сервера (500), а не повод повторять.

### 5.2 Таблицы

```sql
CREATE TABLE rooms (
  id         INTEGER PRIMARY KEY DEFAULT nyxo_random_id('rooms'::regclass),
  -- ...
  msg_seq    INTEGER NOT NULL DEFAULT nyxo_random_seq_base(),   -- последний выданный seq
  created_at TIMESTAMPTZ NOT NULL DEFAULT date_trunc('minute', now())
);

CREATE TABLE chats (
  id            INTEGER PRIMARY KEY DEFAULT nyxo_random_id('chats'::regclass),
  -- ...
  msg_seq       INTEGER NOT NULL DEFAULT nyxo_random_seq_base(),  -- нужен только чату с ботом
  last_read_seq INTEGER NOT NULL,                                 -- задаёт приложение при создании строки
  created_at    TIMESTAMPTZ NOT NULL DEFAULT date_trunc('minute', now())
);

CREATE TABLE room_participants (
  -- ...
  visible_from_seq INTEGER NOT NULL        -- видно сообщения с seq > visible_from_seq
);

CREATE TABLE messages (
  id         INTEGER PRIMARY KEY DEFAULT nyxo_random_id('messages'::regclass),
  seq        INTEGER NOT NULL,             -- присваивает триггер, значение из INSERT игнорируется
  room_id    INTEGER REFERENCES rooms(id) ON DELETE CASCADE,
  chat_id    INTEGER REFERENCES chats(id) ON DELETE CASCADE,   -- только чат с ботом; у комнатных строк NULL (sealed-sender.md §5)
  -- user_id, author_tag и ограничение на них — sealed-sender.md
  -- ...
  created_at TIMESTAMPTZ NOT NULL DEFAULT date_trunc('minute', now()),
  edited_at  TIMESTAMPTZ                   -- до минуты; в API всегда ISO-8601 UTC
);
-- Колонок visible_from_id, last_read_message_id и messages.deleted в итоговой схеме нет.
-- chat_id → CASCADE: при удалении строки chats (удаление аккаунта, пересоздание чата с ботом) строки бота уходят вместе с ней, а триггер
-- nyxo_message_tombstone (AFTER DELETE FOR EACH ROW) оставляет надгробия и для каскадных удалений. Файлы каскадно удалённых строк
-- убирает уборщик файлов-сирот (§11), а не код удаления.

CREATE UNIQUE INDEX idx_messages_room_seq ON messages (room_id, seq) WHERE room_id IS NOT NULL;
CREATE UNIQUE INDEX idx_messages_chat_seq ON messages (chat_id, seq) WHERE room_id IS NULL;
-- Список INCLUDE (колонки для index-only scan последнего сообщения и непрочитанного)
-- задаёт T2.1 по запросам; в нём нет ни id, ни seq (они уже в индексе или в ключе).

CREATE TABLE message_tombstones (
  id         INTEGER PRIMARY KEY,
  expires_at TIMESTAMPTZ NOT NULL          -- с точностью до суток
);
CREATE INDEX idx_message_tombstones_expires ON message_tombstones (expires_at);
```

Тип `edited_at` сегодня `TEXT` с ISO-строкой. Допустимо оставить, но значение пишется уже огрублённым (раздел 11).

### 5.3 Триггеры

```sql
-- Запрещает id из надгробия. Имя триггера идёт раньше seq-триггера (триггеры одного
-- события срабатывают по алфавиту), поэтому запрещённый id не берёт блокировку комнаты.
CREATE OR REPLACE FUNCTION nyxo_message_id_check() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  IF EXISTS (SELECT 1 FROM message_tombstones WHERE id = NEW.id AND expires_at > now()) THEN
    RAISE EXCEPTION 'message id is retired' USING ERRCODE = '23505', CONSTRAINT = 'message_tombstones_pkey';
  END IF;
  RETURN NEW;
END $$;

-- Выдаёт seq. Строка области блокируется на время транзакции вставки: так отправки
-- в одну комнату и вступление новичка выстраиваются в очередь, и seq совпадает
-- с порядком фиксации транзакций.
CREATE OR REPLACE FUNCTION nyxo_message_seq() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  IF NEW.room_id IS NOT NULL THEN
    UPDATE rooms SET msg_seq = msg_seq + 1 WHERE id = NEW.room_id RETURNING msg_seq INTO NEW.seq;
  ELSE
    UPDATE chats SET msg_seq = msg_seq + 1 WHERE id = NEW.chat_id RETURNING msg_seq INTO NEW.seq;
  END IF;
  IF NEW.seq IS NULL THEN
    RAISE EXCEPTION 'message scope not found' USING ERRCODE = '23503';
  END IF;
  RETURN NEW;
END $$;

-- Надгробие при любом удалении строки: таймер, автор, удаление аккаунта, каскад комнаты.
-- Срок: от 30 до 31 суток (округление вверх до суток).
CREATE OR REPLACE FUNCTION nyxo_message_tombstone() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  INSERT INTO message_tombstones (id, expires_at)
  VALUES (OLD.id, date_trunc('day', now()) + interval '31 days')
  ON CONFLICT (id) DO NOTHING;
  RETURN NULL;
END $$;

CREATE TRIGGER messages_10_id_check  BEFORE INSERT ON messages FOR EACH ROW EXECUTE FUNCTION nyxo_message_id_check();
CREATE TRIGGER messages_20_seq       BEFORE INSERT ON messages FOR EACH ROW EXECUTE FUNCTION nyxo_message_seq();
CREATE TRIGGER messages_90_tombstone AFTER  DELETE ON messages FOR EACH ROW EXECUTE FUNCTION nyxo_message_tombstone();
```

Заметки:

- Проверка `NOT NULL` на `seq` выполняется после `BEFORE`-триггеров, поэтому `INSERT` без `seq` допустим.
- Если вставка падает с `23505`, откатывается вся транзакция вместе с `UPDATE rooms SET msg_seq`: пропусков из-за конфликтов нет. Пропуски из-за удалений допустимы всегда.
- Очистка надгробий — фоновая задача (`lib/jobs`, раз в час): `DELETE FROM message_tombstones WHERE expires_at < now()`.
- В надгробии нет ни комнаты, ни автора, ни точного времени: только id и срок с точностью до суток.

## 6. Идентификаторы

### 6.1 Формат

- Строка `^[1-9]\d{6,9}$`, значение не больше `2147483647`. В запросе — только строка; число принимается лишь там, где оно было и раньше (`replyToId`, `messageId` в реакциях).
- В ответах и событиях id всегда `String`, `seq` — `Number`. Тест-запрет (`test/message-order-guard.test.js`) не пускает в код сервера (`server.js`, `src/**`) и в скрипты приложения (`public/js/*.js`) выражения `ORDER BY m.id`, `id < $`, `Number(m.id)`.
- Чистая функция `parseClientMessageId(value)` лежит в `lib/` (её проверяет юнит-тест), клиентская `newClientMessageId()` — в `public/lib/message-order.js` рядом с функциями порядка.

### 6.2 Генерация на клиенте

```js
// 31 случайный бит, значения меньше 1 000 000 отбрасываются (около 0,05 %): без смещения.
function newClientMessageId() {
    const buf = new Uint32Array(1);
    for (;;) {
        crypto.getRandomValues(buf);
        const v = buf[0] & 0x7fffffff;
        if (v >= 1000000) return String(v);
    }
}
```

### 6.3 Проверки на сервере

Порядок проверок в `POST /api/messages` для комнаты (для чата с ботом `clientMessageId` игнорируется, id выдаёт `DEFAULT`):

1. `proto` отсутствует или меньше 4, либо `clientMessageId` отсутствует → 400 `client-outdated` (общее правило — §14.1).
2. Формат неверен → 400 `bad-message-id`.
3. Остальные проверки запроса (E2EE-форма конверта, чат, цитата).
4. Транзакция вставки (раздел 8). Ошибка `23505` с `constraint` равным `messages_pkey` или `message_tombstones_pkey` → разбор конфликта (6.4). Любой другой `23505`, в том числе по `idx_messages_room_seq`, — ошибка сервера (500), повторять её нельзя.

В `POST /api/messages/file` те же пункты 1–2 выполняются в `fileFilter` multer до приёма файла: поля формы до файла уже лежат в `req.body`, как сейчас `encrypted`. Клиент обязан класть `chatId`, `encrypted`, `clientMessageId`, `envelope` в `FormData` до поля `file`. Если поле пришло после файла, при проверке его ещё нет и ответ — 400 `client-outdated`. Предварительная проверка занятости id (запрос к `messages` и `message_tombstones`) тоже выполняется в `fileFilter`: так заведомо конфликтующий файл на диск не пишется.

### 6.4 Конфликты и повторы

При `23505` вне транзакции (вставка откатилась) сервер читает существующую строку по `id`:

```
если строка есть
   и room_id совпадает с комнатой запроса
   и автор строки совпадает с пользователем сессии
        (до R8: user_id; после R8: author_tag = тег(комната, пользователь, неделя created_at строки))
   и расшифрованный на сервере text строки равен присланному конверту
        (для файла: ещё file_url не NULL, конверт тот же)
 → 200 с этой строкой; событие newMessage повторно не рассылается
иначе → 409 { success:false, code:'id-conflict', message:'Идентификатор сообщения занят, повторите отправку' }
```

Надгробие даёт только 409. Файл при любом 409 удаляется с диска, а при повторе той же отправки (200 по существующей строке) второй файл не сохраняется.

Две одинаковые отправки одновременно: вторая останавливается на блокировке строки комнаты в триггере, после фиксации первой получает `23505` и приходит к ветке «200 с существующей строкой». Дубля нет.

### 6.5 Клиент: исходы отправки

| Ответ | Действие клиента |
|---|---|
| 200 | показать сообщение из ответа (дубликат от `newMessage` отсекается по id) |
| обрыв сети, таймаут, 5xx — исход неизвестен | повторить тот же запрос с тем же id и тем же конвертом, не больше трёх раз с нарастающей паузой. Повтор идемпотентен |
| 409 `id-conflict` | взять новый id, зашифровать содержимое заново (новый `mid`, новая итерация цепочки; старая итерация остаётся пропуском, получатели его терпят), повторить. Не больше трёх конфликтов подряд, затем ошибка пользователю |
| 400 `client-outdated` | сообщение «Обновите страницу» и больше не повторять |
| 400 `bad-message-id` | ошибка клиента: не повторять, записать в консоль |

Для файла шифротекст вложения от `mid` не зависит: при 409 заново шифруется только конверт, тот же шифротекст загружается снова.

**Запрос с неизвестным исходом после всех повторов** (клиент, `unknownSend` в `public/js/14-send.js`) запоминается на 5 минут: повторное «Отправить» с тем же текстом, чатом и ответом шлёт его же — с тем же id и конвертом, дубликата не будет. Исключение (повторное ревью клиента W7, RR-9): если мой ключ комнаты (Sender Key) за это время сменился — ротация, например при исключении участника, — старый конверт **не** повторяется, сообщение шифруется заново под новым id. Если первая попытка не дошла, конверт под прежним ключом мог бы прочитать исключённый (сервер по модели угроз может отдать его ему); если дошла — появится дубликат, о чём пользователю сказано. Конфиденциальность здесь важнее дубликата. Для файлов запрос не запоминается вовсе, и тост таймаута не обещает «дубликата не будет» (RR-4).

## 7. Порядок и границы видимости

Сравнение по `seq` допустимо только внутри одной области. Пропуски допустимы (удаления, откат вставки при другой ошибке).

### 7.1 Что меняется в серверных запросах

| Место | Было (`id`) | Станет (`seq`) |
|---|---|---|
| индексы | `(room_id, deleted, id)`, `(chat_id, deleted, id)` | уникальные `(room_id, seq)` и `(chat_id, seq) WHERE room_id IS NULL`; условий `deleted = 0` нигде нет |
| список чатов, последнее сообщение | `MAX(x.id)` при `x.id > visible_from_id` | `MAX(x.seq)` при `x.seq > visible_from_seq` для комнат, по `chat_id` для бота |
| список чатов, непрочитанное | `m.id > c.last_read_message_id` | `m.seq > c.last_read_seq`; фильтр по автору — [sealed-sender.md](sealed-sender.md) |
| список чатов, порядок | `pinned DESC, lm.id DESC` | `pinned DESC, lm.created_at DESC NULLS LAST, c.created_at DESC NULLS LAST, c.id DESC` (при равных минутах порядок стабилен, но произволен) |
| `markChatRead` | `last_read_message_id < $1`, `id > prev AND id <= upTo` | `last_read_seq < $1`, `seq > prev AND seq <= upTo`; событие `messagesRead { up_to_seq }` |
| `GET /api/messages/:chatId` | `id > visible_from`, `?before=<id>`, `ORDER BY id`, `markChatRead(last.id)` | `seq > visible_from_seq`, `?beforeSeq=`, `ORDER BY seq`, `markChatRead(last.seq)`; цитата только при `rt.seq > visible_from_seq` |
| `POST /api/chats/:chatId/read` | `{ upToId }`, `MAX(id)` | `{ upToSeq }`, `MAX(seq)` |
| `scheduleBotReply` | `up_to_id` | `up_to_seq` |
| `POST /api/messages`, проверка цитаты | `m.id > visible_from_id` | `m.seq > visible_from_seq` |
| `addRoomMember` | `visible_from_id = MAX(id)` | `visible_from_seq = rooms.msg_seq`: строка комнаты уже заблокирована, значение читается тем же запросом, который её блокирует |
| `POST /api/chats` (создание комнаты) | `visible_from_id = 0` | `visible_from_seq = 0` |
| `PUT /api/messages/:id`, рассылка правки | `visible_from_id >= messageId` | `visible_from_seq >= message.seq` |
| `userCanAccessMessage` | `visible_from_id < messageId` | `visible_from_seq < m.seq` |
| `GET /api/search` | есть | удаляется (R6) |
| `lib/disappearing-messages.js` | id только как ключ | без изменений |

### 7.2 Маркеры

- `chats.last_read_seq` при создании строки равен счётчику области на этот момент (ничего «фантомно непрочитанного»). Для участника, вступающего позже, это `rooms.msg_seq` на момент вступления. Задаёт приложение явно в трёх местах: создание чата с ботом, создание комнаты, `addRoomMember`.
- Маркер только растёт: `UPDATE chats SET last_read_seq = $1 WHERE id = $2 AND last_read_seq < $1`.
- Сервер ограничивает `upToSeq` фактическим максимумом: `MAX(seq) WHERE seq <= $upTo AND seq > visible_from_seq`. Отметить прочитанным больше, чем есть и видно, нельзя.
- Продвижение маркера отправителем (чтобы собственные сообщения не считались непрочитанными, когда в строке нет автора) описано в [sealed-sender.md](sealed-sender.md). По порядку блокировок оно выполняется отдельным оператором после `COMMIT` вставки: маркер только растёт, и такая перестановка безопасна.

### 7.3 Граница видимости новичка

`addRoomMember` читает `rooms.msg_seq` тем же запросом, который берёт `FOR NO KEY UPDATE` на строку комнаты. Любая отправка в эту комнату либо уже зафиксирована (её `seq ≤ visible_from_seq`, новичок её не видит), либо ждёт на `UPDATE rooms` внутри триггера и получит `seq > visible_from_seq` (новичок её видит). Промежуточных состояний нет. Это инвариант О2 из раздела 10.

### 7.4 Рассылка событий и принятый предел (ревью W7 R2.3)

События сообщения комнаты (`newMessage`, `messageEdited`, `messageDeleted`, `reactionChanged`) уходят после `COMMIT` и не должны доходить до тех, для кого сообщение лежит под границей видимости (`visible_from_seq >= seq`): о сообщении, отправленном до вступления, новичок не знает и о его правке, удалении или реакциях тоже. Сервер читает границы из `room_participants` непосредственно перед рассылкой (`emitVisibleRoomMessage` в `src/services/messages.js`; для удаления — `emitRoomMessagesDeleted` в `src/services/expiry.js`; для реакций — `announceReaction` в `src/http/routes/reactions.js`) и исключает таких участников (`except('user:<id>')`); автору идёт одна копия на `user:<id>` с `mine: true`. Не удалось прочитать границы — комнате событие не отправляется (участники увидят изменение при следующей загрузке истории); для `newMessage` и `messageEdited` автору при этом уходит его копия.

**Принятый предел.** Чтение границ и `emit` — два отдельных шага без общей блокировки, между ними проходят миллисекунды. Участник, который вступил именно в это окно, уже подписан на `room:<id>`, но в прочитанном списке границ его нет (на момент чтения он в комнате ещё не состоял), поэтому он может получить событие сообщения, лежащего ниже его границы. Содержимое он не прочитает: ключа отправителя у него нет (новичок получает ключ отправителя с текущей позиции цепочки, [threat-model.md](../threat-model.md) раздел 2), а файл по ссылке из такого сообщения сервер ему не отдаёт (доступ только участникам, вступившим до сообщения). Утечка — метаданные события: `id`, `seq` и время сообщения (до минуты), то есть факт, что сообщение было, и по `seq` — примерное число сообщений, отправленных незадолго до вступления. Клиент такие события сам не отбрасывает. Предел принят: закрыть окно целиком значило бы держать блокировку комнаты на время рассылки, а утечка ограничена метаданными нескольких сообщений на границе. Инвариант О2 (раздел 10) поэтому относится к истории (`GET /api/messages/:chatId`) и к событиям с этой оговоркой.

## 8. Блокировки

### 8.1 Правило

Основной домен. Таблицы берутся в порядке: **users → rooms → room_participants → chats → room_member_certs → user_left_rooms → upload_quota → messages**. Строки одной таблицы — по возрастанию id. Для вставок, ссылающихся на несколько родителей, нужных родителей блокируют явно и заранее: порядок, в котором Postgres проверяет внешние ключи, определяется порядком их создания и неуправляем.

Домен журнала ключей ([key-transparency.md](key-transparency.md)). Таблицы берутся в порядке: **kt_state → identity_keys → kt_pending** (регистрация ключа, закрытие эпохи, начало поколения). Операция, которой нужны оба домена (удаление аккаунта), берёт основной домен целиком, затем домен журнала в том же порядке; регистрация ключа из основного домена берёт только строку `users` (`FOR KEY SHARE`, первой — до `kt_state`): у `identity_keys` нет внешнего ключа на `users`, и без этой блокировки регистрация, шедшая вместе с удалением аккаунта, оставляла сирот (ревью W7 R2.6).

Откуда таблицы. `room_member_certs` — сертификаты допуска ([signed-membership.md](signed-membership.md) §7.1); `user_left_rooms` — комнаты вышедших с оставшимися сообщениями ([sealed-sender.md](sealed-sender.md) §5); `upload_quota` — квота вложений под псевдонимом (sealed-sender.md §13); `upload_quota` берётся только в транзакциях, уже державших `users` (`KEY SHARE` при отправке вложения, `FOR UPDATE` при удалении аккаунта), поэтому циклов с другими таблицами не образует.

Уровни:

- `users` — `FOR KEY SHARE` у всех, кто пишет строки, ссылающиеся на пользователя; `FOR UPDATE` — только удаление аккаунта.
- `rooms` — `FOR NO KEY UPDATE` (вступление; отправка сообщения и запись сертификата в комнате; также неявно триггером отправки, `UPDATE msg_seq`); `FOR UPDATE` — выход из комнаты и её удаление.
- `kt_state` — `FOR SHARE` у регистрации ключа и удаления аккаунта; `FOR UPDATE` — закрытие эпохи и начало поколения.

### 8.2 Последовательности по операциям

| Операция | Последовательность | Что менять в коде |
|---|---|---|
| Отправка в комнату (`POST /api/messages`, `/file`) | `BEGIN` → `users(я) KEY SHARE` (нет строки → 401) → `rooms FOR NO KEY UPDATE` → проверка `room_participants` (нет → 403) → [вложение: резервирование `upload_quota`] → `INSERT messages` (триггер: `rooms UPDATE msg_seq`) → `COMMIT`. `INSERT` — последний оператор | сегодня вставка идёт без транзакции и без блокировки `users`; защита от гонки с удалением аккаунта держится на внешнем ключе `messages.user_id`, которого у сообщений комнат больше не будет. Проверка участия внутри транзакции — [sealed-sender.md](sealed-sender.md) §8.5 |
| Отправка в чат с ботом | то же, триггер обновляет `chats.msg_seq` | то же |
| Вступление (`addRoomMember`: код без одобрения и одобрение) | `users(новичок) KEY SHARE` → `rooms NO KEY UPDATE` (читается `msg_seq`) → проверки → `room_participants` → `chats` → `room_member_certs` (сертификат допуска или входа) → удаление заявки | сегодня `users` берётся внутри `check` после `rooms` (обратный порядок); перенести в начало `addRoomMember`. При одобрении участие подписавшего проверяется **после** `rooms NO KEY UPDATE`, при входе по ссылке `rooms.invite_cert` и `invite_snap` читаются под той же блокировкой ([signed-membership.md](signed-membership.md) §7.1) |
| Запись сертификата (`POST /api/chats/:chatId/member-certs`) | `users(я) KEY SHARE` → `rooms NO KEY UPDATE` → проверка `room_participants` (подписавший и субъект) → число допусков → `room_member_certs` | новая операция; транзакция — [signed-membership.md](signed-membership.md) §7.1 |
| Выход из комнаты (`DELETE /api/chats/:chatId`) | `users(я) KEY SHARE` → `rooms FOR UPDATE` → `room_participants` → `chats` → `room_member_certs` → `user_left_rooms` → `messages` (последний участник: `messages`, `join_requests`, `rooms`) | добавить первый шаг; порядок для таблиц волны 4 — [sealed-sender.md](sealed-sender.md) §12.1 |
| Удаление аккаунта (`deleteUserAccount`) | `users FOR UPDATE` → `rooms FOR UPDATE ORDER BY id` → `room_participants` → `chats` → `room_member_certs` → `user_left_rooms` → `upload_quota` → `messages` → домен журнала (`kt_state FOR SHARE` → `identity_keys` → `kt_pending`) | сегодня `messages` удаляются раньше `room_participants` и `chats`; переставить. Порядок и состав — [sealed-sender.md](sealed-sender.md) §12.2 |
| Регистрация ключа в журнале (`PUT /api/keys/identity`) | одна транзакция: `kt_state FOR SHARE` → `identity_keys` → `kt_pending` | новая операция; `createKeyStore` получает клиент транзакции ([key-transparency.md](key-transparency.md) §6.2) |
| Закрытие эпохи, начало поколения | `kt_state FOR UPDATE` → `identity_keys` → `kt_pending` | задача `lib/jobs` ([key-transparency.md](key-transparency.md) §6.3–6.4) |
| Создание комнаты (`POST /api/chats`) | `users(я) KEY SHARE` → вставки `rooms`, `room_participants`, `chats` | добавить первый шаг |
| Правка, удаление автором, исчезновение по таймеру | только `messages` (и каскады `message_expiry`, `reactions`); надгробие пишет триггер; `room_participants` читается без блокировки ([sealed-sender.md](sealed-sender.md) §8.2) | без изменений |
| `markChatRead` | `UPDATE chats`, затем отдельным оператором `UPDATE messages SET status` | без изменений (разные операторы, не одна транзакция) |
| Создание заявки, ключи (`e2ee_key_shares`), реакции | не обязаны следовать правилу целиком; ошибку `40P01` закрывает повтор | реакции хранят `user_id` до отдельной задачи (R8), поэтому они остаются в зоне повтора |

### 8.3 Повтор при взаимной блокировке

Хелпер `withTransactionRetry(fn)` выполняет транзакцию и при `error.code === '40P01'` повторяет её целиком один раз. Повтор безопасен: первая попытка откатилась, а вставка сообщения идемпотентна по `clientMessageId`. Если повторная попытка тоже упала с `40P01`, клиент получает 503 `busy` с просьбой повторить; в лог пишется только код ошибки, без id (`logError`).

### 8.4 Пропускная способность

Отправки в одну комнату выстраиваются в очередь на её строке. Окно блокировки — один `INSERT` и `COMMIT`, поэтому `INSERT` сообщения должен быть последним оператором транзакции. Для комнаты до 1000 участников это допустимо. Срок жизни сообщения желательно записывать тем же оператором (`WITH m AS (INSERT ... RETURNING id) INSERT INTO message_expiry ...`): так сообщение не остаётся без срока при сбое между операторами. Это желательное улучшение, а не требование.

## 9. Содержимое E2EE: `mid`, `ts`, правки

### 9.1 Формат

```
{ t:'text', b:'…',                    mid:'<id>', ts:<мс>, e?:1, re?:'<id>' }
{ t:'file', mime, name, size, key, iv, caption, mid:'<id>', ts:<мс> }
```

- `mid` — строка, равная `String(id сообщения)`. Обязателен для всех сообщений комнат.
- `ts` — время отправителя в миллисекундах от эпохи, безопасное целое неотрицательное число.
- `re` — id сообщения, на которое это ответ (строка по формату 6.1; только у текста, в правке тот же `re`, что у исходного). Сервер хранит `reply_to_id` открыто и отдаёт цитату сам, поэтому без `re` он мог бы приписать сообщению участника любую настоящую цитату (ревью R4 W7, З3). Клиент показывает цитату сервера, только если её id равен `re` из расшифрованного содержимого (`result.replyTo`, `NyxoE2eePolicy.replyQuoteTrusted`); иначе цитата не показывается. Некорректный `re` — `'bad-plaintext'`.
- `e: 1` — признак правки. Правятся только текстовые сообщения (кнопка «Редактировать» скрыта у вложений; сервер дополнительно отвергает правку строки с `file_url`).
- Формат конверта `{ v:3, alg:'senderkey-v3', senderKeyId, iteration, iv, ct, sig }` (T5.4: подпись с меткой домена `nyxo-skmsg-v3` и комнатой, AAD `senderkey-v3:…`, см. [sealed-sender.md](sealed-sender.md) 9.3; конверт v2 не принимается, R0). `mid` и `ts` лежат внутри шифротекста и дополнения Padmé.
- Сообщений без `mid` нет (R0). Получатель отвергает их с причиной `'no-mid'`.

### 9.2 API клиента

```
encryptOutgoing(roomId, content, { messageId, edit?, replyTo? })
   replyTo — id сообщения, на которое отвечают (строка по формату 6.1): кладётся внутрь содержимого как re;
   messageId обязателен (строка по формату 6.1), иначе E2eeError('protocol');
   ts = now() для нового сообщения;
   для правки (edit:true): ts = max(now(), ts_текущей_версии + 1), e = 1.

decryptIncoming(roomId, senderIdHint | null, text, messageId)
   → { ok:true, text, file?, senderId, ts, edit, replyTo } | { ok:false, reason }   // replyTo: id из re либо null
```

Новые причины отказа: `'id-mismatch'`, `'sender-mismatch'`, `'stale-edit'`, `'no-mid'`. Тексты — в таблице `E2EE_FAILURE_TEXTS` в `public/js/04-e2ee-rooms.js` (по строке на причину). Подсказка отправителя `senderIdHint` — только для юнит-тестов; production-код в комнатах передаёт `null`, а отправитель определяется по `senderKeyId`, привязанному к нему ([sealed-sender.md](sealed-sender.md) §9.2–9.3).

### 9.3 Запись о версии сообщения

Хранилище ключей устройства, на комнату: `edits:<room>[mid] = { author, ts, keyId, it }` — последняя принятая версия сообщения с этим `mid`: автор (числовой id пользователя), `ts`, `senderKeyId` и итерация конверта. Запись создаётся при первой принятой расшифровке сообщения, оригинала или правки, а не только правок: иначе первая правка не с чем было бы сверять.

Хранить можно по записи на `mid` (`edit:<room>:<mid>`), а не одной картой: запись одной версии не должна переписывать всю карту. Предел — 5000 записей на комнату, вытесняется запись с наименьшим `ts`. Вытесненный `mid` теряет защиту от отката и подмены автора (раздел 12, строка 7). Запись удаляется вместе с историей комнаты (режим «Не хранить историю», таймер комнаты — дизайн в плане 5.2 и 5.3).

### 9.4 Проверки получателя

Выполняются после расшифровки и проверки подписи, **до любой записи** в `seen:<room>:<sender>:<keyId>` и `edits`. Иначе сервер мог бы «отравить» эти таблицы конвертом, который потом не пройдёт проверку.

```
0. снятие дополнения (строго, ревью R4 W7, З7): длина буфера — ровно класс Padmé для объявленной длины (не меньше 256 байт), всё дополнение — нули;
   иначе, как и при испорченном JSON → 'bad-plaintext'. Поля `iv`, `sig`, `ct` конверта — каноническое base64 (алфавит, выравнивание, нулевые лишние биты)
1. c = раскодированное содержимое; нет c.mid                          → 'no-mid'
2. String(c.mid) !== String(messageId)                                 → 'id-mismatch'
3. c.ts не безопасное целое ≥ 0                                        → 'bad-plaintext'
4. rec = edits[mid]
   нет rec:                      принять; записать { author: senderId, ts, keyId, it }
   rec.author !== senderId:      'sender-mismatch'
   (rec.keyId, rec.it) совпадает с конвертом: принять (повторный показ той же версии), запись не менять
   иначе, если c.e === 1:        принять при c.ts > rec.ts, иначе 'stale-edit'; записать новую версию
   иначе (оригинал с другой итерацией при уже известном mid): 'id-mismatch'
5. записать seen[iteration] = String(messageId)  (как сейчас), затем edits
```

Что это закрывает:

- конверт под чужим id, в том числе правку, перенесённую на другое сообщение (шаг 2);
- повторное использование `mid` другим автором (шаг 4, `'sender-mismatch'`);
- откат правки к более старой версии у клиента, видевшего более новую (шаг 4);
- подмена автора правки у клиента, видевшего оригинал.

Что остаётся: клиент, у которого записи нет (первое появление сообщения, очищенное хранилище, вытеснение по пределу), принимает любую версию, прошедшую шаги 1–3. Это предел и в модель угроз вносится честно.

Автор берётся из `senderKeyId` по индексу отправителей (`senderKeyId` выводится из комнаты, отправителя и подписывающего ключа): сервер автора не сообщает.

### 9.5 Показ времени

- У неправленого сообщения (`edited_at` пуст) показывается `ts` из конверта, если `|ts − created_at| ≤ 10 минут`; иначе `created_at`.
- У правленого показывается `created_at`: `ts` правки — время правки, а не создания, и время оригинала сервер перезаписал вместе с текстом. Рядом метка «изменено».
- Интерфейс показывает часы и минуты. `ts` нужен как счётчик версий правки и для точного времени во всплывающей подсказке; на порядок он не влияет.

### 9.6 Почему нет предупреждения о перестановке (R5 плана криптографии)

Идея: внутри одного `senderKeyId` порядок итераций должен совпадать с порядком `seq`. Но шифрование и отправка не атомарны: при двух вкладках одного аккаунта (и даже при быстрой отправке) вкладка A может зашифровать итерацию 5, вкладка B — итерацию 6, а на сервер раньше придёт запрос B. Честный сервер выдаст `seq` в порядке прихода, и проверка даст ложную тревогу. Удержание блокировки на время сети недопустимо. Поэтому проверка не показывается пользователю; по желанию можно считать несовпадения в консоли для отладки.

### 9.7 Две вкладки: Web Locks

В `public/js/03-e2ee-client.js` при создании клиента передаётся блокировка (в коде её собирает `NyxoE2eeLock.makeLock` из `public/lib/e2ee-lock.js`; ниже — суть):

```js
const lock = (typeof navigator !== 'undefined' && navigator.locks)
    ? (fn) => navigator.locks.request('nyxo-e2ee-' + userId, { mode: 'exclusive' }, fn)
    : null;
E2EE.createClient({ storage, userId, lock });
```

`options.lock` уже есть (T0.4): очередь клиента остаётся снаружи, внешняя блокировка — внутри секции. Защищаются критические секции чтения и записи хранилища: продвижение цепочки Sender Key, ротация, установка ключа. Сетевые запросы остаются вне блокировки. Без Web Locks действует внутренняя очередь, как сейчас; запасной вариант «одна активная вкладка» через `BroadcastChannel` не строится (вопрос 3).

## 12. Граничные случаи и атаки

| № | Ситуация | Исход |
|---|---|---|
| 1 | Участник присылает чужой существующий id | PK-конфликт; автор или конверт не совпадают → 409. Чужое сообщение не меняется |
| 2 | Участник присылает id удалённого менее 30 суток назад сообщения | 409 по надгробию |
| 3 | Два одинаковых запроса одновременно | вторая транзакция ждёт строку комнаты, затем получает существующую строку: 200, дубля нет |
| 4 | Ответ 200 потерян, клиент повторяет | 200 по существующей строке |
| 5 | Конверт под чужим id, правка на другое сообщение | `'id-mismatch'`, `seen` и `edits` не меняются |
| 6 | Старая правка после новой | `'stale-edit'`, если запись версии есть |
| 7 | Запись версии вытеснена или хранилище очищено | предел: любая версия, прошедшая шаги 1–3, принимается |
| 8 | Участник занимает id сообщения, которое удаляется в этот момент | узкая гонка: триггер проверки надгробия не видит ещё не зафиксированного надгробия. Клиентская защита (`'sender-mismatch'` по записи `edits`) основная, надгробие — дополнительная серверная |
| 9 | Сервер переставляет сообщения | не обнаруживается (Н2) |
| 10 | Одновременные отправки в одну комнату | очередь на строке комнаты; `seq` без дублей; внутри очереди порядок совпадает с порядком фиксации |
| 11 | Отправка и удаление аккаунта | отправка ждёт `FOR UPDATE` на `users` и затем получает «нет пользователя», сообщение не остаётся без владельца |
| 12 | Вступление и отправка одновременно | граница `visible_from_seq` точная (О2) |
| 13 | `40P01` | один повтор; затем 503 `busy` |
| 14 | `seq` близок к переполнению | недостижимо на практике (запас 2^30); при `22003` — 500 |
| 15 | Часы отправителя уходят | `ts` вне ±10 минут от `created_at` не используется для показа |
| 16 | Восстановление базы из бэкапа | счётчики откатываются, новые `seq` могут совпасть по значению с уже показанными клиентам. Курсоры живут только в памяти вкладки; клиент после перезагрузки согласуется. Явно в модель угроз бэкапов |

| 18 | Тот же `seq` у двух разных `id` у одного клиента | дубликатом считается только совпадающий `id`; расхождение `seq` у уже известного `id` игнорируется и пишется в консоль |

| 20 | Запись сертификата одновременно с выходом субъекта или подписавшего | транзакция `member-certs` под блокировкой `rooms`: второй получает 404, строк без владельца нет |
| 21 | Регистрация ключа одновременно с закрытием эпохи и удалением аккаунта | порядок домена журнала `kt_state → identity_keys → kt_pending`; `40P01` не возникает, SKT выдан на ту эпоху, в которую попала запись |

## 13. Клиент: алгоритмы

### 13.1 Курсоры и вставка

- Переменные: `oldestSeq`, `lastSeenSeq` (вместо `oldestMessageId`, `lastSeenMessageId`), у каждого DOM-узла сообщения `data-message-id` (строка) и `data-seq`.
- `GET /api/messages/:chatId?beforeSeq=<oldestSeq>` для истории вверх.
- `appendMessage` → `placeMessageElement(el)`: двоичный поиск места по `seq`, служебные строки без `data-seq` пропускаются. Защищает от переставленной доставки по сокету.
- `findMessageEl(id)` ищет через `CSS.escape`. `updateReplyQuotes` сравнивает id как строки.
- `lastRenderedMessage()` возвращает `{ id, seq }`; `markVisibleMessagesRead` отправляет `{ upToSeq }`.
- Событие `messagesRead { up_to_seq }`: отмечаются свои сообщения с `Number(el.dataset.seq) <= up_to_seq`.
- `refreshCurrentChat`: диапазон и дедупликация по множеству `String(id)` и по `seq`.
- Чистые функции — `public/lib/message-order.js` (UMD): `insertionIndex(seqs, seq)`, `mergeBySeq`, `dedupById`, `newClientMessageId`. Новый скрипт вносится в `CLIENT_SCRIPTS` теста `test/client-static.test.js`.

### 13.2 Отправка текста

```
sendText(text, { chatId, roomId, replyToId }):
   id = newClientMessageId()
   конверт = client.encryptOutgoing(roomId, text, { messageId: id })
   ответ  = POST /api/messages { chatId, text: конверт, encrypted: true, clientMessageId: id, replyToId }
   (исходы — таблица 6.5)
```

Для файла: `sendOneFile` выбирает id, шифрует файл (ключ и iv внутри конверта) и конверт с `mid`, затем `FormData` с полями в порядке `chatId`, `encrypted`, `clientMessageId`, `envelope`, `file`.

### 13.3 Правка

`encryptOutgoing(roomId, text, { messageId: id, edit: true })`, затем `PUT /api/messages/:id { text: конверт }`. Свою правку клиент принимает по тем же проверкам 9.4, когда видит её в истории или по `messageEdited`.

### 13.4 Показ

Отображаемое время — по правилу 9.5. Счётчик непрочитанного приходит с сервера (`unread`), на клиенте не пересчитывается.

## 14. Выкат

- Схема и триггеры описываются в DDL `initDatabase`. До первого релиза новой версии ничего не мигрирует (R0).
- Старая вкладка без `clientMessageId` (а для изменяющих запросов волны 4 — и без `proto: 4`, §14.1) получает 400 `client-outdated` с текстом «Обновите страницу…», который `sendText` уже показывает тостом (`api()` отдаёт тело JSON, поэтому `code` читается из тела, а статус остаётся для машин). Ответ `GET /api/messages/:chatId?before=<id>` (старый параметр) — 400 `client-outdated`.
- Все ошибки нового контракта имеют тело `{ success:false, code, message }`. Остальные маршруты по-прежнему отвечают 200 с `success:false`: менять их не нужно.
- После первого релиза любое изменение контракта идёт через `lib/migrations` и остаётся совместимым на один релиз: вкладки, закреплённые service worker (T4.3), живут до принятия обновления.
- Откат релиза — по R0: остановить сервис, удалить базу, задеплоить прежнюю версию.

### 14.1 Общий признак версии клиента: `proto`

Волна 4 меняет контракт нескольких изменяющих запросов сразу (отправка в комнату, ключи, сертификаты состава, журнал ключей). Вместо отдельных маркеров на каждый запрос (`sealed: true`, `cert-required` как признак версии, ответ на отсутствие `clientMessageId`) вводится **один общий признак**: целое поле `proto` в теле запроса. Текущее значение — `4` (`PROTO_CURRENT`), минимальное, которое принимает сервер, — `4` (`PROTO_MIN`, константа в `lib/proto.js`).

- **Какие запросы несут `proto`.** Все изменяющие запросы волны 4: `POST /api/messages`, `POST /api/messages/file`, `PUT /api/messages/:id`, `POST /api/keys/key-shares`, `PUT /api/keys/identity`, `POST /api/join-requests/:id/approve`, `POST /api/chats/join`, `POST /api/chats/:chatId/member-certs`, `POST /api/chats/:chatId/invite/rotate`, `POST /api/chats/:chatId/invite/disable` (signed-membership.md §7.2: все изменяющие запросы состава несут `proto`). Чтения (`GET`) признак не несут: они совместимы, старая страница получает данные и показывает «Участник группы» либо баннер «Обновите страницу».
- **Ответ сервера.** Поле отсутствует, не целое или меньше `PROTO_MIN` — 400 `{ success:false, code:'client-outdated', message:'Обновите страницу…' }`. Значение больше `PROTO_CURRENT` принимается (будущий клиент против старого сервера возможен только при несовместном выкате; в одном выкате такого нет).
- **Порядок проверок.** Первая проверка запроса — `proto` (до `clientMessageId` и остальных, §6.3), чтобы старая вкладка получала одну понятную ошибку.
- **`multipart/form-data`.** Для `POST /api/messages/file` поле `proto` кладётся в `FormData` **до** поля `file`, как `clientMessageId`; проверяется в `fileFilter` multer до приёма файла. Поле после файла при проверке ещё не видно — ответ `client-outdated`, файл на диск не пишется.
- **Единственный источник.** Клиент берёт значение из константы `PROTO_VERSION` (`public/e2ee.js` для запросов ключей, `public/js/04-e2ee-rooms.js` для запросов страницы), сервер — из `lib/proto.js`; тест `test/proto-client.test.js` сверяет константу `e2ee.js` с серверной. Менять признак — только вместе с несовместимым изменением контракта; увеличение на единицу не требует новых маркеров в запросах.
- **Что не меняется.** Остальные коды `client-outdated` из §6 и §7 (старый параметр `?before=`, `{ upToId }`) сохраняются; `bad-message-id` — отдельный код ошибки клиента, а не устаревшей вкладки.

  - два клиента на одном `MemoryStorage` с общей блокировкой получают разные итерации; без блокировки воспроизводится коллизия (контрольный прогон).
- Серверные юнит-тесты на фейковой БД (`makeFakeApp`, `makeFakeDb`): форма ответов 400 `client-outdated`, 400 `bad-message-id`, 409 `id-conflict`; порядок полей `FormData` и проверка в `fileFilter`.
- Тест-запрет: в `server.js`, `src/**` и `public/js/*.js` нет `ORDER BY m.id`, `id < $`, `Number(m.id)`.

### Сквозные (настоящий Postgres)

Набор `messages-order`:

- `seq` уникален и строго растёт при N параллельных отправках в одну комнату; в ответах нет `40P01`;
- одновременные отправка и вступление: граница `visible_from_seq` точна, новичок видит ровно сообщения после вступления;
- начальный `msg_seq` у разных комнат различается и не равен нулю; новичок не может по `seq` определить число сообщений до себя;
- идемпотентность: повтор того же запроса — один ряд; параллельные одинаковые запросы — один ряд; тот же id другим автором — 409;
- надгробия: удаление автором, по таймеру, при удалении аккаунта и каскадом комнаты оставляет надгробие; id из надгробия — 409; после сдвига часов на 31 сутки и запуска очистки id принимается;
- файл: `clientMessageId` в `FormData` до файла проверяется до приёма; при 409 файл удалён с диска; повтор той же отправки не создаёт второй файл;
- старый клиент: запрос без `clientMessageId` в комнату — 400 `client-outdated`; старый параметр `before` — 400;
- время: все `created_at` и `edited_at` кратны минуте; `last_active_at` кратно пяти минутам и не меньше момента запроса; `expires_at` округлён вверх, сообщение не исчезает раньше срока; имена файлов без цифр времени; `mtime` кратен часу;
- блокировки: отправка и удаление аккаунта, одобрение заявки и удаление заявителя, вход по коду и выход последнего участника — без `40P01` в ответах (повтор допускается, но тест считает случаи); выход без сообщений и отправка в обоих порядках; `member-certs` и выход субъекта; регистрация ключа, закрытие эпохи и удаление аккаунта (домен журнала);
- `messages.chat_id`: удаление строки `chats` чата с ботом каскадом удаляет его сообщения и оставляет надгробия; `CHECK messages_author_scope` не нарушается;
- признак версии клиента: изменяющий запрос без `proto` или с `proto` < 4 — 400 `client-outdated` во всех маршрутах списка §14.1; `proto` в `FormData` после файла — `client-outdated`;
- пагинация вверх по `beforeSeq`, счётчик непрочитанного, `messagesRead { up_to_seq }`;
- несколько сообщений за одну минуту от двоих приходят в порядке `seq`.

### Ворота G2

Старая вкладка получает понятную ошибку «Обновите страницу»; несколько сообщений за минуту от двоих, прокрутка вверх и счётчик непрочитанного работают.

## 16. Решения по открытым вопросам (интегратор, 2026-10-09)

1. **Уровень блокировки комнаты** в `addRoomMember` — `FOR NO KEY UPDATE`: его достаточно для очереди с отправками, и он не блокирует внешние ключи. `FOR UPDATE` — только выход из комнаты и её удаление. Roadmap R1 уточняется этим документом.
2. **Колонка `messages.time`** убирается в итоговой схеме (дублирует `created_at`, раскрывает часовой пояс сервера). Клиент форматирует время сам по правилу 9.5.
3. **Web Locks используются** (раздел 9.7). Запасной путь, когда `navigator.locks` нет, — внутренняя очередь клиента, как сейчас, плюс предупреждение в консоли; «одна активная вкладка» через `BroadcastChannel` не строится.
4. **`bad-message-id`** вводится как отдельный код 400: неверный формат — ошибка клиента, а не устаревшая вкладка.
5. **`mtime` и `atime` файлов** — с точностью до часа, вниз; порог уборщика сирот не меньше двух часов.
6. **Запись версии** делается для каждого принятого сообщения (раздел 9.3), предел 5000 на комнату.
7. **Срок надгробий** — 30 суток (до 31 с округлением вверх до суток); основная защита от повторного `mid` — клиентская (`'sender-mismatch'`).
8. **Правки по ревью криптографа волны 4** (2026-10-10, T4.0): `messages.chat_id` — `ON DELETE CASCADE` (§5.2); единый порядок блокировок для таблиц волны 4 и домен журнала ключей (§8.1–8.2); общий признак версии клиента `proto: 4` вместо отдельных маркеров (§14.1).
