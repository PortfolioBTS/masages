# Миграции схемы

Схема создаётся и обновляется при каждом старте сервера:

1. `initDatabase()` в `src/db/schema.js` — итоговая схема в DDL (`CREATE ... IF NOT EXISTS`).
   **До первого релиза новой версии** (roadmap R0: реальных пользователей нет, старая
   схема 2.0.0 сбрасывается целиком) схема меняется прямо в этих `CREATE TABLE`, без
   `ALTER` и без файлов миграций.
2. Файлы `lib/migrations/NNNN-<имя>.js` — всё новое ПОСЛЕ первого релиза. Раннер
   (`lib/migrations/index.js`) находит их сам и выполняет после `initDatabase()`
   по возрастанию номера.
3. Запись версии в `schema_meta`.

Всё это идёт под advisory-блокировкой Postgres (`lib/advisory-locks.js`):
одновременно мигрирует только один экземпляр сервера, остальные ждут и затем
проходят миграции вхолостую.

## Номера

| Волна | Диапазон |
|---|---|
| 0 (фундамент) | 0001–0099 |
| 1 | 0100–0199 |
| 2 | 0200–0299 |
| N | N00–N99 |

Номер `0000` занят: версия схемы 0 значит «миграций нет». Внутри волны задачи
берут номера по порядку слияния; если номер уже занят — следующий свободный.

## Как написать миграцию

```js
// lib/migrations/0101-users-last-seen.js
'use strict';
module.exports = {
    id: '0101-users-last-seen',   // ровно имя файла без .js
    async up({ pool, client, log, config }) {
        const col = await pool.query(`
            SELECT 1 FROM information_schema.columns
            WHERE table_schema = current_schema() AND table_name = 'users' AND column_name = 'last_seen_at'`);
        if (col.rows.length === 0) {
            await pool.query('ALTER TABLE users ADD COLUMN last_seen_at TIMESTAMPTZ');
        }
    },
};
```

Правила:

- **Идемпотентность обязательна.** Раннер выполняет ВСЕ миграции при каждом
  старте, а не только «новые»: задачи сливаются не по порядку номеров, и
  миграция 0105, слитая после 0110, иначе не выполнилась бы никогда. Миграция
  проверяет состояние (колонка есть? данные уже перенесены?) и ничего не делает,
  если всё сделано. Проверка должна быть дешёвой — она идёт на каждом старте.
- Миграция может выполниться дважды за один старт: при `lock_timeout` (55P03)
  всё повторяется с начала (см. ниже).
- `ctx.pool` — пул сервера, `ctx.client` — соединение, которое держит
  блокировку миграций (для транзакций: `BEGIN`/`COMMIT`/`ROLLBACK` миграция
  делает сама и не оставляет транзакцию открытой). `ctx.log` — `console.log`.
  `ctx.config` — `{ isProduction, uploadsDir, env }`.
- В лог — только счётчики, без id и имён (см. `lib/log-error.js`).
- Схема — `current_schema()`, как в `initDatabase`.
- Тест: юнит-тест логики (если она есть) и сквозной — старт сервера на пустой БД
  и повторный старт (набор `smoke` проверяет, что второй старт не меняет снимок
  схемы).

## lock_timeout и повторы

У всех запросов миграций `lock_timeout = 2.5 с`. DDL на работающей базе
(`ALTER TABLE`, `CREATE INDEX`), которому мешают запросы другого экземпляра, не
встаёт в очередь, задерживая за собой все запросы к таблице, а падает. Тогда
`initDatabase()` и все миграции повторяются целиком, до 5 раз. Не помогло —
сервер выходит с ошибкой, хостинг его перезапускает.

## schema_meta

Одна строка: `schema_version` — наибольший номер миграции, известный коду,
который её записал, и `updated_at` — когда версия изменилась (до минуты).

Если версия в базе **новее**, чем знает код (откат на старую сборку после
миграций новой), сервер не стартует с ошибкой `NYXO_SCHEMA_TOO_NEW`: старый код
на новой схеме мог бы испортить данные. Выход — развернуть новую версию или
восстановить базу из резервной копии.

DDL таблицы (в `database.sql` она попадает из свежей базы). `database.sql` — генерируемый слепок итоговой схемы (источник истины — `initDatabase()` и миграции): его пересоздают после каждой правки схемы или новой миграции командой `pg_dump -s --no-owner --no-privileges` со свежей базы, порядок описан в шапке файла.

DDL `schema_meta`:

```sql
CREATE TABLE IF NOT EXISTS schema_meta (
    singleton BOOLEAN PRIMARY KEY DEFAULT TRUE CHECK (singleton),
    schema_version INTEGER NOT NULL,
    updated_at TIMESTAMPTZ NOT NULL
);
```
