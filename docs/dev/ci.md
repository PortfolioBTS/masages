# CI: что проверяется и как это повторить локально

Конфигурация лежит в `.github/`: `workflows/ci.yml`, `workflows/codeql.yml`, `workflows/release.yml`, `workflows/watchdog.yml`, `dependabot.yml`. Политика зависимостей — `scripts/audit-check.js` и `audit-allowlist.json`. Версии действий и образов в этом документе не перечисляются: они устаревают с каждым PR Dependabot, актуальные значения — в самих файлах.

## Что запускается и когда

| Проверка (имя в GitHub) | Файл | Что делает | Локально |
|---|---|---|---|
| `unit (ubuntu-latest)`, `unit (windows-latest)` | ci.yml | `npm ci`, `npm test`. Windows ловит проблемы с путями и окончаниями строк (разработка идёт на нём), Ubuntu — то, что окружение GitHub отличается от локального | `npm test` |
| `e2e` | ci.yml | Сквозные тесты на настоящем Postgres 16 (сервисный контейнер): `npm run test:e2e`. Раннер сам создаёт отдельную БД на каждый набор. При падении логи серверов сохраняются артефактом `e2e-logs` (7 дней) | `npm run test:e2e:docker`, подробности — `docs/dev/testing.md` |
| `audit` | ci.yml | `npm ci --ignore-scripts`, затем `node scripts/audit-check.js` (политика уязвимостей) и `npm audit signatures` (подписи реестра). Вторая проверка выполняется, даже если упала первая | `npm run audit:check`, `npm audit signatures` |
| `workflows-lint` | ci.yml | actionlint: синтаксис workflow, выражения `${{ }}`, входы действий, shellcheck блоков `run` | см. ниже |
| `analyze (javascript-typescript)`, `analyze (actions)` | codeql.yml | CodeQL, запросы `security-extended`, `build-mode: none`. `actions` анализирует сами workflow. Результаты — Security → Code scanning | отдельно локально не повторяется |
| `build (ubuntu-latest)`, `build (windows-latest)`, `release` | release.yml | Только на теге `v*` (и вручную как репетиция): `npm ci`, `npm test`, манифест клиента на двух ОС, сравнение через `cmp`, аттестация и GitHub Release. В защиту `main` не входят | `node scripts/release-manifest.js` |
| `verify` | watchdog.yml | Раз в сутки сверяет продакшен с манифестом последнего релиза. Выключен, пока не задана переменная репозитория `WATCHDOG_URL`. В защиту `main` не входит | `node scripts/verify-deployment.js <url> --manifest client-manifest.json` |

Расписание: `ci.yml` — push в `main`, любой `pull_request`, ручной запуск и понедельник 03:17 UTC (ловит новые уязвимости без единого коммита); `codeql.yml` — push и PR в `main` и среда 04:41 UTC (GitHub пополняет запросы CodeQL); Dependabot — понедельник 05:00 UTC. Прогоны по расписанию GitHub запускает только на ветке по умолчанию, а в публичном репозитории отключает их после 60 дней без активности: если расписание «замолчало», сделайте любой коммит или включите workflow вручную на вкладке Actions.

Параллельные прогоны: в PR новый push отменяет устаревший прогон, прогоны `main` не отменяются (у каждого коммита должен быть законченный результат).

### Принципы

- Токен только на чтение (`permissions: contents: read` на верхнем уровне каждого workflow); повышенные права — только в job, которому они нужны (CodeQL: `security-events: write`).
- `actions/checkout` всегда с `persist-credentials: false`: токен не остаётся в `.git` и не доступен последующим шагам.
- Секреты в CI не используются вообще, поэтому PR из форков запускаются безопасно. Пароль Postgres `nyxo-ci-only` — одноразовый пароль контейнера, который снаружи недоступен.
- Каждое `uses:` закреплено полным SHA коммита (см. ниже). Это проверяет `test/workflows.test.js` в составе `npm test`: тег или ветка вместо SHA, SHA без комментария версии, разные SHA одного репозитория, `checkout` без `persist-credentials: false`, workflow без `permissions` и `docker run` без digest — тест красный.

## Как повторить локально

Юнит-тесты и политика зависимостей:

```
npm test
npm run audit:check        # нужна сеть: запускает npm audit дважды (прод и все зависимости)
npm audit signatures       # нужен установленный node_modules
```

Проверка workflow (нужен Docker). Образ берётся прямо из `ci.yml`, чтобы локальная проверка не расходилась с CI.

Bash (на Windows в Git Bash добавьте `export MSYS_NO_PATHCONV=1`, иначе путь в `-v` искажается):

```
IMG=$(grep -o 'rhysd/actionlint:[^ ]*' .github/workflows/ci.yml | head -1)
docker run --rm -v "$PWD:/repo:ro" -w /repo "$IMG" -color
```

PowerShell:

```
$img = (Select-String -Path .github\workflows\ci.yml -Pattern 'rhysd/actionlint:\S+').Matches[0].Value
docker run --rm -v "${PWD}:/repo:ro" -w /repo $img -color
```

Чисто — вывода нет и код 0. Флаг `-verbose` покажет, какие файлы проверены.

Поведение на Linux без GitHub можно проверить в WSL или в контейнере `node:24` на чистой копии исходников (`npm ci`, затем `npm test`): так видны различия с Windows — регистр имён файлов, права, окончания строк.

У `dependabot.yml` офлайн-валидатора нет: GitHub показывает ошибки конфигурации на вкладке Insights → Dependency graph → Dependabot после слияния в `main`. При правке держитесь документированных ключей; при создании файла ключи сверялись по JSON-схеме SchemaStore для Dependabot.

## Закрепления: как обновлять

### Действия GitHub

Обычно это делает Dependabot (`github-actions`, по понедельникам): один PR на все действия, он меняет и SHA, и комментарий `# vX.Y.Z`. Перед слиянием прочитайте заметки о выпуске каждого действия — закрепление по SHA защищает от подмены тега, но не от вредоносного коммита, попавшего в настоящий релиз. Для этого и стоит пауза `cooldown` (3 дня): вредоносные релизы чаще всего находят и отзывают в первые дни.

Вручную (новое действие или срочное обновление):

1. Найдите тег: `git ls-remote --tags --refs https://github.com/<владелец>/<репозиторий> | sort -V | tail`.
2. Получите SHA коммита, на который указывает тег:

   ```
   git ls-remote https://github.com/<владелец>/<репозиторий> "refs/tags/<тег>" "refs/tags/<тег>^{}"
   ```

   Если строк две — тег аннотированный, берите SHA со строки `^{}` (это коммит; SHA первой строки — объект тега, а не коммит, и в `uses:` ему не место). Если строка одна — тег простой, и это уже SHA коммита. Например, `v4.38.2` у `github/codeql-action` аннотированный, а `v7.0.1` у `actions/checkout` — простой.
3. Берите SHA только из `ls-remote` официального репозитория: GitHub разрешает обращаться по SHA коммита, существующего лишь в форке этого репозитория, и подсунутый SHA выглядел бы правдоподобно.
4. Запишите `uses: <владелец>/<репозиторий>@<40 символов SHA> # v<версия>`. У одного репозитория действий должен быть один SHA во всех workflow (`github/codeql-action/init` и `/analyze` — один и тот же).
5. Прогоните actionlint и `npm test`.

### Образ actionlint

Он указан в job `workflows-lint` по digest и в `docker run` Dependabot его не видит, поэтому обновляется вручную (раз в квартал и при выходе версии с нужными проверками):

1. Версия: `git ls-remote --tags --refs https://github.com/rhysd/actionlint | sort -V | tail -3`.
2. `docker pull rhysd/actionlint:<версия>`: строка `Digest: sha256:…` в выводе — digest индекса образов, он подходит для всех платформ. Сверьте: `docker buildx imagetools inspect rhysd/actionlint:<версия>` — первая строка `Digest` та же.
3. Замените `rhysd/actionlint:<версия>@sha256:<digest>` в `ci.yml`.
4. `docker run --rm rhysd/actionlint:<версия>@sha256:<digest> -version` печатает версию — убедитесь, что она нужная.

### Образы Postgres и tor-service

`postgres:16-alpine` в сервисном контейнере `e2e` указан тегом: Dependabot его не обновляет, а мажорная версия должна совпадать с локальным контейнером `nyxo-pg-test` и `database.sql`, поэтому её меняют сознательно и вместе. Базовый образ `tor-service/Dockerfile` обновляет Dependabot (`docker`).

## Политика зависимостей (`audit`)

`scripts/audit-check.js` разбирает `npm audit --json` и применяет политику. Сам `npm audit` умеет лишь «падать при находке выше порога» и не различает прод и dev, не знает исключений со сроком и не пишет сводку.

| Область | Порог падения сборки |
|---|---|
| Прод-зависимости (`npm audit --omit=dev`) | **high** и **critical** |
| Только dev (есть в полном отчёте, нет в прод-отчёте) | **critical** |
| moderate, low, info | не блокируют: попадают в сводку (`$GITHUB_STEP_SUMMARY`, вкладка Summary прогона) и в оповещения Dependabot |

Что важно понимать:

- Политика применяется к уникальным advisory (идентификаторы `GHSA-…`), а не к пакетам. Пакет, уязвимый только через зависимость (`via: ["ws"]`), собственной уязвимости не имеет, поэтому исключение на корневой advisory закрывает всю цепочку, а несвязанные находки в тех же пакетах остаются.
- Скрипт запускает `npm audit` дважды: с `--omit=dev` и без. Всё, что есть в первом отчёте, — прод.
- Код выхода: `0` — политика соблюдена; `1` — есть нарушения или просроченные исключения; `2` — не удалось получить или разобрать отчёт (реестр недоступен, изменился формат, повреждён файл исключений). Код `2` — это сбой среды, а не уязвимость: перезапустите job; если повторяется — запустите `npm audit` вручную. Если формат вывода npm изменится так, что находки перестанут разбираться, скрипт упадёт с кодом `2`, а не решит «всё чисто».
- Без сети политику можно проверить на готовом отчёте: `node scripts/audit-check.js --stdin < отчёт.json` (формат — вывод `npm audit --json` или `{"prod": …, "all": …}`); примеры лежат в `test/fixtures/npm-audit/`.

### Что делать при падении

1. Обновите зависимость: `npm audit fix` обновляет пакеты в пределах заявленных диапазонов (обычно меняется только `package-lock.json`); затем `npm test`. Если исправление требует мажорного обновления, оцените его отдельно.
2. Если исправления нет или оно ломает совместимость, а риск для Nyxo приемлем на время, внесите временное исключение.

### Исключения: `audit-allowlist.json`

```json
{
  "exceptions": [
    { "id": "GHSA-xxxx-xxxx-xxxx", "reason": "что за уязвимость, почему можно подождать, какие меры приняты", "expires": "2026-12-31" }
  ]
}
```

- `id` — идентификатор из вывода скрипта (регистр букв не важен), `reason` — обязательная причина, `expires` — дата `YYYY-MM-DD`; исключение действует до конца этого дня по UTC. Рекомендуемый срок — до 90 дней, чем короче, тем лучше.
- **Просроченное исключение роняет сборку** — даже если уязвимость уже исправлена: список нужно чистить, иначе «временное» остаётся навсегда. Исключение, которое ничего не закрывает (уязвимость исправлена или она ниже порога), скрипт перечисляет отдельно: его можно удалить.
- Файл меняется обычным PR; в описании — ссылка на advisory и оценка риска. Без файла исключений нет (строже), а ошибка в формате файла даёт код `2`.
- Исключения можно давать только по `GHSA`: advisory без GitHub-идентификатора (в отчёте остался бы только числовой номер реестра) исключить нельзя, он всегда учитывается.

### Подписи реестра

`npm audit signatures` проверяет подписи реестра и происхождение (provenance) установленных пакетов. Падение означает, что пакет не прошёл проверку подписи (подмена, поломка ключей реестра, пакет не из реестра): не обходите его, разберитесь, откуда пакет.

## Защита `main`: какие проверки сделать обязательными

В Settings → Rules → Rulesets (подробный порядок настройки — `docs/ops/branch-protection.md`) в правиле «Require status checks to pass» добавьте проверки по именам:

- `unit (ubuntu-latest)`
- `unit (windows-latest)`
- `e2e`
- `audit`
- `workflows-lint`
- `analyze (javascript-typescript)`
- `analyze (actions)`

Плюс правило «Require code scanning results» для CodeQL (порог High и выше) и «Require branches to be up to date before merging».

Нюансы:

- Имена в списке появляются только после первого прогона (GitHub предлагает проверки, которые запускались в последнее время) — сначала слейте workflow и дождитесь прогона на `main`.
- `e2e` делайте обязательной только когда в `main` есть `npm run test:e2e` и каталог `test/e2e/` (набор сквозных тестов добавляет отдельная задача): до этого job падает на «Missing script».
- `audit` обязателен намеренно: новая уязвимость, опубликованная между созданием PR и слиянием, остановит и несвязанный PR, пока зависимость не обновлена или не добавлено исключение. Красный `audit` в прогоне по расписанию — сигнал обновить зависимости.
- Имена jobs — часть контракта: переименование молча снимет проверку с защиты. Это охраняет `test/workflows.test.js`.

## Релиз и сторож клиента

Что именно сверяется и как это делает пользователь — `docs/VERIFY.md`; здесь — как устроены workflow.

**Релиз (`release.yml`).** Запускается на тег `v*`; ручной запуск (`workflow_dispatch`) — репетиция без публикации. «Сборка» клиента — сами файлы `public/` (минификации нет), поэтому артефакты воспроизводимы из исходников.

1. Job `build` на Ubuntu и Windows: `npm ci`, `npm test`, `node scripts/release-manifest.js --out release-out` (переменная репозитория `KT_PUBLIC_KEY` — открытый ключ журнала ключей — передаётся в env шага и попадает в `keys.kt` манифеста и `release.json`; пусто — журнал выключен, поля нет). Три файла: `client-manifest.json` (тот же, что отдаёт сервер по `/client-manifest.json`, без commit и времени), `release.json` (версия, commit, время коммита, версия Node, хэш манифеста), `SHA256SUMS` (формат `sha256sum`).
2. Job `release` скачивает результаты обеих ОС и сравнивает `client-manifest.json` и `SHA256SUMS` через `cmp`: если Windows и Linux дали разные байты, релиза нет (причина обычно в окончаниях строк или порядке файлов). `release.json` сравнивается без поля `node`: `setup-node` берёт последнюю 24.x, и на двух ОС она может отличаться.
3. На теге: проверка, что тег равен `v<версия из package.json>` (допустим суффикс `-rc.1`) и commit в `release.json` — коммит тега; `actions/attest-build-provenance` по трём файлам (права `id-token: write`, `attestations: write`); `gh release create --verify-tag` с тремя файлами и хэшем манифеста в описании. Права на запись есть только у job `release`; охраняет `test/release-workflows.test.js`.

Выпуск: поднять `version` в `package.json`, слить в `main`, затем `git tag vX.Y.Z && git push origin vX.Y.Z`. Проверить без публикации: Actions → Release → Run workflow на любой ветке.

**Сторож (`watchdog.yml`).** Раз в сутки (05:41 UTC) на раннере GitHub — то есть вне проверяемого сервера — скачивает манифест последнего релиза, проверяет его аттестацию (`gh attestation verify`) и запускает `scripts/verify-deployment.js` против продакшена. Код 1 (расхождение) — открывает issue «Сторож: клиент на продакшене не совпадает с последним релизом» или дополняет уже открытый, и запуск красный; код 2 (проверить не удалось: сайт недоступен, эталон не читается) — красный запуск без issue. Закрывать issue нужно вручную.

- **Включение:** Settings → Secrets and variables → Actions → Variables → `WATCHDOG_URL` = адрес продакшена (`https://chat.example.com`). Пока переменной нет, job пропускается: сторож выключен по умолчанию.
- **Что он не ловит:** адресную подмену (другой код отдают только отдельным людям) и подмену на уровне самого GitHub. Сразу после выпуска, пока продакшен не обновлён, он покажет расхождение: версию выкаченного кода видно в `release.json`.
- Скрипт сверки берётся из ветки по умолчанию, эталон — из релиза.

## Типовые ситуации

- **`audit`, код `2`.** Сеть или реестр. Перезапустите job; если повторяется — `npm audit` вручную покажет причину.
- **`audit`, нарушения.** См. «Что делать при падении».
- **`e2e`: «Missing script: test:e2e».** Набор сквозных тестов ещё не слит в эту ветку.
- **`e2e` упал.** Скачайте артефакт `e2e-logs` со страницы прогона; логи серверов лежат в `test/e2e/.logs/`.
- **`workflows-lint`.** Сообщение указывает файл, строку и правило; замечания `SC…` — от shellcheck по блокам `run`.
- **CodeQL, первый запуск.** Находки появятся в Security → Code scanning: исправьте или закройте с причиной. Если шум создаёт сторонний код (например, `public/vendor/qrcode.js`), исключите его через `config` с `paths-ignore` в шаге `init`, а не отключайте проверку целиком.
- **PR Dependabot красный.** Прочитайте заметки о выпуске обновлённых пакетов; чаще всего нужна правка кода либо временное исключение одного пакета из обновлений (ключ `ignore` в `dependabot.yml`).

## Известные ограничения

- Сквозные тесты идут только на Linux: сервисные контейнеры GitHub есть лишь там.
- CodeQL с `build-mode: none` для JavaScript — штатный режим, но он не заменяет ревью и аудит криптографии.
- Закрепление по SHA не защищает от вредоносного коммита в настоящем репозитории действия — поэтому PR Dependabot читают, а не сливают вслепую.
- Образ `postgres:16-alpine` закреплён тегом, а не digest (см. выше).
