# Nyxo — план работ

Итоговый план. Основа — план владельца (этапы 0–9). Его доработали четыре архитектора (сервер, клиент, криптография,
качество и инфраструктура), затем три критика проверили сводный черновик (данные и деплой, клиент и E2EE, процесс).
Этот документ главнее рабочих материалов: при расхождении верен он.

Исполнители — ИИ-агенты, каждый в своём git worktree. Интегратор — координирующая сессия: сливает ветки, проходит
ворота и ведёт этот документ. Работа идёт волнами; у каждой волны есть ворота (G0–G6) — проверки, без которых следующая
волна не начинается.

## 1. Решения владельца (не пересматриваются)

1. Только временные аккаунты. Аккаунт удаляется, если не заходить дольше выбранного при входе срока.
2. **Реальных пользователей пока нет — все данные в базе тестовые** (решение от 2026-10-02). Поэтому новая версия при
   первом запуске на старой схеме (v2.0.0) один раз полностью очищает базу и создаёт новую схему. Флаг очистки,
   совместимость с откатом и перенос старых данных не нужны.
3. Аудио убирается полностью, вместе с записью голоса.
4. Бот остаётся и по запросу выдаёт гайд по мессенджеру.
5. MLS/OpenMLS и PQ-ratchet (5.5, 5.7), подписанные приложения Tauri/Capacitor (6.4) — только дизайн-документы.
6. Тесты — с настоящим Postgres в Docker. Коммиты локальные, push и PR — после подтверждения владельца.
7. Готовые решения из плана можно заменять своими, если они качественнее. В конце — разбить большие файлы.

## 2. Сквозные решения

### R0. Схема базы до первого релиза

- **Схема в DDL.** Пока новая версия не выкачена, схема описывается прямо в DDL `initDatabase` («итоговая схема»). Все
  изменения волн 1–6 вносятся в эти CREATE TABLE, без ALTER-миграций.
- **Удаление старого кода.** Шаги совместимости со старыми схемами удаляются целиком: перевыпуск старых кодов, обезличивание
  старых имён файлов, soft-delete, перенос личных таймеров, исправления FK, бэкфиллы.
- **Сброс старой схемы.** Если таблица `users` есть, а таблицы `schema_meta` нет, значит перед нами старая схема. Тогда
  под блокировкой миграций:
  - удаляются все таблицы приложения, функции и таблица `session`;
  - из папки вложений удаляются только файлы с именами по шаблону загрузок (`<цифры>-<hex>.<расширение>`, временные
    `*-cleaned-*`); остальные файлы на volume не трогаются;
  - создаётся итоговая схема и `schema_meta` с версией 1;
  - в лог пишутся только числа.

  Если `schema_meta` уже есть, сброс не выполняется никогда.
- **Будущие релизы.** После выката каталог `lib/migrations/NNNN-*.js` (из T0.1) — единственный способ менять схему.
  Сервер не стартует, если схема в БД новее кода.
- **Локальные БД.** Сквозные тесты каждый раз создают новую БД. Для ручных запусков БД тоже пересоздаётся
  (`npm run dev:local`).

### R1. Идентификатор, порядок и время сообщений (4.1 + 4.4)

**Почему не «created_at + случайный id».** По 4.4 `created_at` огрубляется до минуты, и сортировка по нему перемешала
бы сообщения внутри минуты. Поэтому порядок задаёт отдельный номер.

**Идентификатор.**
- `messages.id INTEGER`, случайный из `[1 000 000, 2^31−1]` (`DEFAULT nyxo_random_id('messages')`).
- **id сообщения комнаты выбирает клиент** (`clientMessageId`). Так он известен до шифрования и кладётся внутрь
  E2EE-содержимого (`mid`): сервер не может выдать правку одного сообщения за другое.
  - Формат строго `^[1-9]\d{6,9}$`, не больше 2147483647.
  - Без `clientMessageId` сообщение в комнату отклоняется: 400 `{code:'client-outdated', message:'Обновите страницу…'}`.
  - Конфликт первичного ключа (только `messages_pkey`) или попадание в «надгробие» → 409 `{code:'id-conflict'}`.
    Клиент выбирает новый id, шифрует заново (новый `mid`) и повторяет не больше трёх раз.
  - Повтор того же запроса (тот же автор и конверт) после обрыва связи → 200 с уже сохранённой строкой, без дубля.
  - «Надгробия» id удалённых сообщений хранятся 30 дней: занять id чужого удалённого сообщения нельзя.
  - `/api/messages/file`: поле `clientMessageId` в FormData идёт до файла и проверяется до приёма файла; при 409 файл
    удаляется.
  - Чат с ботом и служебные строки: id по DEFAULT, при гонке — один повтор на 23505.

**Порядок.**
- `messages.seq INTEGER NOT NULL` внутри области (комната или чат с ботом). Его выдаёт триггер BEFORE INSERT из счётчика
  `rooms.msg_seq` / `chats.msg_seq`. Счётчик начинается со случайной базы: новичок не узнает, сколько сообщений было
  до него.
- Уникальные индексы `(room_id, seq)` и `(chat_id, seq) WHERE room_id IS NULL`.
- Маркеры `room_participants.visible_from_seq` и `chats.last_read_seq` — NOT NULL. Колонок `visible_from_id`,
  `last_read_message_id` и `messages.deleted` в итоговой схеме нет.

**API.**
- `seq` есть во всех ответах и событиях.
- Курсоры: `?beforeSeq=`, `{upToSeq}`, `messagesRead {up_to_seq}`.
- На границе API id приводится к `String`, seq — к `Number`. Тест-запрет не даёт вернуть в server.js и script.js
  `ORDER BY m.id`, `id < $`, `Number(m.id)`.

**Содержимое E2EE.**
- `mid` (= String(id)) обязателен для сообщений комнат.
- `ts` — точное время отправителя; `e:1` — признак правки.
- Получатель проверяет `mid`, автора правки и откат правки. Проверка идёт после расшифровки, но ДО записи в таблицы
  `seen` и `edits`, иначе сервер мог бы «отравить» `seen`. При отказе: `'id-mismatch'`, `'sender-mismatch'`,
  `'stale-edit'`, `'no-mid'`.
- В `edits:<room>[mid]` хранится `{author, ts, keyId, it}`: повторный показ принимается, откат — нет.
- `ts` правки = `max(now, ts текущей версии + 1)`.
- Клиент различает сообщения по паре (id, seq).

**Время.**
- `created_at` и `edited_at` хранятся до минуты во всех таблицах.
- `last_active_at` — с шагом 5 минут, с округлением ВВЕРХ; `message_expiry` — до минуты вверх.
- Строки `session` огрубляет `NyxoPgStore`.
- Ключи и prekey — до дня (задача T3.2).
- Имена загружаемых файлов без `Date.now()`, mtime огрубляется; работает уборщик файлов-сирот.
- Показ времени: у неправленого сообщения — `ts` из конверта, если |ts − created_at| ≤ 10 мин; у правленого —
  `created_at`.

**Блокировки.**
- Порядок везде: users → rooms → room_participants → chats → messages.
- `addRoomMember` сначала берёт `users FOR KEY SHARE`, затем `rooms FOR UPDATE`.
- При 40P01 — один повтор.
- INSERT сообщения — последний оператор транзакции.

**Мультивкладочность.** Две вкладки одного аккаунта сейчас отправляют одну и ту же итерацию Sender Key, и получатель
отвергает второе сообщение как повтор. Межвкладочная блокировка (Web Locks) вводится в T2.1.

### R2. Сессии и срок жизни аккаунта (план сервера, раздел 1.1)

- **Срок без активности:** tab — 30 минут, day — 24 часа, week — 7 дней. Потолка «7 дней от создания» нет.
- **Активность** — HTTP-запрос или открытый сокет. `last_active_at NOT NULL` пишется не чаще раза за шаг 5 минут, с
  округлением вверх.
- **Продление сессии** — раз в 5 минут, маркер `sess.renewBucket`. Кука day/week: `maxAge = L + 15 мин`. Кука tab —
  сессионная, её строку в `session` продлевает touch открытых сокетов. TTL строк — 24 часа.
- **`NyxoPgStore`** огрубляет `expire` и `originalMaxAge` и не хранит `createdAt`.
- **Сессии без `isAnonymous`** недействительны.
- **Клиент** вызывает `GET /api/auth` раз в 4 минуты, при возврате на вкладку, при восстановлении сети и после
  переподключения сокета. Сокет не может продлить куку — её ставит только HTTP-ответ.
- **Повторная регистрация** при живой сессии → 409 `{code:'already-authenticated'}`, проверка до PoW.
- **BroadcastChannel `nyxo-session`** защищает от двух аккаунтов в двух вкладках одного браузера.

### R3. Onion

- Адрес — поле `onionUrl` в `GET /api/auth`: заголовок `Onion-Location` из JavaScript не прочитать.
- Поле отдаётся строго при тех же условиях, что и заголовок; эквивалентность проверяет тест.
- Ссылка «Открыть через Tor» открывает раздел Tor в окне «Как это работает»: там адрес, кнопка «Скопировать» и ссылка
  для Tor Browser.

### R4. Бот

- `lib/bot-guide.js` — чистая функция «текст → ответ».
- **Подсказки.** Подписи кнопок отдаёт сервер: `chat.quickReplies` в `GET /api/messages/:chatId`, только для чата с
  ботом. Клиент рисует их через `textContent` (не больше 6 кнопок и 60 символов), отправляет в тот `chatId`, для
  которого нарисовал, и очищает при смене чата.
- **Приветствие и дисклеймер.** Приветствие `welcomeText(lifetime)` живёт в bot-guide. Дисклеймер «чат не защищён
  сквозным шифрованием» — в каждой реплике.
- **Ограничения текстов.** В текстах гайда нет отпечатков, инструкций сверки кодов и ссылок.

### R5. Аудио

- Сервер — по плану сервера (раздел 2), клиент — по собственному белому списку типов.
- `video/webm` принимается только по сигнатуре EBML.
- Старых аудиосообщений нет (R0), поэтому отрисовка «старого аудио» не нужна.
- `/uploads` отдаёт всё, кроме изображений и видео, с `Content-Disposition: attachment`.
- Аудио внутри зашифрованного вложения сервер отклонить не может — проверяет клиент (в модель угроз).

### R6. Поиск

- `/api/search` удаляется вместе с клиентской заменой (T2.4).
- Список чатов фильтруется на клиенте.
- Поиск идёт по загруженным сообщениям открытого чата.
- Открытый текст на диск не сохраняется.

### R7. E2EE обязательно в комнатах (5.8, план криптографии, раздел 3)

- Сервер принимает в комнате только E2EE-конверты правильной формы (`lib/e2ee-envelope.js`). Открытых сообщений в
  комнатах нет (R0), поэтому пометка «без шифрования» в интерфейсе убирается.
- Открытый текст клиент отправляет только в чат с ботом, id которого он запомнил при создании аккаунта (`botChatId` в
  ответе регистрации), а не по признаку от сервера.
- Выключатель E2EE и флаги `e2ee-enabled:*` удаляются. Ошибки инициализации — `E2eeError{code}`. Состояние шифрования
  показывается под полем ввода.

### R8. Sealed sender (4.3) — частичный, на хранении (план криптографии, раздел 7)

- **Хранение.** У сообщений комнат с самого начала нет `user_id` и `chat_id`, вместо них — недельный `author_tag`.
  Ограничение CHECK на это ставится сразу. Шифрование на сервере — `enc:v3` с привязкой к id сообщения. Отправителя
  клиент находит по `senderKeyId`.
- **Выход из комнаты.** Сообщения остаются, а комната записывается в `user_left_rooms` до удаления аккаунта. Так
  удаление аккаунта по-прежнему удаляет все его сообщения. При выходе свои сообщения можно удалить сразу.
- **Квота и реакции.** Квота вложений — объём загрузок за 30 дней. Реакции пока хранятся с `user_id` (в модель угроз).

### R9. Остальная криптография (план криптографии)

- **По разделам плана:**
  - 5.1 — раздел 4;
  - 5.2 — раздел 5;
  - 5.3 — раздел 6, личная настройка устройства;
  - 5.4 — раздел 8: сертификаты, ссылка-приглашение `#join=<КОД>.<секрет>`, код без секрета превращается в заявку;
  - 5.6 — раздел 9: разреженное Merkle-дерево по часовым эпохам, поколения по 30 дней, `KT_SIGNING_KEY`;
  - 8.2 — раздел 12.
- **Поле `ext` в SKDM.** В T3.1 в SKDM появляется расширяемое поле `ext` внутри AEAD. Туда ложатся `prev` (5.2), `view`
  (5.4) и голова журнала ключей (5.6).
- **IndexedDB.** Версия базы не меняется: новые данные лежат в хранилище `kv` под новыми префиксами ключей.

### R10. Целостность кода клиента (6.1–6.3)

- **Манифест.** Один детерминированный манифест — `lib/client-manifest.js`: без commit, времени и версии Node (они в
  отдельном файле релиза). Сервер отдаёт `/client-manifest.json`, а `scripts/release-manifest.js` на теге даёт
  байт-в-байт тот же файл.
- **Клиент socket.io.** Вендорится в `public/vendor/`, `serveClient: false`.
- **Шаблонизация index.html убирается.** `/link.my` → 301 на `/`, nonce из CSP удаляется, без `'strict-dynamic'`.
- **SRI.** Инструменты делает T3.3, а атрибуты `integrity` включаются после разбиения файлов (волна 6).
- **Service worker** закрепляет хэш манифеста; `sw.js` в манифест не входит.
- **pow-worker.js** не покрыт SRI — у Worker нет integrity (в модель угроз).
- **`Clear-Site-Data`** — только `"cache"`.

### R11. Инфраструктура

- **Лимиты.** Сервис с volume на Railway в нескольких репликах не запускается, поэтому лимиты в Postgres нужны, чтобы
  переживать рестарты.
  - Точные лимиты — в Postgres: регистрация, вход по коду, PoW, ключи. При ошибке хранилища они закрываются (503).
  - Общий лимит `/api` — в памяти.
  - Таблицы UNLOGGED, ключи — HMAC. Адаптера socket.io нет, блокеры реплик описаны в docs/ops/scaling.md.
- **Мониторинг.** `/healthz`, `/readyz` (healthcheck Railway), `/metrics` по токену — без id и IP.
- **CSRF** привязан к сессии; для клиента доставка не меняется.
- **HSTS preload** — по `HSTS_PRELOAD=yes`.
- **security.txt** отдаётся маршрутом (RFC 9116): Contact по умолчанию — GitHub Security Advisories репозитория,
  `Expires` скользящий.
- **Cloudflare.** Проверка IP Cloudflare остаётся — она безвредна и в режиме DNS-only.
- **Ротация `SESSION_SECRET`** сбрасывает лимиты, CSRF и PoW (это есть в docs/ops).

### R12. Тесты

- Юнит-тесты запускает раннер с автообнаружением файлов (уже есть).
- Сквозные тесты:
  - `node:test` и свой клиент сокетов на глобальном `WebSocket`;
  - сервер запускается отдельным процессом, у каждого набора своя БД;
  - фикстура v2.0.0 нужна только для проверки сброса.
- Тестовые ручки работают только при `NODE_ENV=test`: `NYXO_TEST_MAINTENANCE_MS`, `NYXO_TEST_RENEW_INTERVAL_MS`.
- Тесты-запреты (forbidden-terms) — с построчными разрешениями.
- Статика клиента: каждый id из script.js есть в index.html, инлайновых скриптов нет.
- Смоук в настоящем браузере — через CDP, без новых зависимостей (T2.6).
- Ворота прогоняются во временном контейнере (`npm run test:e2e:docker`).

### R13. Точки расширения (снижают конфликты слияния)

- **Сервер:**
  - `lib/migrations/` с `schema_meta` — для релизов после этого;
  - `lib/routes/index.js` — маршруты до сессии и после неё;
  - `lib/jobs/index.js` — фоновые задачи под общей блокировкой.
- **Клиент:**
  - функции `setupXxxListeners`, `sendText` и группы в `elements`;
  - в e2ee.js — экспорт по одному имени в строке, `createClient({lock, now})` и `E2eeError`.

### R14. Разбиение файлов в конце

- **script.js** — на классические скрипты с SRI, а не на ES-модули. Это чистый перенос, его можно проверить
  механически: части, склеенные вместе, дают прежний файл, и повторных имён верхнего уровня нет.
- **server.js** — на `src/` по плану сервера.
- **style.css** — на `public/css/`.
- **e2ee.js** — выносятся только чистые функции; состояние `createClient` остаётся в одном файле.

прерываний. Общие файлы — README.md, database.sql, package.json — правит интегратор. Атрибуты integrity исполнители не
коммитят.

## 4. Деплой у владельца (кратко; полный чек-лист — docs/ops)

1. Задать новые переменные production. Секрет сессий и ключ шифрования сообщений — новые, не утёкшие (пункт 0.1).
2. Задеплоить. При первом старте сервер сам удалит все тестовые данные (в логе строка о сбросе с числами) и создаст
   новую схему. Healthcheck Railway — на `/readyz`. Короткий простой ожидаем.
3. Смоук: вход, группа, сообщение, файл, бот.
4. Откат: остановить сервис, удалить базу (или восстановить пустую) и задеплоить прежнюю версию. Реальных данных пока
   нет, поэтому это безопасно.
5. Очистку истории git от `.env` (0.6) сделать после финального слияния и до первого push.

## 5. Отличия от плана владельца (решения интегратора)

1. Порядок сообщений — по номеру внутри комнаты, а не по `created_at` (иначе конфликт с огрублением времени).
2. Тексты экрана входа честнее макета:
   - «Мы не спрашиваем, кто вы…» — сервер всё-таки видит IP;
   - «Сервер не читает переписку в группах…» — чат с ботом не шифруется;
   - кнопка «Удалить и выйти».
3. Срок по умолчанию на экране входа — «Пока открыта вкладка».
4. Строка «Код: …» (`uniqueCode`) убирается из профиля: она ни на что не влияет.
5. Вместо поэтапного удаления аккаунтов с паролем — разовый сброс всех тестовых данных (решение владельца).
6. При выходе из комнаты сообщения остаются, но удаляются вместе с аккаунтом; при выходе их можно удалить сразу.
7. Квота вложений — объём загрузок за 30 дней (следствие sealed sender).
8. Журнал прозрачности ключей ведётся поколениями по 30 дней, а не бессрочно — по принципу «всё удаляется».
9. Вход по коду без секрета ссылки превращается в заявку (следствие подписанного состава группы).
10. Поиск только на устройстве, в том числе по названиям чатов: сервер не видит запросов.
11. Кнопки бота и тексты гайда приходят с сервера из одного источника.
12. В Postgres хранятся только точные лимиты; общий лимит API — в памяти.
13. Критерий поиска этапа 1 применяется со списком разрешений: фраза интерфейса, проверка URL, env-check.
