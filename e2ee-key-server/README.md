# e2ee-key-server

Сервис **①** из плана «4 Rust-микросервиса» (приоритет №1). Сервер обмена
prekey-bundles в стиле X3DH/PQXDH: клиенты публикуют сюда публичный
ключевой материал, а тот, кто хочет начать переписку, забирает bundle
собеседника и локально (на клиенте) вычисляет общий секрет.

**Сервер никогда не видит и не хранит ни одного приватного ключа и не
выполняет ни одной DH/KEM-операции.** Это только хранилище и верификатор
публичного материала.

## Что это НЕ делает (сознательно вне рамок сервиса)

- Не шифрует и не пересылает сами сообщения — этим занимается
  Node/Socket.IO слой (после того как клиенты через этот сервис обменяются
  ключами, всё дальнейшее шифрование — на клиенте).
- Не реализует Double Ratchet / Sender Keys и не хранит сессионное
  состояние — это клиентская логика (`public/e2ee.js`) поверх результата
  X3DH/PQXDH.
- Не решает, кому чьи ключи можно видеть: проверку общей комнаты и лимиты
  на bundle делает Node-прокси (`lib/e2ee-proxy.js`), см. «Интеграция с Node».
- Не прячет от себя самого, кто чей bundle запросил (см. «Threat model»
  ниже — это осознанно принято, не забыто).

## Threat model (зафиксирована в переписке до этого шага)

| Параметр | Значение | Следствие для этого сервиса |
|---|---|---|
| Адверсарий | L4 — до юридического принуждения включительно | Сервер обязан физически не иметь возможности отдать приватные ключи по запросу/повестке — он их никогда не получает |
| Доверие серверу | Ноль, «слепой ретранслятор» | Сервер не участвует в вычислении общих секретов, только хранит/раздаёт публичные байты |
| Топология | Попарные сессии | Bundle всегда привязан к одному user_id; групповые комнаты строятся клиентом поверх попарных сессий |
| Эфемерность | Оба слоя | `DELETE /internal/v1/keys` для полного стирания; ротация SPK/PQ-prekey и расход OPK поддерживают forward secrecy |
| Mixnet/PIR | **Явно не требуется** (это L5/L6, вне модели) | Сервер намеренно видит связку «кто чей ключ запросил» — задокументировано как принятый риск, а не недосмотр |

## Криптографический дизайн

### Два identity-ключа вместо одного (XEdDSA)

Классический X3DH (Signal) использует один Curve25519-ключ и для DH, и
для подписи — через конвертацию Montgomery↔Edwards (XEdDSA). Здесь
вместо этого используются **два независимых ключа на пользователя**:

- `identity_signing_key` — Ed25519, только для подписи Signed PreKey и
  PQ-prekey;
- `identity_dh_key` — X25519, только для DH1/DH2 в X3DH.

Это осознанное отступление от «чистого» протокола ради простоты и
корректности: не нужен самодельный код конвертации точек между
кривыми — исторически частый источник тонких багов. Итоговые
security-свойства (аутентичность SPK, forward secrecy, deniability)
не страдают.

### Постквантовый prekey (PQXDH)

К классическому bundle добавлен ML-KEM-768 prekey (FIPS 203,
encapsulation key 1184 байта), подписанный тем же `identity_signing_key`
(Ed25519 над **сырыми** 1184 байтами ключа). Клиент, начинающий сессию,
инкапсулирует секрет под этот ключ и подмешивает его к результату X3DH:
запись переписки, перехваченная сегодня, не раскрывается будущим
квантовым компьютером, пока не взломан ML-KEM.

**Честное ограничение: это «last resort» PQ-prekey.** У пользователя один
текущий PQ-prekey (ротация = перезапись, как у SPK), при выдаче bundle
он не расходуется, пула одноразовых PQ-prekey нет. Спецификация PQXDH
такой режим допускает (last-resort ключ используется, когда одноразовых
нет), но цена та же, что у SPK без OPK: все сессии, начатые с
пользователем между двумя ротациями PQ-prekey, используют один и тот же
KEM-ключ. Компрометация его приватной части до ротации ослабляет
PQ-защиту всех этих сессий (классическая часть X3DH при этом не
страдает). Поэтому клиент ротирует PQ-prekey регулярно.

Подпись без доменного префикса: и SPK, и PQ-prekey подписываются одним
ключом над сырыми байтами. Подмены вида «подпись SPK выдать за подпись
PQ-prekey» это не открывает — сообщения разной длины (32 и 1184 байта).

### Что сервер проверяет, а что должен проверять клиент

Сервер проверяет **при загрузке** (defense in depth — отбрасывает
заведомо битые bundle):

- подпись SPK и PQ-prekey ключом `identity_signing_key`;
- длины всех ключей и подписей;
- X25519-ключи: all-zero (известная low-order точка Curve25519);
- ML-KEM-ключ: каждый 12-битный коэффициент < q = 3329 (проверка ввода
  из FIPS 203, которую шифрующая сторона обязана делать перед Encaps)
  и ненулевой вектор t (при t = 0 шифротекст раскрывает секрет).

Так как сервер не доверенная сторона (L4), это **не заменяет**
обязательную повторную проверку подписей и ключей **на стороне клиента**,
получающего bundle, перед тем как использовать SPK/PQ-prekey. Полная
защита от small-subgroup атак — тоже ответственность клиентского кода,
выполняющего сам DH.

## API (внутренний, только для Node-бэкенда)

Все эндпоинты кроме `/healthz` требуют заголовки:
```
X-Internal-Secret: <INTERNAL_SHARED_SECRET>
X-User-Id: <числовой id уже аутентифицированного сессией пользователя>
```

Сервис **не должен** быть доступен из интернета — только Node в той же
приватной сети (loopback при локальном запуске, private networking на
Railway). Секрет — defense in depth, а не основная защита.

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/healthz` | health-check, без авторизации |
| PUT | `/internal/v1/keys/identity` | зарегистрировать/заменить identity-ключи |
| PUT | `/internal/v1/keys/signed-prekey` | ротация Signed PreKey |
| PUT | `/internal/v1/keys/pq-prekey` | ротация ML-KEM-768 PQ-prekey |
| POST | `/internal/v1/keys/one-time-prekeys` | пополнить пул OPK (батч) |
| GET | `/internal/v1/keys/one-time-prekeys/count` | сколько OPK осталось у себя |
| GET | `/internal/v1/keys/identities?ids=1,2,3` | identity-ключи нескольких пользователей (OPK не расходует) |
| GET | `/internal/v1/keys/bundle/:target_user_id` | забрать bundle для старта сессии (атомарно расходует один OPK у target) |
| DELETE | `/internal/v1/keys` | стереть весь ключевой материал вызывающего, включая PQ-prekey |

Ключи и подписи передаются как base64 (`STANDARD` алфавит, с padding).
Ошибки — `{ "success": false, "message": "..." }` со статусом `400`
(неверный ввод или подпись), `401` (нет/неверный секрет или `X-User-Id`),
`404`, `409` (нет identity для проверки подписи), `500`.

### Пример: регистрация identity-ключей

```
PUT /internal/v1/keys/identity
{
  "identity_signing_key": "<base64, 32 байта, Ed25519 pub>",
  "identity_dh_key": "<base64, 32 байта, X25519 pub>"
}
→ { "success": true }
```

### Пример: PQ-prekey

```
PUT /internal/v1/keys/pq-prekey
{
  "key_id": 3,
  "public_key": "<base64, ровно 1184 байта, ML-KEM-768 encapsulation key>",
  "signature": "<base64, 64 байта, Ed25519 identity_signing_key над сырыми байтами public_key>"
}
→ { "success": true }
```
`409`, если identity-ключи вызывающего ещё не зарегистрированы (нечем
проверить подпись). `400` при неверной длине, битом ML-KEM-ключе или
неверной подписи. Повторная загрузка заменяет текущий ключ.

### Пример: identity-ключи участников

```
GET /internal/v1/keys/identities?ids=5,42,7
→ {
  "identities": [
    { "user_id": 5,  "identity_signing_key": "...", "identity_dh_key": "..." },
    { "user_id": 42, "identity_signing_key": "...", "identity_dh_key": "..." }
  ]
}
```
Для проверки safety number и обнаружения смены identity у собеседников.
До 200 положительных id через запятую; повторы схлопываются. Пустой
список, мусор, `0` или больше 200 элементов — `400`. В ответе только
пользователи с зарегистрированным identity, по возрастанию `user_id`
(в примере у пользователя 7 identity нет). OPK не расходуются.

### Пример: получение bundle

```
GET /internal/v1/keys/bundle/42
→ {
  "identity_signing_key": "...",
  "identity_dh_key": "...",
  "signed_prekey": { "key_id": 7, "public_key": "...", "signature": "..." },
  "one_time_prekey": { "key_id": 103, "public_key": "..." } | null,
  "pq_prekey": { "key_id": 3, "public_key": "<1184 байта>", "signature": "..." } | null
}
```
`404`, если у пользователя 42 ещё нет identity-ключей или SPK
(E2EE-онбординг не завершён). `one_time_prekey: null`, если пул исчерпан
— X3DH в этом случае деградирует на один DH-шаг (см. спецификацию X3DH),
сессия остаётся безопасной, но с чуть меньшей forward secrecy для
самого первого сообщения. Клиент должен воспринимать это как сигнал
срочно попросить получателя пополнить OPK. `pq_prekey: null` — у
получателя клиент без ML-KEM; сессия строится классическим X3DH.
Всё читается в одной транзакции с расходом OPK.

## Интеграция с Node

Браузер ходит не сюда, а в Node: `lib/e2ee-proxy.js` регистрирует
маршруты `/api/keys/*`, проверяет сессию (`req.session.userId`) и
проксирует запрос на `KEY_SERVER_URL`, подставляя `X-Internal-Secret`
(`INTERNAL_KEY_SERVER_SECRET`) и `X-User-Id`. Там же то, чего этот сервис
намеренно не делает:

- чужие ключи (bundle, identities) отдаются только тем, у кого с
  владельцем ключей есть общая комната; для identities недоступные id
  молча выкидываются до вызова key-server;
- лимиты на bundle (каждый запрос расходует чужой OPK): 60 в час на
  вызывающего и 5 в час на пару (вызывающий, цель).

`INTERNAL_KEY_SERVER_SECRET` у Node и `INTERNAL_SHARED_SECRET` у этого
сервиса — одно и то же значение (сервис понимает оба имени).

## Схема БД и миграции

Таблицы создаются автоматически при старте: `sqlx::migrate!` встраивает
файлы из `migrations/` в бинарник на этапе компиляции и применяет
недостающие.

- `0001_init.sql` — `identity_keys`, `signed_prekeys`, `one_time_prekeys`.
- `0002_pq_prekeys.sql` — `signed_pq_prekeys` (один текущий PQ-prekey на
  пользователя).

Уже применённые миграции **нельзя менять** — даже перевод строк
(CRLF↔LF): sqlx сверяет их контрольные суммы с таблицей
`_sqlx_migrations`, и сервис перестанет стартовать. Изменения схемы —
только новым файлом `000N_*.sql`. `build.rs` говорит cargo
пересобирать бинарник при изменении `migrations/`, иначе новая миграция
при инкрементальной сборке могла бы не попасть в бинарник.

## Переменные окружения

| Переменная | Обязательна | Назначение |
|---|---|---|
| `DATABASE_URL` | да | Postgres (может быть тот же инстанс, что у Node — схемы не пересекаются) |
| `INTERNAL_SHARED_SECRET` (или `INTERNAL_KEY_SERVER_SECRET`) | да | общий секрет с Node, не короче 32 символов |
| `BIND_ADDR` | нет | адрес прослушивания, по умолчанию `127.0.0.1:7420` (только loopback). В контейнере и на Railway — `[::]:7420`, см. ниже |
| `MAX_OTPK_BATCH` | нет | максимум OPK в одном запросе загрузки (по умолчанию `200`) |
| `RUST_LOG` | нет | уровень логов `tracing` (по умолчанию `info`) |

## Деплой (Dockerfile, Railway)

`Dockerfile` — двухстадийная сборка: `rust:1.94-bookworm` собирает
бинарник с `--locked` (ровно версии из `Cargo.lock`; `migrations/`
копируется до сборки, она нужна `sqlx::migrate!`), рантайм —
`debian:bookworm-slim`, процесс запускается от непривилегированного
пользователя (uid 10001).

```bash
docker build -t e2ee-key-server e2ee-key-server/
docker run --rm -e DATABASE_URL=... -e INTERNAL_SHARED_SECRET=... \
  -e BIND_ADDR=0.0.0.0:7420 -p 127.0.0.1:7420:7420 e2ee-key-server
```

`BIND_ADDR` по умолчанию — `127.0.0.1:7420`, и образ его не
переопределяет: без явного адреса сервис в контейнере недоступен никому,
в том числе Node. Это сознательно — открыть порт должно быть решением
того, кто деплоит.

На Railway:

1. Отдельный сервис из этого репозитория, Root Directory =
   `e2ee-key-server` (Dockerfile подхватывается автоматически).
2. **Не** генерировать для него публичный домен — сервис должен быть
   виден только в private network проекта.
3. Переменные: `DATABASE_URL` (ссылка на Postgres проекта),
   `INTERNAL_SHARED_SECRET` (то же значение, что
   `INTERNAL_KEY_SERVER_SECRET` у Node) и **`BIND_ADDR=[::]:7420`**:
   private networking Railway в окружениях, созданных до октября 2025,
   работает только по IPv6, и сервис, слушающий `127.0.0.1` или
   `0.0.0.0`, будет недоступен для Node. `[::]` на Linux слушает и IPv6,
   и IPv4.
4. У Node-сервиса: `KEY_SERVER_URL=http://<имя-сервиса>.railway.internal:7420`.

## Запуск локально

```bash
# DATABASE_URL и INTERNAL_KEY_SERVER_SECRET берутся из .env в корне
# репозитория (dotenvy ищет .env в текущей папке и выше)
cargo run
curl http://127.0.0.1:7420/healthz
# ok
```

## Тесты

```bash
cargo test
```
Юнит-тесты без БД:

- `crypto.rs` — подписи SPK и PQ-prekey (валидная подпись, подмена
  ключа, чужой подписант, подпись только над префиксом PQ-ключа),
  декодирование ключей (all-zero, неверная длина, границы коэффициентов
  ML-KEM `q - 1`/`q`, нулевой вектор t);
- `handlers.rs` — разбор `?ids=` (сортировка и дедупликация, пустые
  элементы, мусор, `0`, переполнение, лимит 200).

Интеграционных тестов с реальной БД нет — потребуют `DATABASE_URL` в CI.

## Toolchain

`Cargo.toml` требует Rust ≥ 1.75; максимальный MSRV среди зависимостей
в `Cargo.lock` — 1.71, так что lock-файл собирается на любом Rust ≥ 1.75.
Docker-образ закреплён на `rust:1.94-bookworm`. `Cargo.lock` лежит в
репозитории (в отличие от `anon-service`) — сборка воспроизводима.

## Известные ограничения V1 (осознанно, не баги)

- Один identity на пользователя (мультидевайс не поддержан).
- PQ-prekey — «last resort», без одноразовых PQ-prekey (см. выше).
- После замены identity-ключей текущие SPK и PQ-prekey остаются в базе
  до следующей загрузки: они подписаны старым ключом, и клиент-получатель
  отвергнет их при проверке подписи. Клиент загружает новые сразу после
  нового identity.
- Нет rate-limiting на уровне этого сервиса — лимиты на Node-прокси.
- Нет метрик/observability кроме структурных логов через `tracing`.
- Cross-service coupling через общий Postgres — если когда-нибудь
  сервисы физически разъедутся по разным БД, `user_id` как «мягкая»
  внешняя ссылка продолжит работать без изменений схемы.
